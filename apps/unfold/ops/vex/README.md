# OpenVEX statements

Reviewed exploitability statements for findings the release gate should not count. Each statement is scoped to one image at one digest, carries a status and a justification from the OpenVEX vocabulary, and is attested onto the image by the signing step. Harbor's project allowlist stays empty; a suppression without a statement here does not exist.

Both images start at a budget of zero critical and zero high findings in `enforce` mode, as recorded in [ops/security/cve-budgets.yaml](../security/cve-budgets.yaml). The measured state on 2026-09-10 was zero findings at every severity. On 2026-09-27 and 2026-10-03 the image carried statements for CVE-2026-85091 (zlib) and CVE-2026-93748 / GHSA-ch52-4w7c-c8xp (npm's bundled http-cache-semantics). They were removed on 2026-10-18 once rc.92 shipped the fixed zlib 1.3.2-r1 and http-cache-semantics 4.3.0, and grype found neither without them. On 2026-10-18 rc.86 found CVE-2026-77214 (libexpat 2.8.5, High). The fix, libexpat 2.9.0-r0, is in Alpine 3.24 but not yet in dhi.io's mirror. The only program in the image that loaded libexpat was `git-http-push`, git's WebDAV push for dumb HTTP remotes, which agents never use, so the image build deletes it and the statement records the finding as `not_affected`. [check-expat-users.mjs](../agent/check-expat-users.mjs) fails the build if any ELF file names `libexpat.so.1` again. Remove the statement once the base image ships libexpat 2.9.0. Add a statement only after a rebuild on a patched base cannot remove the finding, and reference the [infrastructure VEX guide](https://forgejo.webgrip.dev/webgrip/infrastructure/src/branch/main/ops/vex/README.md) for the file shape.
