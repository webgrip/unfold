# VS Code 1.142 against Unfold: the first real AHP 1.0 client, and what it unblocks

Research date: 2026-10-16. This dossier follows [the 1.141 dossier](2026-10-08-vscode-1-141-fit.md) and [the protocol-gap dossier](2026-10-13-protocol-integration-gaps.md) to the [1.142 release](https://code.visualstudio.com/updates/v1_142) of 14 October 2026. It asks what 1.142 unblocks for Unfold and Ploeg, which new integrations it makes possible, and what comes after it.

Sources:

- the release notes in [raw markdown](https://github.com/microsoft/vscode-docs/blob/main/release-notes/v1_142.md), the 1.143 draft (`v1_143.md`, last updated 2026-10-15) and every agent page they link;

The conditional items are added to the [protocol-gap watchlist](2026-10-13-protocol-integration-gaps.md#watchlist) as T12 to T16.

## Verdict

1.142 adds no extension API and needs no change to the host, but it makes the host's untested half the one that runs. **(source)** VS Code 1.142 offers AHP `1.0.0, 0.10.0, 0.9.0`. Unfold's host picks the highest offered version in either baseline, so every Agents window on 1.142 now negotiates **1.0.0**. That switches on the 1.x catalog path (`SessionSummary.chats`, `defaultChat`), which until now only Microsoft's SDK client has exercised. Both breaks the 1.141 dossier queued, `chat/isReadChanged` on 0.9 connections and `ahp-session:/` session URIs, shipped, and the host already accepts both (`d91f8db0`, `f71edfb5`, in production since rc.46).

What 1.142 unblocks, in order of value:

1. **The desktop acceptance pass can run today** ([VIK-1922](https://vikunja.webgrip.dev/tasks/1922)). The owner's machine has VS Code 1.142.0 and production runs rc.77, which contains every host fix. It has become more urgent: it is the first desktop run of the 1.x path.
2. **A browser link can open a session in the Agents window** ([VIK-1660](https://vikunja.webgrip.dev/tasks/1660)). Session links now carry `connectionAuthority`, so a link can name Unfold's remote host.
3. **The extension can hand out `ploeg-mcp` without a secret** ([VIK-1653](https://vikunja.webgrip.dev/tasks/1653)). The constraint that blocked VIK-1653 was a token written in plaintext to disk. The remote `ploeg-mcp` needs no token in its definition: VS Code signs in itself through the pre-registered client `ploeg-mcp`, and since 1.142 it also asks for `offline_access`, which `ploeg-mcp` advertises. Refresh tokens therefore work.
4. **Background work becomes the natural home for live command output.** 1.142 gives agent-host chats a Background Shells pill with Stop Shell and full scrollback, driven by AHP 1.0's `chat/backgroundWorkSet`. A Run's command can appear there (watchlist T12) once [RFC-0006](../../../../docs/design/rfc-0006-live-command-output.md) phase 2 delivers its output.

The rest of 1.142 serves VS Code's own harnesses: Canvases, moving chats, the Copilot harness as default, and the model picker. Adopt none of it. Two items matter as signals. Enterprise policy can now force every chat onto the Copilot harness, a risk for the agency phase. The backlash against the Copilot harness removing Keep and Undo supports Unfold's review-first stance.

## What 1.142 actually is

The release is a Copilot-harness release. The notes call it "a shared foundation that helps align behavior, capabilities, and improvements across Copilot products". The Copilot harness, "powered by the Copilot SDK", runs through the Agent Host and is "progressively" becoming the default for new sessions. Around it:

- **Canvases (Preview).** `chat.canvases.enabled` adds a surface beside the chat that the person and the agent both edit, such as a Kanban board. Canvas extensions live in `.github/extensions` or `~/.copilot/extensions` and come from `/create-canvas` or a Copilot-app plugin. Desktop only, local Copilot-harness sessions only.
- **Move chats** to another folder or a new Git worktree, by asking the agent. The notes and the docs disagree on which harness supports it (Codex in the notes, the Copilot harness or Codex on the Agent Host in the docs). The protocol shape is AHP 1.0's atomic `moveChat` with a per-chat `movable` flag.
- **Agents window layout.** `sessions.experimental.layoutScope` and Align Panel.
- **Chat.** Harness names prefix chat titles. Stop Shell for attached background shells. Shell output is no longer cut off. `statefulResponses` for BYOK endpoints. A redesigned model picker. Ask is back as a read-only agent in the Copilot harness.
- **Enterprise.**
  - A non-empty managed `permissions` object or `sandbox.enabled: true` moves Local chats to the Copilot harness on the Agent Host, and makes Claude, Codex and terminal chat unavailable.
  - `vscode.temporaryDefaultToLocalHarness` is the temporary opt-out.
  - `permissions.disableBypassPermissionsMode` and `permissions.disableAssistedPermissionsMode` are new.
- **Deprecated:** Windows sandboxing for the Local harness.
- **GitHub Pull Requests 0.170.0:** stacked pull requests on by default, with Update stack.

The notes carry no "Extension authoring", "Proposed APIs" or MCP section, and none is missing. **(source)** `vscode.d.ts` changed only a doc comment. One proposal was added, `customTextEditorNavigation`, and `externalUriOpener` gained `viewColumn`. Both items the 1.141 dossier expected, URL-opening hooks ([#109277](https://github.com/microsoft/vscode/issues/109277)) and contributable chat context ([#271104](https://github.com/microsoft/vscode/issues/271104)), moved to the 1.143.0 milestone.

### The agent host client, changed in source

- **Version.** `PROTOCOL_VERSION` is `'1.1.0'` and the baselines are `['1.0.0', '0.9.0']` (`platform/agentHost/common/state/protocol/version/registry.ts:19,36-38`). The client offers `['1.0.0', '0.10.0', '0.9.0']` (`agentHostProtocolCompatibility.ts:25`; offered at `agentHostProtocolClient.ts:737,1110`). VS Code's private `0.10.0` is kept for its own older hosts.
- **Break A shipped.** `ChatIsReadChanged` is registered as introduced in `0.9.0` (registry.ts:166), so a 0.9 host receives `chat/isReadChanged` on the chat channel. Upstream AHP registers it the same way, which is why [AHP#491](https://github.com/microsoft/agent-host-protocol/issues/491) is still open.
- **Break B shipped.** `createSession` uses `ahp-session:/<uuid>` unless the host is identified as an older native VS Code host, by `_meta['vscode.agentHost']` or a non-empty `_meta.hostBuild.version` (`agentHostSessionUrisMeta.ts:10-25`). Unfold sets neither. The client now always sends `_meta['vscode.ahpSessionUris']: true`.
- **Session links.** `buildOpenSessionLinkUri(…, connectionAuthority?)` adds `connectionAuthority=` and, for a session URI with an authority, query or fragment, `session=<uri>` (`common/openSessionLink.ts:93-103`). A malformed authority invalidates the link (:186). The "needsInput" label now reads "Needs attention".
- **Confirmed dispatch.** The new `dispatchConfirmed` waits for the echo whose `origin` matches its `clientSeq` (`agentHostProtocolClient.ts:1518`). The host echoes every accepted action and sends each rejection as an `action` with the sender's `origin` and a `rejectionReason` (`host.ts:441-445`), so a refused action does not leave the client waiting.
- **Background work.** New `vscode/stopBackgroundWork` and `vscode/cancelAgentHostDebugLogs` requests (`agentHostExtensionProtocol.ts:51,62`). Unfold advertises no background work, so a 1.142 client has nothing to stop. Not verified whether VS Code sends either request to a non-native host.
- **Sign-in.** A `-32603` during initialize-time authentication now reconnects instead of closing. `expiresIn` handling is unchanged. The sign-in limits in [the spike](2026-10-10-ahp-sign-in-spike.md) still hold.
- **MCP delivery to agent hosts is still plaintext.** `syncedCustomizationBundler.ts` writes `server.configuration` verbatim into the forwarded `.mcp.json`. New in 1.142: Copilot-home servers are never forwarded, because they "may hold literal credentials", and the migrator rewrites `${env:NAME}` to `${NAME}`. On main only, OAuth servers are forwarded with `oauthClientId` (`23f0b8ef434`).
- **MCP itself** is still on `2025-11-25` (`platform/mcp/common/modelContextProtocol.ts:43`). VS Code does not speak `2026-07-28` or `server/discover`. The OAuth order is unchanged: a configured `oauth.clientId` first, then CIMD, then DCR (`mainThreadAuthentication.ts:182-201`). New: `offline_access` is requested when the server advertises it, and Entra hosts get no RFC 8707 `resource`.
- **Unchanged:** terminal streaming (`terminal/data`) and the review flow (`changeset/filesReviewChanged`).

### AHP after 1.0.0

No 1.1.0 release yet; the repository's `PROTOCOL_VERSION` is `'1.1.0'` and its CHANGELOG section is empty. On `5d542f9e`:

- `chat/configChanged` with `ChatState.config`, sent only for config properties a host marks `chatMutable`. VS Code main already sends it (`e941aa12741`).
- Experimental windowed delivery: `channel/frame`, `channel/credit`, `channel/snapshot`.
- A TCP channel: `createTcpConnection`, `tcp/data`, `tcp/eof`, `tcp/reset`.
- Steering and queued messages unified into `queuedMessages` with `PendingMessage.kind`; `steeringMessage` is mirrored while deprecated.
- `EmptyState` snapshots, which clients must tolerate.
- Open pull requests worth watching: per-channel replay cursors ([#494](https://github.com/microsoft/agent-host-protocol/pull/494)), session artifacts ([#508](https://github.com/microsoft/agent-host-protocol/pull/508), RFC #507), a canvas registry ([#528](https://github.com/microsoft/agent-host-protocol/pull/528)), and client windowed delivery ([#529](https://github.com/microsoft/agent-host-protocol/pull/529)).
- [#422](https://github.com/microsoft/agent-host-protocol/issues/422), a TypeScript server SDK, is still open. hydra-ahp was added to the implementation list ([#502](https://github.com/microsoft/agent-host-protocol/pull/502), merged by a maintainer on 2026-10-08).

## What this unlocks later

These are possible because of 1.142 or AHP after 1.0, but each needs a trigger or a decision first.

- **A Work Item canvas.** A canvas beside the chat that shows the Work Item, its Runs, Holds and spend, and the candidate's review state. Today a canvas runs only in a local Copilot-harness session, from a Copilot-app extension. A remote host could offer one once AHP's canvas registry ([#528](https://github.com/microsoft/agent-host-protocol/pull/528)) and the experimental `ahp-canvas:` channels let a host provide its own. T13.
- **Session artifacts.** RFC #507 / [#508](https://github.com/microsoft/agent-host-protocol/pull/508) would let the host publish the pull request, the Run card, test reports and the delivery evidence as first-class artifacts instead of chat text. T14.
- **Previewing a Run's running app.** The TCP channel lets a client open a connection through the host. Unfold could forward a Run's dev server to the reviewer's machine for a live check before accepting. This crosses Ploeg's worker network policy and the "AHP sandbox writes or shell input: never" line of the gap dossier, so it needs its own security review and an ADR. T15.
- **Live output at scale.** Windowed delivery (`channel/frame`, `channel/credit`) and per-channel replay cursors ([#494](https://github.com/microsoft/agent-host-protocol/pull/494)) are what RFC-0006 phase 4 ("push channel, only if measured") would otherwise invent. T16.
- **Per-chat settings.** `chat/configChanged` with `chatMutable` would let a person change a session's budget or approval mode from the chat's own config picker. The host must not mark anything `chatMutable` until a budget change through it passes the same authorization as the browser's.
- **A position nobody holds.** No product that turns tracker work into reviewed pull requests under a budget ships an AHP host or an Agents-window integration. The nearest ([Navarch](https://www.stork.ai/tools/navarch), [Merlin](https://usemerlin.ai)) have none. The loudest 1.142 complaint, the Copilot harness removing per-change Keep and Undo ([vscode#339363](https://github.com/microsoft/vscode/issues/339363), 148 reactions, 130 comments), asks for the control Unfold's review gate already gives.

## Recommendations

1. **Run the desktop pass now, on 1.142 against production (VIK-1922).** Attach with **Attach as Agent Host**, then:
   - create a session and send a turn;
   - answer a permission request and a question;
   - mark the session read, then done;
   - accept a candidate in the Changes view;
   - reconnect.

   Also open a Ploeg Work Item session. Check that the session grid shows "Needs attention" when a decision waits. Record that the connection negotiated `1.0.0`. This is the first desktop run of the 1.x catalog path, so expect defects there first.
2. **Build the browser link into the Agents window (VIK-1660).** The Work Item page and the extension's Now view get "Open in Agents window". It builds `vscode://agents/agent-host-session/…` with `connectionAuthority` set to the host's `chat.remoteAgentHosts` address. Verify a malformed or unknown authority falls back to the browser view. Test it in the desktop pass.
3. **Unblock VIK-1653 with the remote server, not a token.**
   - The extension registers `ploeg-mcp` as an HTTP server definition: the URL only, no headers and no token.
   - VS Code signs in through the pre-registered client `ploeg-mcp`.
   - Before building, verify that `McpHttpServerDefinition` from a provider uses the server's protected-resource metadata and accepts a pre-registered client id. If it does not, ship a documented `.mcp.json` / `mcp.json` snippet instead.
   - Agent-host delivery forwards OAuth servers with `oauthClientId` only from 1.143 (main `23f0b8ef434`), so test the Copilot harness on 1.143.
4. **Plan background work as RFC-0006's second rendering target.** When a 1.x client follows a Run, publish each running command as a `chat/backgroundWorkSet` shell entry and remove it on exit. Stop Shell must not kill paid work: answer `vscode/stopBackgroundWork` by asking whether to withdraw the Run, as Stop on a Work Item does now. Amend RFC-0006 before building. Its phase 2 (Ploeg worker offset chunks, Ploeg ADR-0090) is the prerequisite.
5. **Use the chat status for "needs you" (RFC-0005 3.3).** 1.142 labels a waiting session "Needs attention" from the status the host already sends per chat. Close 3.3 by checking, in the desktop pass, that each kind of decision a person owes sets the input-needed status on both the session and its chat.
6. **Keep `unfold-mcp` on the 2025 revisions for VS Code, and give it the `ploeg-mcp` treatment.** VS Code still speaks only `2025-11-25`, so the gap dossier's phase 1 item 1 (`2026-07-28` in `unfold-mcp`) matters for other clients, not VS Code. The higher-value step is the one `ploeg-mcp` just took: Streamable HTTP plus OAuth resource-server checks against Authentik, on the internal route. With ADR-0011's write toolsets, that lets a person act from chat.
7. **Record the enterprise-policy risk for the agency phase.** Managed `permissions` or `sandbox.enabled` moves chats to the Copilot harness and makes Claude and Codex unavailable. Not verified: whether remote agent hosts stay usable under that policy. Check it in the desktop pass if a managed-settings profile can be applied locally. Otherwise carry it as an open question for the first agency with managed VS Code.
8. **Finish the Open VSX claim (VIK-1924).** [EclipseFdn/open-vsx.org#14003](https://github.com/EclipseFdn/open-vsx.org/issues/14003) is closed, but `GET https://open-vsx.org/api/webgrip` still returned `verified: false` on 2026-10-16. Ask on the issue why.
9. **Tolerate AHP 1.1 before it ships.** Accept `queuedMessages` entries with `PendingMessage.kind` next to `steeringMessage`, and ignore unknown snapshot state. Never mark a config property `chatMutable` until recommendation 4's authorization rule exists for it. Add a replay test once VS Code main sends 1.1 shapes to a 1.0 host.
10. **Re-confirm Ploeg backlog item 101 at its 2026-10-31 review.** The second gate, "a production non-Microsoft host", is still not met. The largest third-party host, pi-ahp, has 25 stars, and hydra-ahp and ahpd have no releases.
11. **Adopt nothing else from 1.142.** Canvases, moving chats, the Copilot harness, Ask and the layout settings serve VS Code's own harnesses.

## Follow-up, 2026-10-16

Recommendation 3 was checked against the source at tag 1.142.0 (`d956e8a6ac5`) and main (`19fd99357ad`), then built for [VIK-1653](https://vikunja.webgrip.dev/tasks/1653). This closes the loop on the [1.141 dossier's recommendation 6](2026-10-08-vscode-1-141-fit.md#recommendations): the extension provides `ploeg-mcp` with no secret in its definition. **(source)** for every finding below.

- **A provider cannot name a pre-registered client.** `McpHttpServerDefinition` has `label`, `uri`, `headers` and `version` only (`src/vscode-dts/vscode.d.ts:20476-20506`). `McpServerDefinition.from` builds the HTTP launch from `uri`, `headers` and the proposed `authentication`, and never sets `oauth` (`extHostTypeConverters.ts:4192-4213`). `oauth.clientId` reaches the sign-in only from `mcp.json` (`mcpTypes.ts:763,821`; read at `extHostMcp.ts:771`). Main is the same. The proposed `McpHttpServerDefinition2.authentication` (`vscode.proposed.mcpToolDefinitions.d.ts:85-96`) names an authentication provider, not a client, and `mcpTypes.ts:764-768` calls it dead code. Proposed APIs are unusable on Open VSX anyway ([ADR 0021](../adrs/0021-the-extension-ships-through-open-vsx-first.md)).
- **Without a client id, VS Code asks the person for one.** It uses a stored registration first, then CIMD when the server metadata says it is supported (`mainThreadAuthentication.ts:182-195`). Authentik offers neither CIMD nor DCR, so `$registerDynamicAuthProvider` skips registration and calls `$promptForClientRegistration` (`extHostAuthentication.ts:284-310`). That shows a "Dynamic Client Registration not supported" dialog with **Copy URIs & Proceed**, then asks for a client ID and an optional secret (`mainThreadAuthentication.ts:651-700`). The redirect URIs it names are `http://127.0.0.1:33418` and `https://vscode.dev/redirect` (:652). The answer is stored as the registration for that authorization server and resource (:359), so it is asked once. Sign-in does not fail; it costs one typed `ploeg-mcp`.
- **VS Code's install link keeps `oauth`.** `<scheme>:mcp/install?<json>` opens the server's install view (`mcpWorkbenchService.ts:942`), and the payload sanitizer keeps `oauth` for a remote server (:128). An extension can open it with `env.openExternal`, and Install writes the user `mcp.json`.
- **Agent-host delivery drops the client id on 1.142 and on main.** A forwarded remote server is projected to `{type, transport, url, headers}` (`agentHostMcpServerSupport.ts:676-683`), and a server with `oauth` is marked `OAuthClientConfigurationIgnored` (:737-738). An extension's definition is forwarded like a `mcp.json` server. Main's `23f0b8ef434` writes `oauth.clientId` as `oauthClientId` in the customization *migrator* (`mcpServerCustomizationMigration.ts`), which moves servers into the Copilot configuration. It is not the agent-host bundle, so this dossier's "OAuth servers are forwarded with `oauthClientId`" overstated it. Re-check on 1.143.
- **Registration needs the manifest.** `registerMcpServerDefinitionProvider` throws unless the id is listed under `contributes.mcpServerDefinitionProviders` (`extHostMcp.ts:184-187`). Extension servers are trusted by default (:191).

Built (branch `feat/extension-mcp-servers`):
