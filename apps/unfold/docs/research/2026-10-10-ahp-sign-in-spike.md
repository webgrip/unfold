# AHP sign-in spike: can VS Code sign a person in to Unfold's host without a pasted token?

Research date: 2026-10-10. A spike of about four hours, run for [VIK-1940](https://vikunja.webgrip.dev/tasks/1940) and the "Connect VS Code" decision. It follows [the 1.141 dossier](2026-10-08-vscode-1-141-fit.md).

**Verdict: it does not work in VS Code 1.141, and nothing on main (1.142) changes that.** When a remote agent host declares a protected resource whose authorization server is not GitHub or Microsoft, VS Code looks only for an authentication provider that is already registered for that server. It never fetches the server's metadata for an agent-level resource, never registers a client and never opens a browser. If the person starts a session, the only prompt is "Sign in to use GitHub Copilot". The machinery that does all of that (RFC 8414 metadata, dynamic client registration, PKCE, a loopback redirect) exists in the same file, but VS Code calls it only for MCP servers. A live probe confirmed it: VS Code connected without a token and received the protected resource. The authorization server saw no requests, and no `authenticate` call arrived.

Sources:

- `microsoft/vscode` at tag 1.141.0 (`2a59476c`) and main at `95903124` (2026-10-10 05:36 UTC);
- the [AHP repository](https://github.com/microsoft/agent-host-protocol) at `cb6ba618` (2026-10-09), [authentication.md](https://github.com/microsoft/agent-host-protocol/blob/cb6ba6189ed861e7e5ae61fab92d6e68e8505182/docs/specification/authentication.md);
- a live probe against the VS Code 1.141.0 stable build installed on the owner's Mac, in an isolated profile;
- this repository at `1c330aa0`.

Evidence read in source is marked **(source)**, and evidence observed in the running build is marked **(probe)**.

## The flow as VS Code implements it

### Connecting

1. **The connection needs no credential.** **(source, probe)** "Add Remote Agent Host…" (`sessions.remoteAgentHost.add`, [remoteAgentHostActions.ts:67-71](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/sessions/contrib/providers/remoteAgentHost/browser/remoteAgentHostActions.ts#L67-L71)) takes `host`, `host:port`, or an `http(s)`/`ws(s)` URL. If the URL carries `tkn`, the command lifts it out as the connection token ([remoteAgentHostService.ts:867-901](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/platform/agentHost/common/remoteAgentHostService.ts#L867-L901)). The command takes no arguments, so an extension cannot pre-fill it. Its precondition, `chat.remoteAgentHostsEnabled`, defaults to `true`. Without a token, VS Code opens the WebSocket bare and sends `initialize`.
2. **The root state is the only discovery channel.** **(source)** On every root-state change, `_handleRootStateChange` calls `_authenticateWithConnection` ([remoteAgentHostChatContribution.ts:318-319](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts#L318-L319), [505-530](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts#L505-L530)). That function runs `authenticateProtectedResources` over each agent's `protectedResources` ([agentHostAuth.ts:563-576](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L563-L576)). It also re-runs when the default account changes, when a provider registers, or when sessions change ([remoteAgentHostChatContribution.ts:177-181](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts#L177-L181)).

### Resolving a token for a resource

3. **Only providers that are already registered count.** **(source)** For each entry in `authorization_servers`, `resolveAuthenticationSessionForResource` asks `getOrActivateProviderIdForServer(server, resource)` for a provider ([agentHostAuth.ts:375-466](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L375-L466)). That method matches registered providers by authorization server and, when the provider has one, by resource server. It then tries extension-declared providers whose `authorizationServerGlobs` match ([authenticationService.ts:343-365](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/services/authentication/browser/authenticationService.ts#L343-L365), [417-437](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/services/authentication/browser/authenticationService.ts#L417-L437)). A stock install declares only `github`, `github-enterprise`, `microsoft` and `microsoft-sovereign-cloud`. For any other server the method returns `undefined`. The code logs "No authentication provider resolved for server", returns `signedOut` and sends nothing. Nothing in this path fetches metadata or creates a provider.
4. **If the person was already signed in, the token goes to the host as is.** **(source)** When a provider does match, `forwardAuthenticationToken` sends `authenticate` on the root channel with `{ resource, scopes, token, expiresIn?, _meta? }` ([agentHostAuth.ts:519-551](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L519-L551)). `token` is the session's raw `accessToken`, and `expiresIn` is the remaining lifetime in whole seconds. `_meta` names the provider and account. `scopes` is the resource's `scopes_supported`, not the scopes actually granted. VS Code does no audience handling, so the token's audience is whatever the authorization server put in it. A per-connection `AgentHostAuthTokenCache` suppresses repeats ([agentHostAuth.ts:77-191](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L77-L191)). The cache belongs to the connection's state, so a new connection gets a new cache and the token is sent again.

### Challenges and prompts

5. **A host challenge never prompts a signed-out person.** **(source, probe)** An `auth/required` notification goes to `AgentHostAuthenticationRecovery.recover` ([remoteAgentHostChatContribution.ts:539-575](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/remoteAgentHost/remoteAgentHostChatContribution.ts#L539-L575)). When resolution is `signedOut`, `recover` logs the result and returns ([agentHostAuth.ts:269-283](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L269-L283)). It prompts only when a session exists and the host rejected its token. That prompt is the same GitHub dialog as in step 6.
6. **Starting a session prompts for GitHub, whatever the resource says.** **(source)** `_ensureRequiredAuthentication` runs before `createSession`, and the session handler retries once on `-32007` ([agentHostSessionHandler.ts:5875-5886](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts#L5875-L5886), [5949-5970](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSessionHandler.ts#L5949-L5970)). Both paths call `resolveAuthenticationInteractively`, and it ends in `forceAuthenticationInteractively`. That function runs the Copilot setup command with `dialogTitle: "Sign in to use GitHub Copilot"` and passes the resource's scopes as extra GitHub scopes ([agentHostAuth.ts:838-897](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L838-L897)). Afterwards it resolves the third-party resource again, still finds no provider, and returns `noSessionResolved`. Session creation then fails with "Authentication is required to start a session. Please sign in and try again." A host that declares a required non-GitHub resource therefore cannot start a session from VS Code at all.

### Where the general OAuth flow does exist

7. **MCP servers get the full flow.** **(source)** `resolveMcpServerAuthentication` and `getOrCreateProviderForMcpResource` handle a server that no provider covers ([agentHostAuth.ts:920-1067](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L920-L1067)). They fetch RFC 8414 or OIDC metadata in the renderer, which is why CORS matters (open issue [#340533](https://github.com/microsoft/vscode/issues/340533)). They then create a dynamic provider. That provider registers by RFC 7591 with `token_endpoint_auth_method: none`, `application_type: native` and redirect URIs `https://vscode.dev/redirect`, `https://insiders.vscode.dev/redirect` and `http://127.0.0.1/` ([oauth.ts:947-971](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/base/common/oauth.ts#L947-L971)). It uses a Client ID Metadata Document instead when the server advertises `client_id_metadata_document_supported` ([mainThreadAuthentication.ts:189-192](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/api/browser/mainThreadAuthentication.ts#L189-L192)). On desktop the first flow is a loopback server with PKCE S256 and the RFC 8707 `resource` parameter ([node/extHostAuthentication.ts:60-65, 92-128](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/api/node/extHostAuthentication.ts#L60-L128)). That flow is reached only from `authenticateMcpServer`, when the person presses Authenticate on a session's MCP server in the `AuthRequired` state ([agentHostCustomizationService.ts:341-366](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostCustomizationService.ts#L341-L366)). Without interaction it is reached from `autoAuthenticateMcpServer` ([agentHostAuth.ts:900-918](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L900-L918)). The agent-level path in steps 3 to 6 never calls it.

### Sign-in gates in the Agents window

8. **The Agents window's own gate is GitHub.** **(source)** `chat.agentHost.allowSignedOutWhenUsable` is `false` by default, experimental, and marked `experiment: { mode: 'startup' }` ([chat.shared.contribution.ts:1776-1783](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts#L1776-L1783)). When it is `false`, `resolveSignedOutWindowGate` returns `ForceGitHubSignIn` before any sessions UI shows ([sessionsAuthGate.ts:59-72](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/sessions/browser/sessionsAuthGate.ts#L59-L72)). A person without a GitHub account cannot use the Agents window for Unfold under any authentication design. When it is `true`, the window proceeds if any session type is not GitHub-gated. The setting does not change how a third-party resource is treated. It only lets a BYOK model skip the agent's auth check ([agentHostAuth.ts:53-66](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L53-L66)).
9. **The UI has no sign-in state for a third-party resource.** **(source)** `resolveAgentAuthRequirement` returns `GitHub` when `protectedResources` is absent or names the Copilot resource. Otherwise it returns `None` when the agent has models and `Unusable` when it has none ([baseAgentHostSessionsProvider.ts:752-757](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/sessions/contrib/providers/agentHost/browser/baseAgentHostSessionsProvider.ts#L752-L757), [agent.ts:431-434](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/platform/agentHost/common/agent.ts#L431-L434)). The "Sign in" affordance the target UX describes exists only for GitHub. Unfold's host today publishes no `protectedResources` field ([host.ts:314-322](../../src/ahp/host.ts#L314-L322)), so VS Code counts its agent as GitHub-gated.

### 1.142 and the spec

10. **On main (1.142) the logic is the same.** **(source)** Between the tag and main `95903124`, `agentHostAuth.ts` gains only a `preferredSessionId` option. The Copilot dialog title moves to line 870. `getOrCreateProviderForMcpResource` is still called only from the MCP path. `resolveAgentAuthRequirement` and the window gate are identical. `remoteAgentHostChatContribution.ts` changes only in how the MCP authenticate callback and the content provider are wired. No open `microsoft/vscode` issue asks for third-party authorization servers on agent-level resources. The closest are [#326116](https://github.com/microsoft/vscode/issues/326116) and [#340483](https://github.com/microsoft/vscode/issues/340483), both about MCP. The 1.142 breaks recorded in the 1.141 dossier are unrelated to authentication.
11. **The spec allows it, and VS Code just does not do it.** **(source)** AHP says that using RFC 9728 means "dynamic auth providers (for enterprise IdPs) work without hardcoded knowledge of specific providers" in "runtimes that support it" ([authentication.md:206-212](https://github.com/microsoft/agent-host-protocol/blob/cb6ba6189ed861e7e5ae61fab92d6e68e8505182/docs/specification/authentication.md#L206-L212)). It also says `-32007` must carry `data.resources`, that an empty `token` revokes, and that `auth/required` is not replayed after a reconnect ([authentication.md:88-203](https://github.com/microsoft/agent-host-protocol/blob/cb6ba6189ed861e7e5ae61fab92d6e68e8505182/docs/specification/authentication.md#L88-L203)). VS Code 1.141 is not such a runtime for agent-level resources.

## Probe

`probe.mjs` used Node 24 and `ws` 8.18.0, and stayed in the session scratchpad. It ran two servers on loopback:

- **AHP host on `127.0.0.1:47911`.** It accepted the WebSocket without a token and negotiated `0.9.x` the way [host.ts](../../src/ahp/host.ts) does. It published one agent, `unfold`, with one model and `protectedResources: [{ resource: "http://127.0.0.1:47911/", authorization_servers: ["http://127.0.0.1:47912"], scopes_supported: ["unfold:agent-host"], required: true }]`. Every call that needs authentication got `-32007` with `data.resources`. The host served `/.well-known/oauth-protected-resource`, sent `auth/required` eight seconds after `initialize`, and logged each `authenticate` by length and claims only.
- **Authorization server on `127.0.0.1:47912`.** It served RFC 8414 metadata, DCR `/register`, an auto-approving `/authorize` that checked PKCE S256, and a `/token` endpoint issuing an HS256 JWT with `aud` set to the resource.

A curl self-test ran the full DCR, authorize and token exchange against the probe, and the PKCE check passed. VS Code 1.141.0 then ran with `--agents --log trace` and a separate `--user-data-dir` and `--extensions-dir`. Its `settings.json` held `chat.remoteAgentHosts: [{ address: "127.0.0.1:47911", name: "Unfold probe" }]` with no token, plus `chat.agentHost.allowSignedOutWhenUsable: true`. The instance was not signed in to GitHub.

Two launch notes:

- The scratchpad path makes the IPC socket name longer than macOS allows ("listen EINVAL … longer than 103 chars"), so a short symlink pointed at the profile.
- A shell started from VS Code carries `ELECTRON_RUN_AS_NODE=1`, which turns `Code` into Node ("bad option: --agents"). Clearing it fixed the launch.

What happened, from the probe log and VS Code's `renderer.log`, 12:03:24 to 12:04:08 UTC:

| Time | Observed |

The instance and the probe were stopped at the end, and the symlinks were removed.

## What Unfold would have to implement

The target UX cannot be built in 1.141 or 1.142 from the host side alone. The list below says what to do now and what the host and HTTP server need once VS Code resolves non-GitHub authorization servers for agent-level resources. Sizes: S is hours, M is a day or two, L is several days.

### Now

1. **S. Publish `protectedResources: []` on the agent.** An absent field makes VS Code treat Unfold as GitHub-gated (step 9). An empty array makes it `None`, which states the truth: the connection token already authenticated the person.
2. **S. "Connect VS Code" hands over an address that already carries the credential.** The command mints a connection token, copies `wss://<host>/api/agent-host?tkn=<token>` to the clipboard, and opens the Agents window. The person runs "Add Remote Agent Host…" and pastes. The command strips `tkn` into the entry's `connectionToken` (step 1). That is one paste and no settings editing. The token travels through the clipboard, so mint it short-lived and single-purpose.
3. **S. Do not declare a required non-GitHub protected resource yet.** In 1.141 and on main it blocks session creation behind a GitHub dialog that cannot succeed (step 6). An optional one (`required: false`) does no harm, but it does nothing either.
4. **S. Draft the upstream issue for the owner to file.** Steps 3 and 7 point at a small change: let `resolveAuthenticationSessionForResource` and `forceAuthenticationInteractively` fall back to `getOrCreateProviderForMcpResource` when no provider matches. AHP's own design-decisions section supports it.

### When VS Code supports it

5. **M. Upgrade without a token.** Accept the WebSocket without `tkn`, and keep `tkn` for headless clients. Answer `initialize`, the root subscription, `ping` and `getNetworkDiagnosticsInfo` unauthenticated. The root state must then show no user data: today's `activeSessions` count is per user ([host.ts:314-322](../../src/ahp/host.ts#L314-L322)), so publish zero until the connection is authenticated.
6. **S. Return `-32007` with `data.resources`** for `listSessions`, session subscriptions, `createSession`, `resolveSessionConfig`, `resourceRead` and actions. Do this until `authenticate` succeeds on that connection. The probe shows VS Code backs off politely on this.
7. **M. Implement `authenticate`.** Today it is a no-op ([host.ts:884](../../src/ahp/host.ts#L884)). It must check that `resource` equals the advertised one exactly, or answer `-32602`. It must validate the token: signature, `iss`, `aud` equal to the resource, `exp`, and the scope. It binds the user to the connection, and an empty `token` unbinds it. A failed validation answers `-32007`. Authentication belongs to the connection. A reconnect is a new connection, so VS Code sends the token again from a fresh cache, and the `reconnect` path must accept a connection that authenticates after `reconnect`.
8. **M. Expiry and revocation.** Send `auth/required` with `reason: expired` shortly before `exp`, using the forwarded `expiresIn`. Send it again, or close the connection, when the person signs out of Unfold or an admin revokes the grant. VS Code's own sign-out sends `authenticate` with an empty token ([agentHostAuth.ts:616-669](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostAuth.ts#L616-L669)).
9. **L. Unfold as authorization server**, in front of the existing Authentik login, as decided. It needs these pieces:
    - `/.well-known/oauth-protected-resource` (RFC 9728) for the AHP resource and later ADR-0011's MCP resource;
    - `/.well-known/oauth-authorization-server` (RFC 8414) with `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]` and `registration_endpoint`, served with `Access-Control-Allow-Origin` because VS Code fetches it from the renderer;
    - either DCR (RFC 7591) that accepts `http://127.0.0.1/` on any port (RFC 8252) plus `https://vscode.dev/redirect`, or `client_id_metadata_document_supported: true`, which lets VS Code use its published client metadata URL and avoids open registration;
    - `/authorize` that requires the Authentik session, shows a consent screen naming the client, and binds `resource` (RFC 8707);
    - `/token` that issues short-lived JWT access tokens with `aud` set to the resource, plus rotating refresh tokens;
    - a grants page where the person can see and revoke connected VS Code clients.
10. **S. Keep the resource string stable and exact**, for example `https://unfold.webgrip.dev/`. VS Code matches providers to resources by case-insensitive string equality ([authenticationService.ts:417-437](https://github.com/microsoft/vscode/blob/1.141.0/src/vs/workbench/services/authentication/browser/authenticationService.ts#L417-L437)).

## What stays open

- **Whether an MCP-created provider bridges the gap.** A dynamic provider exists after the person authenticates an MCP server against the same authorization server and the same `resource` string, for example ADR-0011's server in `mcp.json`. Step 3's matcher would then find that provider for the agent resource, and VS Code would forward its token silently. That follows from source, but the probe did not test it: the consent dialogs need a click, and no computer-use tool was available. It would make sign-in depend on a second, unrelated configuration, so it is a workaround, not the UX.
- **Whether an MCP challenge inside a session counts.** A host could put an MCP server customization in the `AuthRequired` state inside a session, and the person's Authenticate click would run the full browser flow (step 7). That needs a session to exist first, and it presents a fake MCP server. Untested, and probably not worth building.
- **Whether VS Code will add the fallback.** Watch `agentHostAuth.ts` for a call to `getOrCreateProviderForMcpResource` outside `resolveMcpServerAuthentication`. Re-run this probe on every weekly release until it appears.
- **What a person without GitHub can do.** With the default `allowSignedOutWhenUsable: false`, the Agents window demands GitHub sign-in before anything else. The person cannot change that experiment-controlled default per host.

## Risks

- **The clipboard URL carries a credential.** Copying `?tkn=` is better than editing settings, but the token can land in clipboard history. A short lifetime and one token per device limit the damage. `connectionToken` is then stored in VS Code's settings, which is the status quo.
- **Building the authorization server early.** Items 5 to 9 are worth building for ADR-0011's MCP server anyway. For VS Code's Agents window they pay off only when upstream changes, and the date for that is unknown.
- **Copilot-first defaults.** The window gate, the "Sign in to use GitHub Copilot" dialog and the GitHub classification of agents without `protectedResources` all assume Copilot. Each weekly release can move these, so the probe should be re-run, not trusted, after an upgrade.
