# Unfold features by bounded context

Unfold's features grouped by the bounded contexts of the domain model in [`docs/domain/model.yaml`](../../../docs/domain/model.yaml), in its ubiquitous language, with each context's ports (the interfaces in code) and adapters (what binds them to the world). Snapshot: `webgrip/unfold` at `6738fb37` on `development`.

How to read it: terms in Capitalized Case are canonical model terms. "(Ploeg term)" marks the first use in a context of a term Unfold's model imports from Ploeg's model; "(Ploeg term, not imported)" marks a Ploeg term Unfold's code relies on but its model does not import. Code names that differ from the model term appear in backticks. Evidence links open the file that implements or decides the capability. A port is listed only when its type exists in code; where the code calls a vendor directly, the table says "implicit, no interface".

## Context map

| Context | What words mean here | Upstream / downstream relations (as the code shows them) |
| --- | --- | --- |
| System | A Workbench is one running deployment; Ploeg is the only Authority; the demo makes no model calls. | Upstream of every other context (configuration, mode). Pins a released Ploeg (system ADR-0039) and checks at runtime that the Ploeg it reaches serves the contract majors it needs (system ADR-0044). In demo mode it substitutes demo implementations for the Execution ports. |
| Work | What was asked for and whether it was delivered: Result, Evidence, Review, Acceptance, Acceptance Conditions, Ready. | Downstream of Execution: reads Ploeg's Work Item facts through the Ploeg client's Anti-Corruption Layer. Supplier to Participation (in-process, shared types) and to Billing (Acceptance, computed from Ploeg's delivery facts). |
| Participation | How a person takes part: Session, Linked Session, Attempt, Supervision, Stage, Needs-you Reason, Candidate, Unfold Chat, Access Role. | Customer of Execution and Work in-process. Open Host Service with its own Published Language for agent reporters (Linked Session hook events, Agent Trace records), for editors and AI apps (MCP tools with the Apps, Tasks and Events extensions, the AHP host, the ACP agent). Conformist to Ploeg's Ask and Chat contracts and to each notification provider (ntfy, Web Push, Slack, Microsoft Teams). |
| Execution | Ploeg's words: Run, Shift, Lease, Team, Role, Outcome, Verdict, Admission, Authority, Tracker Item, Follow-Up; plus Unfold's Workspace, Budget, Model Provider, Agent. | Conformist to Ploeg's Open Host Service (operator API `/api/v1/operator/*`) and its Published Language (the JSON schemas in the contract bundle under `apps/ploeg/docs/contracts`, checked by [`apps/unfold/test/ploeg-contract.test.ts`](../test/ploeg-contract.test.ts)). A thin Anti-Corruption Layer in [`apps/unfold/src/ploeg.ts`](../src/ploeg.ts) validates every field, accepts only listed enum values (`ploegAccepted`), maps Ploeg's `active` to Unfold's older `leased`, derives Unfold-only values (`rejected`, `stopped`) and maps to screen words ([`docs/domain/ploeg-words.json`](../../../docs/domain/ploeg-words.json)). Not Customer-Supplier: Ploeg knows no consumer; Unfold changes Ploeg upstream and pins a release. Toward trackers and forges, one adapter per vendor behind a registry acts as the Anti-Corruption Layer (`TaskProviderAdapter`, `LinkProviderAdapter`, `DeliveryPublisherAdapter`). |
| Cards | Run Card and its life in production: Play, Steward, Roster, Gate, Bounce, Crack, Mend, Finish, Grade, Rarity, Binder, Pack, Skin. | Downstream of Ploeg's delivery facts through its own ACL ([`apps/unfold/src/cards/facts.ts`](../src/cards/facts.ts) parsers), now reached through the first slice of `PloegPort`. Separate Ways from Execution and Billing in the other direction: card state never changes what Ploeg authorizes, budgets or merges. |
| Offering | Agency, Client, Client Portal, Request, Intake Source, Client Sign-off, Ticket, Edition. | Partly built behind flags and configuration: Tenant (Ploeg term) and Client (Ploeg term) ownership of repositories and task sources, memberships from single sign-on and SCIM, enforcement behind `tenancy.enforce`. Intake is an Open Host Service (signed webhook receiver) with an Anti-Corruption Layer of mapping templates per sender. Client Sign-off is downstream of Ploeg's delivery facts (head commit) and writes only through Ploeg's keyed pull request comment. Customer of Work (Acceptance). |
| Billing | Size, Quote, Credit, Delivery Fee, Token Charge, Markup, Delivery, Dispute, Reversal. | Partly built: a Delivery read model downstream of Work's Acceptance and Ploeg's settled spend, and billing lines sent to the Agency's own tool. Conformist to Simplicate's API; Published Language toward any other tool (CSV, UBL 2.1 JSON) and toward FinOps tools (FOCUS 1.4). Sizes, Quotes, Credits, Delivery Fees and Markup are not built. |
| Release | Qualification and Cutover of Unfold's own source and releases. | Generic subdomain. Conformist to the Ploeg release pin (the Helm chart carries the Ploeg chart it was tested with) and to Ploeg's consumer-expectation format ([`apps/unfold/src/ploeg-expectations.json`](../src/ploeg-expectations.json)). |
| Tooling | External tools and protocols: AHP, OpenSpec, TechDocs, Zensical (and, in code, MCP, ACP, OFREP, Agent Trace, in-toto, OCSF, CloudEvents, Standard Webhooks, SCIM, FOCUS). | Conformist to each external Published Language. |

## Status legend

- `shipped`: implemented and on by default. "ADR proposed" beside it means the code ran ahead of the decision record.
- `behind flag <name>`: gated by [`apps/unfold/src/flag-registry.json`](../src/flag-registry.json); every flag defaults to off.
- `needs config <key>`: built, and off until the deployment configures that key.
- `demo-only`: exists only in the deterministic demo or the replay.
- `partial`: some code exists; the rest is proposed.
- `proposed`: only in docs or ADRs; no code.
- `tooling`: opt-in scripts and developer tools, not part of a running Workbench.

## Context: System

Owns what a Workbench is and in which mode it runs. Terms that only mean what they mean here: **Unfold** (the product and monorepo), **Workbench** (one running deployment with its configuration, credentials and storage), **Ploeg** (the only Authority), and the deterministic demo (a Workbench without Ploeg that makes no model calls). A Workbench's readiness to start new work belongs here; the work itself does not.

### Domain capabilities

- **Workbench mode: demo or live**: `UNFOLD_MODE` / `mode` picks a deterministic, credential-free demo or an authenticated live Workbench; a live boot is refused without Ploeg execution (`ploeg.url`, `ploeg.tokenEnv`, `execution.team`), without a repository, or without a bootstrap admin; demo mode refuses real credentials, because every demo visitor is an administrator. Shipped. Evidence: [`apps/unfold/src/config.ts`](../src/config.ts) (`requirePloegExecution`), [`apps/unfold/src/main.ts`](../src/main.ts).
- **Deterministic demo**: illustrative Ploeg records with no model calls or spend, labelled "Demo · no model calls" everywhere, destructive actions disabled; a demo Ploeg serves card KPIs and working-hours maths and refuses real notes, context files and delivery facts; one-click demonstration Session. Demo-only. Evidence: [`apps/unfold/public/shell.js`](../public/shell.js), [`apps/unfold/src/ploeg-demo.ts`](../src/ploeg-demo.ts), [`apps/unfold/src/ploeg-demo-port.ts`](../src/ploeg-demo-port.ts), [`apps/unfold/src/ploeg-demo-kpis.ts`](../src/ploeg-demo-kpis.ts), [`apps/unfold/public/views/sessions.js`](../public/views/sessions.js).
- **Demo or live marking**: a badge says whether Runs spend real Budget or the Workbench is the demo. Shipped. Evidence: [`apps/unfold/public/shell.js`](../public/shell.js).
- **Hosted replay**: the static `/demo` page answers the real app's API from a recording, so visitors click through without a server. Demo-only. Evidence: [`apps/unfold/public/replay/replay.js`](../public/replay/replay.js), [`apps/unfold/public/replay/routes.js`](../public/replay/routes.js).
- **Unified local demo**: runs Unfold with an ephemeral signing key next to a local Ploeg. Demo-only. Evidence: [`apps/unfold/scripts/unified-demo.ts`](../scripts/unified-demo.ts).
- **Ploeg reachability**: tells a person whether Ploeg is in demo, connected, partly unavailable, unreachable, not configured or has no Teams for their account, and when the page last updated. Shipped. Evidence: [`apps/unfold/public/shell.js`](../public/shell.js).
- **Ploeg contract compatibility**: Unfold reads the contract majors Ploeg serves at `GET /api/v1/operator/version` at start and every minute; while Ploeg lacks a required major, every call to Ploeg is refused before it is sent with `ploeg_contract_incompatible`, every page shows a banner that managed actions are paused, and `/healthz` and `/api/status` carry the state while `/readyz` stays up. Unfold's expectations of each operator request are recorded in Ploeg's consumer format. Shipped (system ADR-0044 proposed). Evidence: [`apps/unfold/src/ploeg-compatibility.ts`](../src/ploeg-compatibility.ts), [`apps/unfold/src/ploeg-expectations.json`](../src/ploeg-expectations.json), [`apps/unfold/public/shell.js`](../public/shell.js), [`docs/adr/adr-0044-unfold-refuses-a-ploeg-that-does-not-serve-the-contract-majors-it-requires.md`](../../../docs/adr/adr-0044-unfold-refuses-a-ploeg-that-does-not-serve-the-contract-majors-it-requires.md).
- **Workbench readiness: can new work start?**: answers Yes, Probably, Yes but not reliably, Not right now or This is a demo, with the start line (Ploeg authorizes, gateway Budget, Workspace, Team works) and check times, Sessions waiting for a Workspace (own by name, others as a count), failures of the last 24 h by cause, the card-import line, a return path to the failed Session, a red or amber dot on the Status navigation item, a probe of the model gateway's liveness route, and whether the person's changes reach Ploeg with a proven person token. Administrators can open the raw scheduler message. Shipped. Evidence: [`apps/unfold/public/views/status.js`](../public/views/status.js), [`apps/unfold/public/core/status-signal.js`](../public/core/status-signal.js), [`apps/unfold/src/status.ts`](../src/status.ts) (`gatewayProbe`).
- **Administrator notes on Status**: an administrator posts a note for everyone and marks it resolved; recently resolved notes show folded. Shipped. Evidence: [`apps/unfold/public/views/status.js`](../public/views/status.js), [`apps/unfold/src/status.ts`](../src/status.ts).
- **Workbench environment**: six health checks (Ploeg, model gateway, Workspace placements, agent runtimes, task connections, dashboards), Workbench facts and repositories, with the setting that fixes each for administrators; the bootstrap and health APIs hand the browser the person and their memberships, mode, repositories, Teams, models, runtimes, Placements, task sources, tracker display facts, Budget limits, gateway, observability links and client flag values. Shipped. Evidence: [`apps/unfold/public/views/system.js`](../public/views/system.js), [`apps/unfold/src/http.ts`](../src/http.ts) (`/api/bootstrap`, `/api/health`), [`apps/unfold/src/tracker-display.ts`](../src/tracker-display.ts).

## Context: Work

Owns what was asked for and how its answer is judged. Terms that only mean what they mean here: **Result**, **Evidence**, **Review** (a person's review of the pull request, one per Work Item), **Acceptance** (the Agency's decision that a pull request delivers its Work Item), **Acceptance Conditions**, **Ready**, **Preview Environment**, **Work Item Link** (proposed). A Work Item (Ploeg term) states the intended Result; a finished Run or closed Shift (Ploeg terms) does not by itself prove the Result is accepted.

### Domain capabilities

- **Results ready for Review**: lists pull requests ready for a person with CI state, a merge-conflict chip and the reviewing Run's Verdict (Ploeg term); a pull request whose CI failed goes under Needs you instead of Review; the review room says how many more reviews the person can take. Shipped. Evidence: [`apps/unfold/public/now.js`](../public/now.js).
- **Evidence before merge**: for ready work, the merge state, the reviewer's Verdict, CI, settled spend and what each forge action does. Shipped. Evidence: [`apps/unfold/public/ploeg.js`](../public/ploeg.js).
- **The writing Run's account of the Result**: what was wrong and what the pull request changes, with the Role (Ploeg term) and Round (Ploeg term, not imported) that wrote it. Shipped. Evidence: [`apps/unfold/public/ploeg.js`](../public/ploeg.js).
- **Reviewer findings and disagreement**: every reviewer finding with the writer's answer, unanswered first, Shadow Role (Ploeg term, not imported) findings folded away; per Round, where a Shadow Role's Verdict differs from the acting reviewers'. Shipped. Evidence: [`apps/unfold/public/blackboard-view.js`](../public/blackboard-view.js).
- **Acceptance Conditions ledger**: the brief's Acceptance Conditions, stating that Ploeg does not report proof yet. Behind flag `work.unified`. Evidence: [`apps/unfold/public/live/work-parts.js`](../public/live/work-parts.js).
- **Work Item brief**: the Work Item's description rendered as Markdown and folded when long; a tracker's HTML becomes inert Markdown with only http(s) and mailto links kept, and each tracker adapter may tidy its own description format. Shipped. Evidence: [`apps/unfold/public/ploeg.js`](../public/ploeg.js), [`apps/unfold/src/markdown.ts`](../src/markdown.ts), [`apps/unfold/src/rich-text.ts`](../src/rich-text.ts), [`apps/unfold/src/task-providers/index.ts`](../src/task-providers/index.ts) (`displayDescription`).
- **Ready check before the first Run** (`checkBrief`, "brief check"): a cheap gateway model checks whether the objective can be acted on and can ask clarifying questions; `runtime.briefCheck: false` turns it off. Shipped. Evidence: [`apps/unfold/src/engine.ts`](../src/engine.ts) (`checkBrief`).
- **Context files as Evidence for Runs**: a person attaches a file or archive with a note, which every Role reads as Evidence from its next Run; reads and adds go through `PloegPort`. Shipped. Evidence: [`apps/unfold/public/views/work.js`](../public/views/work.js), [`apps/unfold/src/ploeg.ts`](../src/ploeg.ts) (`listContext`, `addContext`), [`apps/unfold/src/ploeg-port.ts`](../src/ploeg-port.ts) (`PloegContextFiles`), [`apps/unfold/docs/adrs/0039-unfold-collects-context-files-and-hands-them-to-ploeg.md`](adrs/0039-unfold-collects-context-files-and-hands-them-to-ploeg.md).
- **Created work awaiting a person** (proposed Work Items, Follow-Ups (Ploeg term)): lists Work Items agents proposed, with kind, Ready or Needs refinement, Team, brief, origin, proposer, repository and whose Budget it uses; a Now group links there; a person with the right Access Role approves and queues it after a confirmation, or rejects it with a kept reason, from the browser or MCP. Shipped. Evidence: [`apps/unfold/public/ploeg-activity.js`](../public/ploeg-activity.js), [`apps/unfold/public/now.js`](../public/now.js), [`apps/unfold/src/ploeg.ts`](../src/ploeg.ts) (`proposed`, `decide`), [`apps/unfold/src/mcp.ts`](../src/mcp.ts).
- **Budget at stake on a proposal**: a Team Budget shown on proposals. Proposed (Ploeg has no Team Budget). Evidence: [`apps/unfold/docs/browser-ui.md`](browser-ui.md).
- **Release track of a Result**: pull request opened, CI on head, approval, merge and first deploy per environment, each with its time. Shipped. Evidence: [`apps/unfold/public/core/delivery-track.js`](../public/core/delivery-track.js).
- **Acceptance per Work Item**: each attempted Work Item in a window gets its Acceptance kind (merged, approved, silent after 10 working days, closed without Acceptance, or open) and its Acceptance date, from Ploeg's delivery facts; working days skip weekends and `acceptanceCalendar.nonWorkingDates`; the last writing Run stands in for ready-for-review. Shipped (the holiday calendar is an open owner decision). ## Context: Participation

Owns how a person takes part in AI work through Unfold and inspects what happened. Terms that only mean what they mean here: **Session** (the internal record of a Work Item started in Unfold), **Linked Session** (a person's own agent session that reports to Unfold), **Attempt** (the screen word for a Shift), **Supervision**, **Stage**, **Needs-you Reason**, **Candidate**, **Placement**, **Unfold Chat**, **Work Item Brief**, **Access Role**. It also owns the driving adapters through which people reach Unfold: browser, MCP, the AHP host, the ACP agent, the editor and harness extensions, and the notification channels.

## Context: Execution

The product view of AI work. Ploeg's model owns this vocabulary, and Unfold conforms to it: a Run (Ploeg term) is one Role (Ploeg term) executing against a Work Item (Ploeg term); a Shift (Ploeg term) is one Team's (Ploeg term) whole engagement, shown on screen as an Attempt; a Lease (Ploeg term) is the right to write the branch; an Outcome (Ploeg term) ends a Run; Admission (Ploeg term) and Authority (Ploeg term) belong to Ploeg alone. Unfold's own terms here are **Workspace**, **Budget**, **Agent**, **Model Provider**. Two concurrent paths share it: work Ploeg runs on its workers (read and commanded through the operator API) and Sessions Unfold runs in its own Workspaces under an Operator Execution (Ploeg term, not imported) that Ploeg admits, heartbeats and pays for.

## Context: Cards

Owns the Run Card: the record of one Work Item's change and its life in production, assembled on read from Ploeg's delivery facts plus Unfold's card store. Terms that only mean what they mean here: **Run Card**, **Play**, **Steward**, **Roster**, **Gate**, **Bounce**, **Crack**, **Mend**, **Finish**, **Grade**, **Rarity**, **Set Card**, **Binder**, **Pack**, **Skin**. A card describes a change, never a person; its state never changes what Ploeg authorizes, budgets or merges.

### Domain capabilities

- **Run Card**: assembled from Ploeg's delivery facts with the Crack workflow, frozen Rarities and computed card rules kept in Unfold's card store, scoped by Tenant and Client; the card page shows cost ring, tokens, run time, diff, pull request and CI, Roles, Steward, day and Finish, Gates strip, KPI strip and 12 detail tabs; figures Ploeg cannot supply yet read "Not collected yet". Shipped (needs a real Ploeg; several ADRs proposed). - **Card import**: a backfill and sweep import facts pages from Ploeg 30 s after boot and every 5 minutes, with the import line on Status. Shipped. ### Process and HTTP (infrastructure)

### Collisions the model does not resolve (proposed resolutions; the model is not edited)

1. **Session.** The model says people never meet a Session and screens say "session" only for a Linked Session (R21), yet the code exposes Sessions as first-class things: the Sessions page, "New session", `/api/sessions`, `unfold_sessions`, `unfold_steer_session`, AHP and ACP sessions. Proposed: either record that "Unfold session" is a screen word for a Session until the unified page ships, or rename the UI and MCP surfaces to "Work Item started in Unfold" and keep "session" for Linked Sessions and the protocols' own word.
2. **Candidate versus Delivery Candidate.** Unfold's Candidate (captured in the Workspace) and Ploeg's Delivery Candidate (rebuilt outside it, bound to a generation) both show as "candidate"; Cards adds "crack candidates". Proposed: import Delivery Candidate, Verification Receipt and Publication Operation into Execution, say "Delivery Candidate" on the delivery gate, and call crack candidates "suspected causes".
3. **Review and Verdict on a Candidate.** Rule R22 says a Work Item has one Review and Unfold records no verdict on a Candidate, but `POST /api/sessions/:id/review`, "Record your review" and AHP Accept / Reject / Request changes record one. Proposed: name the Session decision "Candidate decision" (approve for publication) and keep Review for the pull request; reserve "verdict" for Ploeg's Verdict and say "judgement" for the Run health judge, "hit feedback" for the tripwire, "readiness" for Status and "signature check" for intake.
4. **Team and Run inside Unfold's own engine.** `Team` / `TeamRole` and `Run` / `RunStatus` in [`apps/unfold/src/types.ts`](../src/types.ts) describe Unfold's Session engine, not Ploeg's Team manifest and Run. Proposed: rename in code to Step (already a model term) and to a "Session plan" or similar for the configured Roles, until the engine is retired.
5. **Note.** "Note for the next Run" reaches exactly one later Run; Ploeg's Work Item Note is unreviewed knowledge read by every later Run under the same root; Status has administrator notes, Linked Sessions a hand-over note, and hand-back a note too. Proposed: call the one-shot message a "briefing note" (or Ploeg's own word for it) and import Work Item Note separately.
6. **Delivery and Gate.** Billing's Delivery (an accepted Work Item), the Deliver Stage, Ploeg's "delivery facts", the Session "delivery gate", delivery publishers and outbox "deliveries" share one word; Cards' Gate (board workflow point) collides with "delivery gate". Proposed: call the Session step "publication" (Ploeg: Publication Operation), say "send attempt" for the outbox, and keep Delivery for Billing and Gate for Cards.
7. **Linked Session "never steers".** The model says Unfold never starts, steers or pays for a Linked Session, yet the inbox, remote tool approval, the conversation relay and Start in my Claude / client-carried Runs do some of each. Proposed: amend the definition to "never executes or pays for it; may relay messages, approvals and its conversation for the person".
8. **Ask.** The UI's "Ask a question" covers record answers that are not an Ask (no Run, no Allowance). Proposed: name the free path "record answer" and keep Ask for the metered, admitted Run.
9. **Hand-off.** One word covers assigning a Tracker Item to a Team, handing a Linked Session's Work Item or its uncommitted change to Ploeg, and following "Handed off by you"; hand-back returns a taken-over Run. Proposed: add Hand-off to the model as "giving work to a Team for Ploeg to run, from any channel" and Hand-back as its own term beside Take-over.
10. **Connection.** Settings → Connections (routing wiring), Connect a tracker and Test connection (a task source), the proposed Integration Account and Unfold ADR 0063's per-origin Connection all say "connection". Proposed: keep "Connections" for the routing wiring page, say "task source" on Connect a tracker, and settle Integration Account versus Connection when ADR-0048 and ADR 0063 are decided.
11. **Event.** Ploeg's audit events, product (insight) events, outbound CloudEvents, MCP Events, Security Event Tokens and OCSF records all say "event". Proposed: "Ploeg event" for the Activity feed, "product event" for insight, "outbound event" for webhooks and MCP Events, and "audit record" for OCSF.
12. **Client.** The Offering's Client and the apps that connect over MCP, ACP and AHP are both "clients". Proposed: say "app" or "editor" on screens for the latter, as the "Handed off by you" card already does.
