# HTTP contract

This guide describes routes implemented by [HTTP handlers](../../src/http.ts) and lifecycle rules in [the session engine](../../src/engine.ts). Executable tests and source resolve implementation drift. Routes return JSON objects or arrays directly. Errors have the form `{"error":{"code":"...","message":"..."}}`.

## Identity and mutation requests

Live API access requires a login cookie, or an editor credential as a bearer token (see [Single sign-on](#single-sign-on)). Every `POST`, `PUT`, `PATCH` or `DELETE`, including login, requires `X-Unfold-Request: 1` and passes same-origin checks: a present `Origin` must match the configured base URL, and `Sec-Fetch-Site: cross-site` is refused with 403 `csrf` or `origin`. The one exception is the editor sign-in under `/api/auth/editor`, which an editor extension calls without a browser; it is exempt from the header and origin checks and is protected by its one-time code and secret instead (see [Single sign-on](#single-sign-on)). JSON request bodies require `Content-Type: application/json`, so an action that takes no input still sends `{}`. Cross-origin access is not enabled. Login cookies are HttpOnly and SameSite Strict; an HTTPS base URL enables secure cookies. Configure the public base URL accurately behind a reverse proxy.

Every authenticated `POST`, `PUT`, `PATCH` or `DELETE` under `/api/`, except sign-in, telemetry and flag evaluation, leaves one Action Record (system ADR-0037): the person and role, the channel, the route with identifiers replaced by `:id`, its target (Work Item, session or task), its inputs with secrets redacted and text clipped, the confirmation, the HTTP status and the outcome (`done` for 2xx, `refused` for 4xx, `failed` otherwise). The channel is `browser` for a session cookie and the editor credential's name for a bearer token, followed by the client an editor names in `X-Unfold-Client` (printable, at most 80 characters). An MCP client sends the person's confirmation as `X-Unfold-Confirmation: <id>:<sha256 of the agreed text>`; a malformed value is not recorded. Unfold passes the channel and confirmation to Ploeg as `X-Ploeg-Via` and `X-Ploeg-Confirmation` on every operator call it makes while serving that request (Ploeg ADR-0108).

Operators can read and change sessions they own. Administrators can access all sessions and authorize budget additions. Viewers cannot mutate work. Inaccessible session IDs return 404. The current API does not expose shared team membership or invitation management.

### Single sign-on

When `auth.oidc` is configured, `GET /api/auth/methods` (public) reports the provider's display name and issuer, `GET /api/auth/oidc` redirects to the provider with an authorization-code request carrying PKCE, `state` and `nonce`, and `GET /api/auth/oidc/callback` completes it: the workbench exchanges the code server-side, fetches the provider's signing keys, verifies the identity token's signature, issuer, audience, expiry and nonce, and derives the role. The role is the `roleClaim` value when the provider sends one, otherwise the first of admin, operator and viewer whose configured groups intersect the `groupsClaim` list; a person in none of them is refused with `oidc_not_entitled` and no session. The user record is keyed by issuer and subject, named by email, and its role is refreshed on every sign-in. The local password login remains for the bootstrap administrator.

An editor signs in through the same browser flow, and its person approves it ([ADR-0037](../adrs/0037-an-editor-signs-in-only-after-its-person-approves-it-and-gets-its-own-credential.md)). `POST /api/auth/editor` (public, exempt from the mutation header and origin checks, and only routed when OIDC is configured) takes an optional JSON body `{client, host}` and returns a one-time `code`, a `secret` only the editor holds, a short `userCode` such as `BCDF-GHJK` that the editor displays, the `url` to open (the sign-in with `?editor=<code>`), `expiresIn` (600) and the polling `interval` in seconds (2). It allows 20 starts per client address per ten minutes and 1000 waiting tickets, then answers 429 `rate_limited`. The workbench refuses an unknown, expired or already claimed code before redirecting. The callback records who signed in and sends the browser to `#editor-sign-in/<code>`; signing in does not complete the ticket. The ticket and its credential are named by Unfold, never by the client's own text: `VS Code` by default; `VS Code on <host>` for `client: "vscode"` and `unfold-mcp on <host>` for `client: "mcp"` with a host of up to 63 letters, digits, dots and hyphens; and `VS Code` or `unfold-mcp` for any other host. The VS Code extension sends `{client:"vscode", host}` with the short host name of the machine it runs on; an older extension sends no body and its sign-in reads `VS Code`.

| Method and path | Behavior |
| --- | --- |
| `GET /api/editor-requests/<code>` | For the person who signed in for the ticket: `{userCode, label, status: waiting\|approved\|denied, createdAt, expiresAt, workbench, user, role, credentialDays}`; 404 for anyone else or an expired ticket |
| `POST /api/editor-requests/<code>/approve`, `.../deny` | Same person, browser session and mutation checks; one decision per ticket, then 409 `editor_login_decided` |
| `POST /api/auth/editor/<code>` | `{secret}` from the editor: 202 `{status:"pending"}` until approval; 200 once `{status:"ready", token, expiresAt, user}` after approval; 403 `editor_login_denied` once after a denial; 404 for unknown, expired, consumed or wrong-secret polls (five wrong secrets end the ticket); 429 `slow_down` for a poll within one second of the last |
| `GET /api/editor-credentials` | The person's live editor credentials, neither expired nor idle: `{editors:[{id,label,scope,createdAt,expiresAt,lastUsedAt?,idleExpiresAt}]}`, where `idleExpiresAt` is when it signs out if it stays unused (its last use, or its approval when never used, plus fourteen days) |
| `DELETE /api/editor-credentials/<id>` | Revokes one, with the Agent Host connection tokens it issued; returns the remaining list |

The `token` is an editor credential, `vle_` followed by 43 base64url characters, sent as `Authorization: Bearer <token>`. Unfold stores only its SHA-256 hash. It lasts thirty days from approval and is not renewed by use. It also ends after fourteen days without use, counted from its last use or, when never used, from its approval: an idle credential no longer authenticates, drops off the list and ends the Agent Host connection tokens it issued, exactly like an expired one. A request with the credential, or an Agent Host connection token it issued, records a use at most once a minute. It acts as its person with their current role, except that the `editor-requests` and `editor-credentials` routes answer 403 `browser_only` to it. `POST /api/logout` with the bearer token revokes that credential only. A request with a malformed or unknown bearer token is unauthenticated, whatever cookie it also carries.

## Status

Every signed-in person can read `GET /api/status`; only administrators post and resolve notes. Mutations follow the [identity rules](#identity-and-mutation-requests).

| Method and path | Request or response |
| --- | --- |
| `GET /api/status` | `{generatedAt, overall, checks, waiting, failures, notes}`. `overall` is `operational`, `degraded` or `down`: the worst check or open note. `checks` holds `workspaces`, `gateway` and `ploeg`, each `{id, title, state, summary, detail?}` with `state` one of `ok`, `degraded`, `down`, `idle` (no workspace started in 24 hours) or `not_used`; `detail` is for administrators only. `waiting` lists sessions preparing a workspace, `{sessionId?, title?, own, phase, since, reason?}`, where `phase` is `preparing`, `scheduling`, `capacity`, `creating` (placed; storage and image), `image_unavailable`, `container_error`, `cloning`, `starting` or `connecting`; another person's session carries no id or title unless the reader is an administrator, and only an administrator sees `reason`. `failures` is `{since, total, causes:[{category, message, count, lastAt, sessions:[{id,title}]}]}` for the last 24 hours without `cancelled` and `review_incomplete`. A workbench cause (`capacity`, `timeout`, `connectivity`, `missing_executable`, `gateway_rejected`, `workspace_setup`) counts every session; any other cause counts only the reader's own sessions, or every session for an administrator. `sessions` lists only sessions the reader may open. `notes` holds open notes and those resolved in the last seven days |
| `POST /api/status/notes` | Administrator: `{severity: info\|degraded\|outage, text}` with 1–500 characters → 201 note `{id, severity, text, author, createdAt}` |
| `POST /api/status/notes/:id/resolve` | Administrator: `{}` → the note with `resolvedAt` and `resolvedBy`; 404 for an unknown id |

The `workspaces` check reads the workspaces Unfold is preparing and the last `workspace.ready` event. While a workspace starts, the session records one `workspace.waiting` event `{phase, message}` each time the phase changes, starting with `preparing`; `message` never carries the scheduler or container reason. A Kubernetes workspace whose Pod the scheduler cannot place reports `capacity` while it waits; when its time limit runs out it fails as `capacity` (or `missing_executable` for an image that cannot be pulled, `workspace_setup` for a container that cannot be created) instead of `timeout`. A plain `timeout` carries a `detail` beginning `workspace_start_timeout fired after <elapsed> ms against a limit of <limit> ms`, followed by the time spent in each phase. A `capacity` failure keeps the check `degraded` for 30 minutes unless a workspace starts after it. The gateway check calls LiteLLM's unauthenticated `/health/liveliness` with a three-second limit and keeps the answer for 15 seconds.

## Sessions

| Method and path | Behavior |
| --- | --- |
| `GET /api/sessions` | Sessions visible to the current user |
| `POST /api/sessions` | `{title,objective,repositoryId,teamId,runtime,placement?,approval?,model?,budgetUsd,trackerUrl?}` → created session, status 201. The deprecated `crewId` is still accepted in place of `teamId` ([Team keys](#team-keys)). `model` pins one configured model id for every role of the session, overriding the Team's role models, which is how the same objective is run pinned and auto-routed for comparison; `approval` is `manual` (default) or `auto`; `auto` needs a `docker` or `kubernetes` placement and answers every tool permission inside the sandbox itself, while questions still reach the operator |
| `GET /api/sessions/:id` | Public session view, runs, retained artifacts and accounting status |
| `POST /api/sessions/:id/retry` | Standalone only: after unresolved spend is reconciled, releases the workspace, resets the Team's Roles and current artifacts, records `session.retried`, and launches. Durable history and spent budget remain. Returns 409 `spend_unresolved` for open accounting or `new_authorization_required` for shared Ploeg execution; shared work requires an explicit new session |
| `POST /api/sessions/:id/start` | `{}`; start queued work in the background |
| `POST /api/sessions/:id/pause` | `{}`; deliberately stop active execution while retaining the session |
| `POST /api/sessions/:id/resume` | `{}`; explicitly continue paused/interrupted work subject to spend reconciliation |
| `POST /api/sessions/:id/cancel` | `{}`; intentional cancellation, with no automatic replacement run |
| `POST /api/sessions/:id/messages` | `{text}`; persist an operator instruction for the next execution. A Ploeg-executed session that is stopped and cannot run again answers 409 `session_stranded`, whose message says why and names the way out (deliver, run again or cancel); nothing is recorded and no Ploeg command is sent |
| `GET /api/sessions/:id/recovery` | The next steps for a stopped session; see [Recovering a stopped session](#recovering-a-stopped-session). Reads Ploeg and sends it no command |
| `POST /api/sessions/:id/capture` | `{}`; capture the change of a stopped Ploeg-executed session for review before delivery. Returns the session with its candidate |
| `POST /api/sessions/:id/deliver` | `{}`; deliver a stopped Ploeg-executed session whose last reviewer approved. Returns the completed session |
| `POST /api/sessions/:id/run-again` | `{}`; create a new queued session with the same brief, repository, Team, placement, approval, model and budget, and `previousSessionId` set. Status 201; it never starts. A session imported from a tracker answers 409 `tracked_task` |
| `POST /api/sessions/:id/budget` | Standalone only: `{amountUsd}`; administrator authorizes an additional positive amount within the total limit. A gateway key keeps the budget it was minted with and is never extended in place, so the increase is refused with 409 `pause_required` while the session executes or holds unreconciled keys; it applies to the key minted on the next resume. A finished session answers 409 `invalid_state`, and an increase beyond `maxBudgetUsd` answers 400. Shared budget extension is not implemented: a Ploeg-authorized session answers 409 `authority_budget` |

Selection values must come from the registered profiles. `placement` is one of the workspace backends listed in `placements` (`docker`, `kubernetes` or `local`); omitted, it takes the deployment default, and a demonstration deployment lists none. The created session records `placement`, and the `workspace.ready` event reports the resulting `backend` and `isolation` (`container`, `pod` or `working-directory`). Budgets are positive amounts in USD; they are not token allocations. One optional writer may precede reviewers, and roles execute sequentially. Completion requires explicit approval from required reviewers. A review requesting changes is a human decision point rather than an automatic rewriting loop.

### Recovering a stopped session

`GET /api/sessions/:id/recovery` answers:

```json
{
  "sessionId": "…", "status": "interrupted", "stranded": true,
  "summary": "Reviewer approved the work before Ploeg stopped the session. It will not run again on its own: deliver the approved work, or run it again as a new session.",
  "review": { "runId": "…", "roleName": "Reviewer", "verdict": "approve", "source": "transcript" },
  "execution": { "state": "interrupted", "stopConfirmed": true, "leaseExpired": true, "canPayAgain": false },
  "actions": [
    { "id": "deliver", "label": "Deliver the approved work", "description": "…", "method": "POST", "path": "/api/sessions/…/deliver", "available": true },
    { "id": "resume", "label": "Resume", "description": "…", "method": "POST", "path": "/api/sessions/…/resume", "available": false, "unavailableReason": "Ploeg blocked this execution's inference key when it stopped, so it cannot pay for another generation." },
    { "id": "run_again", "label": "Run again", "description": "…", "method": "POST", "path": "/api/sessions/…/run-again", "available": true },
    { "id": "cancel", "label": "Cancel", "description": "…", "method": "POST", "path": "/api/sessions/…/cancel", "available": true }
  ]
}
```

`stranded` is true for a paused or interrupted session that Ploeg executes and that cannot run again: Ploeg no longer holds it stopped, or its inference capability can no longer pay because Ploeg blocked the key when it stopped. `review` is the last role's verdict, `null` without one; `source` is `result` when the Run finished and `transcript` when the Run stopped after its stored answer already ended in a complete verdict block. `execution` is `null` for a standalone session; `canPayAgain` is `null` when it was not read. `actions` lists every step that applies to the session's state, in this order: `capture`, `deliver` and `resume` for a stopped session, `run_again` for a stopped, failed or cancelled one, `cancel` for one that has not ended, and `close_work_item` for a failed or cancelled Ploeg session whose Work Item is still open. Each action names its call; a step that applies but cannot be taken now has `available: false` and an `unavailableReason`. Viewers get 403.

`POST /api/sessions/:id/capture` requires a Ploeg-executed session that is paused or interrupted, not starting or stopping, with Ploeg's confirmed stop, a writing Team with a finished writing Run, a retained workspace and no captured candidate; otherwise 409 `not_capturable` with the reason. It confirms the remote turn stopped (409 `interrupt_unconfirmed`), captures and signs the candidate and keeps the workspace. If capture fails it answers 409 `candidate_unavailable`. It makes no model call and sends Ploeg no command. The session stays stopped; `deliver` then reuses the candidate, and the candidate's patch is the change to read.

`POST /api/sessions/:id/deliver` requires a Ploeg-executed session that is paused or interrupted, not starting or stopping, with Ploeg's confirmed stop, a writing Team, every earlier Run completed, a last reviewer verdict of `approve`, and a retained workspace; otherwise 409 `not_deliverable` with the reason. It first confirms the remote turn stopped (409 `interrupt_unconfirmed`), then reuses a candidate captured by `capture` or captures one from the workspace; if that fails it answers 409 `candidate_unavailable` and has changed nothing in Ploeg. With a candidate it sends Ploeg `resume`, which starts a new generation, marks the reviewer Run completed, signs and keeps the candidate, completes the session and reports it `completed` to Ploeg, which closes the Shift. It makes no model call and mints no key. Ploeg refusals answer as on resume. The completed session then follows the normal path: review, independent checks and approval.

A message does not promise immediate insertion into an executing model request. Pause, record the changed instruction and resume when the current run must restart with it. Resume preserves the existing authorization and settled spend. Unresolved prior spend remains held and can block resume. A process restart does not silently repeat paid execution. A session Ploeg executes in a pull-transport Kubernetes workspace whose running Run's prompt was accepted keeps running through a restart: the stopping workbench records `workspace.waiting` with phase `reconnecting` and leaves the agent working, and the restarted one checks that Ploeg still holds the execution running, waits up to `runtime.reconnectGraceMs` (default 300000, at most the Ploeg lease) for the workspace's worker to reconnect with the credential it holds, records `workspace.reconnected` and observes the Run to its end without prompting again. Its status stays `running` meanwhile, and `GET /api/status` lists it with phase `reconnecting`. Every other active session, and one whose workspace does not reconnect in time, is marked `interrupted` ([ADR 0051](../adrs/0051-a-running-session-survives-a-workbench-restart.md)). A session that completes, fails or is cancelled revokes its worker's relay credential once its candidate is captured; the worker then gets `401` with code `revoked` and stops, also after a restart.

`POST /api/sessions/:id/approval` with `{approval}` switches a live session between `manual` and `auto`, records `approval.changed`, and when switching to `auto` answers the permissions already waiting with `always`. Later roles are created with allow rules; a read role keeps its edit, bash and task denials.

In standalone mode, while a session runs, the workbench reads each held gateway key every fifteen seconds and records `budget.observed` with the spend the gateway has already attributed; the session carries it as `observedUsd`. The same tick reads the gateway's request ledger for the key and records per-model usage on the session as `usage`: the model that actually answered, the routed group when an auto-router chose it, requests, refusals, cost and tokens. The session also carries `requests`, one row per gateway request with the provider and endpoint host that served it, the inference region, the routed group with the router's tier and cause, the router's savings, retries, fallbacks, guardrails, cache hits and cached tokens, tokens, cost, duration and time to first token, the calling harness, the gateway call id for trace lookup, the error class on refusal, and the role it is attributed to by time. Settlement refreshes both once more. The Gateway tab shows the rows; the signed provenance records the usage and the set of providers. It is a live reading, not the settled figure `spentUsd`, which still arrives after reconciliation. A turn refused by the gateway because the key's ceiling is reached fails with category `budget_exhausted`, which requires mode-specific recovery; failed shared execution needs new explicit authorization.

A Team's read roles are not all reviewers. Only the final role of a Team carries the review verdict and is prompted for it; an earlier read role is an analysis role that answers the objective with evidence and returns no verdict, so an investigation Team of analyst then challenger completes on the challenger's approval alone. Run cards label the two as analysis and independent review.

### Gateway policy

`gatewayPolicy` in the configuration lists the providers and inference regions a workbench allows, as the gateway names them, for example `{"providers": ["anthropic"], "regions": ["eu"]}`. Before a session starts, the workbench resolves every model its Team will use through the gateway's catalogue, following an auto-router into its tiers, and refuses the start with 409 `policy_provider` when any tier is served by a provider outside the list. While the session runs, every ledger row is checked; the first row attributed to a provider or region outside the list stops the session with failure category `policy_violation`, revokes its gateway credential, records `policy.violated` with the offending request, and marks the row in `requests` with `violation`. Regions are only known after the fact, so the region rule is enforced within the fifteen-second ledger read, never before the first token.

### The brief a role received

`run.started` carries the composed prompt as `prompt`, split into objective, role instruction, operator notes, prior work, supplied evidence and the closing guidance, plus the model chosen for the role and `promptSha`, the SHA-256 of the exact text sent. The run keeps `promptSha` and the signed provenance records it per run, so a reviewer can match a transcript to the brief that produced it.

### Before the Team spends

`POST /api/sessions` refuses a manually written objective under twenty characters or four words with 400 `objective_too_thin`; an imported task is exempt. The optional brief check uses the session's credential and prefers a model whose identifier matches the small/fast heuristic, falling back to the first configured model. It does not compare prices. Imported tasks, already-checked briefs and `runtime.briefCheck: false` skip the check. An unavailable or malformed result is recorded as skipped; the check is not an authorization gate. An unclear result records `brief.unclear` and asks up to three questions. Answering through the permissions route appends the answers, records `brief.clarified`, and continues the Team.

Each role may make at most `runtime.maxToolCalls` tool calls, eighty by default, or the role's own `maxToolCalls`; beyond that the session fails with category `runaway` and `run.runaway` is recorded. A Team without a write role, an investigation, completes with its final reader's verdict on the run instead of failing when that verdict is not approve; only a Team with a writer treats a missing approval as `review_incomplete`.

`GET /api/models` describes the configured models through the gateway's catalogue: the provider that serves each, and for an auto-router its tiers and the provider set behind them.

### Team keys

[System ADR-0036](../../../../docs/adr/adr-0036-ploeg-and-unfold-use-one-vocabulary-with-named-screen-words.md) retired the word for a Team that Unfold's keys still used. Since then the API names a Team `teamId`, `teams` and `team`, and keeps the older keys working while clients and stored data move over:

| New | Deprecated | Where | Now |
| --- | --- | --- | --- |
| `teamId` | `crewId` | session requests and session JSON | Requests may send either, or both with the same value; two different values answer 400 `team_conflict`. Every session in a response carries both, with the same value. |
| `teams` | `crews` | configuration file and `GET /api/bootstrap` | The configuration may set either, or both with the same list; different lists stop the start. Bootstrap sends both. |
| `team` | `crew` | Agent host session configuration | Read as `team`; never echoed. |
| `roles` | `crew` | Run card JSON | Cards send both, and a card stored with only `crew` reads as `roles`. |
| `invalid_team` | `invalid_crew` | 400 when a configured Team's roles cannot run: no read role, a writer after the first role, or two roles with one id | Only the new code is sent; no Unfold client matches on the old one. |
| `unfold-team` | `unfold-crew` | Agent host composer model id | Only the new id is advertised; the host ignores the id a client sends. |

The migration has three steps:

1. Accept both names and prefer the new one (this release). Stored sessions are not rewritten: a session read from the store with only `crewId` gets `teamId` in memory, and saving it writes both, so the previous release can still read every row.
2. Rewrite the stored sessions once: a SQLite migration that takes a backup first and sets `$.teamId` from `$.crewId` with `json_set`. The Helm chart warns when its values still set `config.crews`.
3. Drop the deprecated names once the VS Code extension in use reads only the new ones: the API stops accepting and sending `crewId`, `crews` and the card's `crew`, and configuration refuses `crews`. Unfold's admission request to Ploeg keeps `crewId` until Ploeg renames that field.

### The human review

`completed` means the Team finished, the candidate was captured and signed, the workspace was released, and nothing was published; the label reads "Awaiting your review". `POST /api/sessions/:id/review` with `{decision, note?}` records that review once: `accepted`, with an optional note, or `rejected`, which requires a note so the next attempt can use it. The session carries `review` with the decision, who made it, when and the note, and `review.recorded` is appended to the history. A reviewed session cannot be reviewed again; 409 `already_reviewed` names the earlier decision. Publication, when it arrives, will require an accepted review.

## Durable events and human input

Sessions may include an additive `failure` object: `{category, stage, message, remediation, promptAcceptance, automaticRetry:false, detail?}`. Its message and remediation come from a fixed safe catalog. Raw exception text, HTTP headers, credentials, stack traces and provider response bodies are excluded. The optional `detail` is the recorded cause when the server itself produced it: the failing workspace command, its exit code or signal, and the last 4 KiB of its standard error, with credentials, bearer tokens, key-shaped strings and server filesystem paths redacted and the whole bounded to 2,000 characters. Runtime exception messages never become `detail`. Older sessions and servers may omit both fields; `blocker` remains a compatible short message. Every failed session also writes one server log line, `session.failed`, with the session, its Work Item when Ploeg executes it, `category`, `stage`, `promptAcceptance`, the failed Run and its Role, the message and the redacted `detail`, so an operator can tell why a session failed from the logs alone. When OpenCode cannot list its pending permission requests (HTTP 400, an OpenCode defect for some tools, anomalyco/opencode#38912), the turn continues on the event stream, records `runtime.permission_list_unreadable` once, and logs it with the session.

Stages are `credentials`, `workspace`, `runtime`, `prompt` and `execution`. Prompt certainty is `not_submitted`, `rejected`, `accepted` or `unknown`. `accepted` means submission was acknowledged, not completed work or settled spend. `unknown` means the runtime may have started paid work; it never authorizes an automatic retry. `session.failed` and operator pause/cancel events retain the same safe object in `data.failure`. An explicit new execution clears the current failure; durable history retains earlier evidence. Cancellation metadata is stop intent, not proof of remote termination.

| Method and path | Behavior |
| --- | --- |
| `GET /api/sessions/:id/history?after=N` | Durable event array after cursor `N` |
| `GET /api/sessions/:id/events?after=N` | Server-sent events; numeric `id`, JSON Event in `data`. Catch-up from an old cursor is read from storage in batches of 200 events until the client is current |
| `GET /api/sessions/:id/permissions` | Human permission/question requests without native credential state |
| `POST /api/sessions/:id/permissions/:requestId` | Permission `{decision:"once"|"always"|"reject"}` or question `{answers:string[][]}` |
| `GET /api/sessions/:id/investigation` | Read-only first diagnosis of why the session stopped: `class` (`unfold_stall`, `ploeg_unreachable`, `ploeg_refused`, `unfold_restart`, `operator_stop`, `guard` or `unclear`), the `verdict` and the `rule` that matched, `facts`, a `timeline` of Unfold events and Ploeg revisions around the stop, `next` steps and whether the Ploeg side was `read`, `unavailable` or `not_bound`. It sends no Ploeg command and records nothing |

An event contains `id`, `sessionId`, `type`, `at`, `actor`, optional `runId` and structured `data`. Streamed agent text arrives as `message` events that each carry part of one `partId`; a client joins consecutive parts with the same run and `partId`. Unfold stores at most one such event per part every 500 ms. Reconnection can use `after` or the standard `Last-Event-ID` header; when both are sent the stream resumes after the higher of the two, so a browser's automatic reconnect to the original `?after=` URL does not replay what it already received. Treat events as replayable and deduplicate by ID. A terminal session remains inspectable through history.

Permission and question details depend on the adapter. Answer only the actual unresolved request; a generic message is not a permission grant. A successful HTTP action reflects the stored lifecycle transition, not completion of all subsequent background work.

## Linked tasks

Connections are administrator-registered `taskSources`. Forgejo, GitHub, GitLab, ClickUp and Vikunja share the same read API. Only hand-off to Ploeg writes to a tracker, and only to Vikunja. A source maps one tracker project or list to a configured repository. Task content cannot supply a repository URL, model credential, runtime command or execution owner. All authenticated users of this pilot deployment can browse its registered sources; source-level team authorization is a later feature.

A snapshot includes `key`, `sourceId`, `provider`, `id`, `revision`, `title`, `description`, `url`, `status`, `repositoryId` and optional `updatedAt`. It may also carry `labels` (`{name,color?}`, at most 50), `assignees` (`{username,name?}`, at most 50), the provider's own `priority` (omitted when unset), `dueAt` and the tracker's display `identifier` such as `UNFOLD-12`. None of these change the revision. A list page cuts a description over 16,000 characters and sets `descriptionTruncated: true`; its revision still covers the whole description. A preview with `truncate=1` shortens it the same way, while a plain preview or an import of that task still refuses it. The preview alone adds `descriptionMarkdown`, the description to display. A Vikunja description that looks like HTML is first converted to the Markdown subset the browser renders, with relative links resolved against the tracker's web address; any other description is taken as it is. In every case the source's token is then replaced by `[redacted]` ([`presentTask`](../../src/tasks.ts)). The list, the snapshot's `revision`, the stored `sourceTask` and the import never carry it. Status is normalized to `open`, `closed` or `unknown`; only open tasks can be imported. The revision hashes the material snapshot. Import refetches the configured source and returns 409 `task_changed` if the preview is stale. The server retains the accepted snapshot in `session.sourceTask`, redacting any known server credentials from its title and description before persistence and prompting and frames its body as untrusted reference material in the objective.

Import requires an operator or administrator and passes the same mutation guard as other actions. It does not call a model, assign a tracker task or start execution. Calling import twice for the same canonical task and revision returns the existing session across reconnects and process restarts. Another operator receives a generic conflict, without private session details. A changed revision cannot create competing work while an earlier session is active, stopping or has unresolved Holds. Finished revisions remain inspectable; importing is not a retry command.

### Hand a task to Ploeg

A source has `handoff: true` when it is a Vikunja source with a token, `executionOwner: "ploeg"` and a live Ploeg operator connection. Hand-off assigns the tracker user that routes work to a team, which Ploeg's `task.assignee.created` webhook turns into a queued Work Item ([ADR 0025](../adrs/0025-hand-tracker-tasks-to-ploeg-by-assignment.md)).

```ts
type TaskPloegStatus = {
  available: boolean; message?: string; demo: boolean;
  handoff: { allowed: boolean; reason?: string };
  teams: { id: string; assignee: string; queueDepth: number; paused: boolean | null; roles: string[] }[];
  assignedTeams: string[];
  workItems: { id: string; team: string; state: string; attempts: number; updatedAt: string; prUrl?: string; branch?: string; spentUsd?: number; budgetUsd?: number }[];
  fetchedAt: string;
  warnings?: string[];
};
```

`teams` are the caller's Ploeg teams that report at least one tracker assignee; `assignee` is the first. `assignedTeams` are those whose assignee is on the task, compared without case because Ploeg lowercases routing names. `workItems` come from Ploeg's `work-items?provider&externalId` filter, limited to the caller's teams, with the latest Shift's branch and spend and, for the three most recent, a pull request link from checkpoints. An unreachable Ploeg gives `available: false`. A Ploeg too old to report assignees or the filter gives empty `teams` or `workItems` with a reason; neither is an error. The demo fixture source answers `available: false` with `Demo fixture tasks are not linked to Ploeg.`

Hand-off and take-back pass the mutation guard and require an operator or administrator.

| Refusal | Meaning |
| --- | --- |
| 403 `forbidden` | A viewer |
| 422 `handoff_unsupported` | The source cannot hand off |
| 404 `handoff_team` | The team is outside the caller's Ploeg scope, has no tracker user, or Ploeg does not report assignees |
| 409 `task_closed`, 409 `task_changed` | The re-read task is done, or its revision differs from `revision`; reload it |
| 502 `task_write_forbidden` | The workbench's Vikunja token cannot add or remove assignees or add comments |
| 502 `handoff_assignee_unknown` | Vikunja has no user with the team's tracker username that the token can see |
| 409 `handoff_active` | Hand-off while another team's tracker user is on the task, or while any Work Item for it is in a state other than withdrawn, done or stale; a team outside the caller's scope is not named; nothing is written |
| 409 `handoff_started` | Take-back while any Work Item for the task, in any team, is in a state other than queued, withdrawn, done or stale |

These safety checks read Ploeg's Work Items for the task across every team the workbench's Ploeg consumer can see, not only the caller's teams, because Ploeg files one Work Item per tracker task and a board pin can place it in another team. A board that Ploeg pins to a team (`pinnedScopes` on that team) offers only that team; if it has no tracker user or is outside the caller's access, the status explains why hand-off is unavailable.
| 503 `handoff_unverified` | Hand-off or take-back while Ploeg cannot list Work Items by tracker task; nothing is written |

Hand-off resolves the user through `GET /projects/:project/projectusers?s=`, then `GET /users?s=`, and sends `PUT /tasks/:id/assignees` and `PUT /tasks/:id/comments` with `<p>Handed to Ploeg team <code>TEAM</code> by NAME from Unfold.</p>`, NAME HTML-escaped. Take-back sends `DELETE /tasks/:id/assignees/:userId` and a `Taken back from Ploeg team` comment. Both are idempotent: when there is nothing to change, nothing is written. A failed comment leaves the assignment in place and adds a warning. Each action writes a `task.handoff` or `task.take_back` log line with the actor, source, task, team and outcome.

Set `executionOwner: "ploeg"` on repositories assigned to Ploeg execution. A live Unfold always has shared authority configured, because it refuses to start without it; supported tracker imports instead require the current registered Ploeg binding and canonical admission checks at Start. See [tracker binding](ploeg-tracker-binding.md) and [connection setup](../operations/task-connections.md).

### Transcript detail

A `tool` event carries the OpenCode part id, the tool's input as a bounded JSON preview, the tail of its output once completed, and its error text when it failed, so the stream shows one card per tool call that opens to what ran and what came back. Every run also records a `transcript` artifact: the assistant's text, reasoning when the model returned it, and each tool call with input, output and error, prefixed with the model that answered. Transcripts are shown in the Handoff tab and are not fed to later roles as evidence. A run's summary and `summary` artifact have the JSON verdict block removed; the verdict itself is on the run.

| `GET /api/attestations/public-key` | PEM public key of the workbench's Ed25519 attestation key; `X-Key-Id` carries its identifier |

The candidate provenance predicate keeps the key `crew` for the session's Team and its Roles. It is part of a signed, versioned predicate type that verifiers parse, and renaming it would change that type, so it stays until the predicate type gets a new version. `candidate.attestation` records the key identifier and predicate types when signing succeeded; a `candidate.attestation_failed` event marks a captured but unsigned candidate.

## Candidate delivery

Delivery applies only to a shared Ploeg execution on a repository with a configured delivery policy; [governed candidate delivery](candidate-delivery.md) owns the full contract. Each route uses the session's owner or administrator check, and the `POST` routes also require an operator or administrator, the mutation header and a JSON body. Refusals are 409 with a delivery code, for example `shared_execution_required` for a standalone session or `completed_candidate_required` before the execution has completed and confirmed its stop.

| Method and path | Behavior |
| --- | --- |
| `GET /api/sessions/:id/delivery` | `{configured, policySha256?, localPhase?, checks?, candidate, receipt, approval, operation, publication?, publicationEnabled}`: Ploeg's delivery record for the execution, validated against the session, plus the local verification phase and check results. `publication` is `{phase, operationId, branch, pullRequest?}` once a publish started; an operator or administrator reading it reconciles an unfinished publication with idempotent steps; a viewer's read never does. `publicationEnabled` is true only with a configured publisher and no refused reservation |
| `GET /api/sessions/:id/delivery/download` | The canonical Git bundle `canonical-candidate.git.bundle`; 409 `canonical_candidate_unavailable` before verification has canonicalized it |
| `POST /api/sessions/:id/delivery/verify` | `{}`; canonicalizes the captured candidate on the approved base, registers it with Ploeg, runs the pinned policy checks and records the receipt. A retry replays the retained result instead of running checks again |
| `POST /api/sessions/:id/delivery/approve` | `{candidateId, receiptId, policySha256}` exactly; records the candidate-bound approval in Ploeg. Approval alone never publishes |
| `POST /api/sessions/:id/delivery/publish` | `{candidateId, receiptId, policySha256}` exactly, as displayed; a missing identity is 400 `publication_binding_required`. Approves when missing, reserves the publication in Ploeg, pushes the canonical commit and opens one pull request, then reports it published. Serialized per session and resumable. Refusals include `publication_disabled`, `publication_refused`, `publication_recovery_required` (a replayed reservation without local authorization, never pushed) and `publication_unknown` (a different commit on the branch or an unverifiable pull request, which is closed; a human decides) |

Today at most one, `id` `ploeg`, from `UNFOLD_PLOEG_MCP_URL` and `UNFOLD_PLOEG_MCP_CLIENT_ID`; with neither set, `servers` is empty. ## Agent host

| Method and path | Behavior |
| --- | --- |
| `GET /api/agent-host` | Protocol version (`protocolVersion`, the newest baseline, and `protocolVersions`, both baselines), WebSocket address, its `connectionAuthority` (below), the shape of the VS Code setting, and the caller's own initialized connections: `clients` counts them and `attached` lists each as `{name?, version?, protocolVersion, connectedAt, tokenId}`, oldest first. `name` and `version` are the `clientInfo` the client sent in `initialize`, `protocolVersion` the version the connection negotiated, and `tokenId` is the `id` of the token it connected with. Another person's connections never appear |
| `POST /api/agent-host/tokens` | `{label?}` → `{token, id, address, vscodeSetting}`, status 201; viewers are refused. The token is shown once and bound to the caller and the sign-in that issued it. `id` is the token's SHA-256 digest in lowercase hex |
| `DELETE /api/agent-host/tokens/:id` | `{revoked: true}`; revokes one of the caller's tokens and closes its open connections with WebSocket code 1008. It needs the mutation header, as `POST` does. A token that is unknown, already revoked or another person's answers 404 `not_found` |
| `PUT /api/agent-host/editor-window` | `{protocol, windowId}` → the same: remembers the caller's VS Code editor window, which links in their Agents window then open in ([ADR 0012](../adrs/0012-agent-host-protocol-host.md), update 2026-10-18). `protocol` is `vscode` or `vscode-insiders` and `windowId` the number VS Code's `env.asExternalUri` adds to the extension's own link. Anything else answers 400 `invalid_editor_window`, and viewers are refused with 403. Each call replaces the last one, and the workbench keeps it in memory only |
| `DELETE /api/agent-host/editor-window` | `{forgotten}`: forgets the caller's editor window, so their Agents window links open only the browser |
| `GET /api/agent-host/sessions/:id/link` | `{session, attached, address, connectionAuthority, links: {stable, insiders}}`: the link that opens the session in the caller's VS Code Agents window ([below](#agents-window-links)). It goes to whoever the host lists the session to, by the same rule as `listSessions`: its owner and administrators. Anyone else gets 404 `not_found`, as for a session that does not exist, and viewers are refused with 403 |
| `GET /api/agent-host/work-items/:id/link` | The same for a Ploeg Work Item's session, `wi-<id>`, by Ploeg's Work Item id. It is given to whoever Ploeg's team authorization lets open that session, the rule that lists it in their Agents window. A Work Item it hides, one an Operator Execution owns (its Unfold session is the one to open), an unknown id and a workbench without a live Ploeg answer 404 `not_found`; a Ploeg that cannot be read answers its own error status |

A connection token lives as long as a login. It expires after `auth.sessionHours` (twelve by default) without use, and every connection or message renews that window. The workbench stores only its SHA-256 digest. Signing out through `POST /api/logout` revokes every token the sign-in issued and closes their connections with WebSocket code 1008; a sign-in that expires has the same effect at the token's next use. An editor that holds a token derives its `id` by hashing it, so it can revoke the token without keeping anything else.

The WebSocket endpoint is the workbench address, on path `/` or `/ahp`, with `?tkn=<token>`; it speaks both released Agent Host Protocol baselines, 1.0.0 and 0.9.0 ([ADR 0012](../adrs/0012-agent-host-protocol-host.md)). Without an agent host, every `/api/agent-host` route answers 404 `agent_host_disabled`.

### Agents window links

VS Code 1.142 opens a session from a link of the form `<protocol>://agents/agent-host-session/<scheme>/<id>?connectionAuthority=<authority>`. The link endpoints build it as follows, read from VS Code's source at tag 1.142.0 (`buildExternalOpenSessionLinkUri` and `parseExternalOpenSessionLinkUri` in `src/vs/platform/agentHost/common/openSessionLink.ts`, the main process's `handleProtocolUrl` in `src/vs/code/electron-main/app.ts`, and `agentHostAuthority` in `src/vs/platform/agentHost/common/agentHostUri.ts`):

- **Protocol and authority.** `<protocol>` is the build's `urlProtocol`: `vscode` for Stable, `vscode-insiders` for Insiders. The URL authority is always `agents`. `links.stable` and `links.insiders` hold one of each; the extension uses its own `vscode.env.uriScheme`.
- **Path.** `/agent-host-session/<scheme>/<id>` is the session URI the host gave that client, `<scheme>:/<id>`, with the scheme moved into the path. An optional `/chat/<id>` suffix selects a peer chat; Unfold's sessions have one chat, so its links never carry one.
- **Session spelling.** VS Code finds the session by comparing the link's URI with the one the host listed for it, so the link must use that client's spelling: `ahp-session:/<id>` for a 1.142 Agents window, which sends `_meta["vscode.ahpSessionUris"]`, and `unfold:/<id>` for a 1.141 one. `session` is the URI in the spelling of the caller's newest attached Agents window, or `ahp-session` when none is attached. A Work Item's id is `wi-<Work Item id>`.
- **Query.** `connectionAuthority` names the remote host. `session=<uri>` is added only for a session URI with an authority, query or fragment, which Unfold's never have. `turn=<id>` is optional and not used.
- **The authority's spelling.** VS Code derives it from the `chat.remoteAgentHosts` entry's `address` exactly as written, after dropping a leading `ws://`: `local` becomes `remote_local`, a lowercase alphanumeric address stays, a lowercase host-like address (`[a-z0-9.:-]`) replaces each `:` with `__`, and anything else becomes `hex-` and its UTF-8 bytes in lowercase hex. `ws://127.0.0.1:4080` is therefore `127.0.0.1__4080`, and `wss://unfold.example` is `hex-7773733a2f2f756e666f6c642e6578616d706c65`. A trailing slash or a different case changes the authority. The endpoints encode the address this workbench advertises, which is what the extension writes; the extension rebuilds the link from the person's own settings entry. The address never holds the connection token: the advertised address has none, the extension writes the token to the entry's `connectionToken`, and VS Code's **Add Remote Agent Host** moves a pasted `?tkn=` there too (`parseRemoteAgentHostInput`). An address that does carry `tkn`, such as a hand-edited entry, would encode the token into the authority, so no link is built from it, and the extension asks the person to move the token instead. `public/core/agents-window.js` holds the encoding, shared by the server, the browser and the extension.
- **A malformed authority.** A `connectionAuthority` that is empty or does not percent-decode invalidates the link, so the main process does not open the Agents window for it and handles the URL as an ordinary `vscode://` link instead.
- **An unknown authority.** A well-formed authority of a host the window does not have, or a session that host does not list, opens the Agents window, which waits up to 15 seconds for the session to appear and then shows "The linked session could not be found". Nothing falls back to the browser; the browser page stays where it was.

Opening such a link from inside VS Code, with `vscode.env.openExternal`, goes through the window's URL service to the same main-process handler. A click-through against a desktop VS Code is not yet verified ([VIK-1922](https://vikunja.webgrip.dev/tasks/1922)).

The host answers `initialize` with the highest version the client offered in `>=1.0.0 <2.0.0` or `>=0.9.0 <0.10.0`, as the exact string offered: VS Code main, which offers `1.0.0, 0.10.0, 0.9.0`, gets `1.0.0`, and VS Code 1.141, which offers `0.10.0, 0.9.0, …`, gets `0.9.0`. An offer with neither gets `-32005` with `supportedVersions: ['^1.0.0', '^0.9.0']` and the connection closes; a malformed version gets `-32602`, even when another entry would match. The negotiated version holds for the connection and for a later `reconnect` of the same client. A 0.9 client never receives an action that AHP 1.0.0's registry introduces after 0.9 (`chat/canvasesChanged`, `canvas/stateChanged`), nor `SessionSummary.chats` or `defaultChat`. A 1.x client receives both in `listSessions`, `root/sessionAdded` and `root/sessionSummaryChanged`: `chats` holds the session's one chat with its `status` bits, read (32) and archived (64) included, its `origin`, `interactivity` and, once a candidate is ready, `changes`. A chat's read or archive mark republishes that catalog to the person's 1.x clients. A VS Code client whose `clientInfo.name` is `vscode-agents-window` or `vscode-editor-window` and that does not send `_meta["vscode.ahpSessionUris"]` sees sessions as `unfold:/<id>`. Every other client sees `ahp-session:/<id>`, and both spellings are accepted on input. `initialize` answers with `defaultDirectory: file:///unfold-repositories`, a virtual folder: `resourceList` on it lists one directory per configured repository, named after the last segment of the repository's forge path (`twente.dev`), with ` (<id>)` added when two repositories share that name. `resourceList` on `file:///` lists only that folder. `resourceResolve`, which VS Code 1.142's folder picker sends for every folder it opens or stats (`agentHostFileSystemProvider.ts` `stat` and `realpath`), answers `{uri, type: "directory"}` for `file:///`, the repositories folder and each repository's folder, with or without a trailing slash, and echoes the URI it was given. Any other path answers `-32008` to both, and the host's own filesystem is never listed. A repository's folder under its earlier name, `Unfold · <repository>`, still resolves and still picks that repository, so working directories saved before 2026-10-17 keep working; the session's project keeps that display name. The host logs each request it cannot answer as `agent_host.unanswered_request` with the method and, for a resource request, the path only. A working directory in that folder, in `resolveSessionConfig` or as the first of `createSession`'s `workingDirectories`, sets the session's repository and overrides `config.repository`. A session's `project` is `{uri: <repository url>, displayName: Unfold · <repository>}`. A failed session's `activity`, in its summary and its chat's, is `Failed: <reason>`, from the classified failure or the session's blocker. VS Code 1.141 shows a chat's activity whatever its state, but shows a session's activity only while it runs or needs input. The `unfold` agent in the root state declares `protectedResources: []`: the connection token already identifies the person, and VS Code 1.141 treats an agent without that field as gated behind GitHub Copilot sign-in ([sign-in spike](../research/2026-10-10-ahp-sign-in-spike.md)). Read and archive marks are kept per person; they never pause, cancel or change a session. Accepting, rejecting or requesting changes on a candidate from a client's Changes view uses the same review path and owner check as the browser ([below](#reviewing-a-candidate-from-vs-code)). A client that this host initialized can resume with `reconnect` on a new connection, also after a restart, and always receives snapshots, never a replay; any other client must initialize again (`-32008`). The host remembers the last 1,000 clients. `serverSeq` never moves backwards: the host reserves sequence numbers in blocks of 1,000 in its store and resumes after the last reservation, so numbers may skip but a pre-restart `lastSeenServerSeq` is always behind the next action. A session's `activeClients` survive a restart; each restored client gets the usual 30-second grace period to come back. Disposing a session drops its active clients. The host keeps a session's chat projection in memory while it is subscribed, and drops it on `disposeSession` or ten minutes after the last client unsubscribed from an ended session; the next subscribe rebuilds the same snapshot from the durable events.

A session's and its chat's `status` carry the input-needed bits (24), which VS Code 1.142 labels "Needs attention", while a permission, a question or a host choice waits for the person, a review question included; a candidate that only waits in the Changes view stays idle. A Work Item session and its chat carry them while one of the host's questions waits for that person. A waiting choice is also listed in the session's `inputNeeded` as a `chatInput`, for as long as the host holds the chat (while a client follows it, and up to ten minutes after). Every dispatched action is answered with its echo or with a rejection carrying the sender's `origin`, also when the sender's version does not know the action type. AHP 1.1's `chat/configChanged` is never sent to a 1.0 or 0.9 client and is refused, because no configuration property is `chatMutable`. A `chat/pendingMessageSet` or `chat/pendingMessageRemoved` without `kind` counts as `queued`. `vscode/stopBackgroundWork` answers `{stopped: false}`, because the host publishes no background work, and `vscode/cancelAgentHostDebugLogs` answers `null`. `vscode/collectAgentHostDebugLogs` answers `-32009`, because the host's logs cover every person's sessions; VS Code then exports its own logs only. `setClientManagedSettingsPermissions` is a notification and is ignored. `resourceWrite`, `resourceCopy`, `resourceDelete`, `resourceMove` and `resourceMkdir` answer `-32009`, which VS Code maps to `NoPermissions`: a client never changes a Run's workspace. Being answered, they are not logged as `agent_host.unanswered_request`.

A session's configuration schema, from `resolveSessionConfig` and in every session state, has `repository` (read-only, an enum of repository ids with their names as `enumLabels`; the picked working directory decides it), `team` (Team ids, names as labels, and per Team a description naming each role's configured model, or none in the demo; a client that still sends the deprecated key `crew` gets that value as `team`, `team` wins when both are sent, and `crew` is never echoed), `budgetUsd` (a string enum of presets from 1 to 1000 up to `maxBudgetUsd`, plus the default, the limit and the current value, labelled in the shared money format; a number is still accepted), `placement` when more than one backend is enabled, `approvalMode` (`manual`, plus `allow-all` only when the effective placement is `docker` or `kubernetes`; the engine's `auto`) and `title`. Unknown keys a client sends are dropped. Defaults are the picked or first repository, the first Team, 5 within the limit, the runtime's default placement and `manual`. `createSession` refuses a configuration this workbench does not offer with `-32602`. Before the first message, `session/configChanged` on the session channel changes the draft's configuration and is echoed with the full result and `replace: true`; a different `repository` is refused. After it, only `approvalMode` may change, through the same route as `POST /api/sessions/:id/approval`, and only while the session runs in a container or pod, which its schema marks `sessionMutable`; any other changed value is refused. The root state's `unfold` agent advertises one model, `unfold-team` (`unfold-crew` before system ADR-0036; the host never reads the model id a client sends back, so a client that remembers the old id still creates sessions), named `Ploeg team · <execution.team>`, `Unfold team` without managed execution, or `Demo team · no model calls`. A user turn carries no `message.model`, so VS Code labels a response with no model the host did not observe.

A new session starts with its first `chat/turnStarted`. When the workbench refuses that message, for example with `objective_too_thin`, the host accepts the turn and ends it with `chat/error` carrying the code and the reason, instead of `session/creationFailed`, which the Agents window drops without showing it. The session stays open, its chat snapshot keeps the refused turn, and the next message tries again.

On a workbench with a live Ploeg connection and at least one Vikunja task source whose `executionOwner` is `ploeg`, `initialize` also answers `automations: {}` and `_meta["vscode.autonomousAutomations"]: true`. `ahp-automations://` is then a read-only catalogue of tracker routes ([ADR 0012](../adrs/0012-agent-host-protocol-host.md#update-2026-10-10-automations)). Each entry, `ahp-automation:/tracker.<source>.<team>`, is one such board and one Ploeg team the person may route its tasks to: the board's pinned team, or else each of their teams with a tracker user. Its `definition` has `title` `<board> → <team>`, an `automation`-origin message that explains the route, `session: {provider: "unfold", workingDirectories: [<the repository's folder>]}`, `enabled` false while the team is paused, and one event trigger of type `unfold.tracker-assignment` whose `config` is `{source, team, assignee}`. `operations` and `runs` are always empty. `listAutomationTriggerDefinitions` returns that trigger type, `fetchAutomationRuns` answers `{}`, and `runAutomation` answers `-32009`; a resource that is not one of the person's routes answers `-32008`. `automation/createRequested`, `automation/updateRequested` and `automation/removed` are rejected with a `rejectionReason`. While someone watches the catalogue the host reads Ploeg's teams again each minute and sends that person's clients `automation/set` and `automation/removed` for what changed. A person without Ploeg team access gets an empty catalogue whose `_meta["dev.webgrip.unfold"].reason` says why. Without that Ploeg connection or board, `initialize` carries no `automations` and the three commands answer `-32601`. The channel still answers, with no entries and a `reason`, and rejects every change: VS Code 1.141 subscribes to it on every connection, and an unknown-channel error there fails `initialize` and `reconnect` alike. The host also accepts the spelling `ahp-automations:`, which is what VS Code sends: it parses the channel as a URI and prints it again without the empty authority's `//`.

On a workbench with a live Ploeg connection, outside the demo, `listSessions` also lists the Ploeg Work Items a person may see as read-only sessions ([ADR 0023](../adrs/0023-unfold-submits-work-to-ploeg-and-never-executes-it.md), [`src/ahp/work-items.ts`](../../src/ahp/work-items.ts)). Each is `wi-<workItemId>` under provider `unfold`, in either spelling, titled `#<id> <title>`, with Ploeg's record under `_meta["unfold.workItem"]` (`id`, `team`, `state`, `url`, `pullRequest`, `round`, `budgetUsd`, `spentUsd`, a needs-human or stale `reason`, `stale` and `readOnly: true`). Who sees one is Ploeg's team authorization, the same `userTeams` scope as the Ploeg pages; a person without a Ploeg team sees none. The list holds every open Work Item of the person's teams and those that finished in the last 14 days, open ones first, newest change first, at most 100. A Work Item an Operator Execution owns, whose latest Shift runs on a branch `operator/<session>`, is left out: it already lists as its Unfold session. Status and activity follow the state:

| Ploeg state | Status | Activity |
| --- | --- | --- |
| `ingested`, `queued` | idle | `Queued for <team>` |
| `leased` | in progress | `<Role> · Round <n> · <spent>/<budget>` |
| `proposed` | needs input | `Waiting for approval` |
| `needs_human` | needs input | the reason chip, as on the Work Item page |
| `awaiting_review` | needs input | `Ready for review · PR #<n>` |
| `stale` | error | the reason chip |
| `done` | idle | `Merged`, or `Done` without a pull request |
| `withdrawn` | idle | why it was withdrawn |

The session's default chat holds one turn per Round, in the order Ploeg ran them, each with a system-notification message `Round <n>` (and `· Shift <m>` when the Work Item had more than one Shift). Each Run is a `ploeg_run` tool call rendered as a subagent, completed with its verdict and reported summary once it finished; its own chat is read-only and shows what Ploeg recorded of the Run (below) and what it reported. A failure that holds a Python traceback, in Rich's box-drawing form or the interpreter's, is shown as the exception type and message and the last three frames, with the full text after it under **Full output**; when Ploeg's failure reason is only a code such as `agent_error`, its stuck reason is shown instead. Neither chat offers configuration, and the session, its default chat and each Run's chat carry an empty `changesets` catalogue: the change lives in the Work Item's pull request, which the activity names ("Ready for review · PR #n") and Ploeg's detail does not list the files of. An absent catalogue would leave VS Code 1.142 waiting for one, and its Changes view would keep the last session's file count over an empty list. An Unfold session without a candidate carries the same empty catalogue; the default chat takes the input requests of the commands below.

While a client is attached, one fleet poller reads Ploeg's `GET /api/v1/operator/events` oldest first with `after=<cursor>` every three seconds. It starts at the newest event, after reading back up to 14 days of events to find recently finished Work Items, and keeps its cursor across an outage. It reads each Work Item an event touched once and sends `root/sessionAdded`, `root/sessionSummaryChanged` or `root/sessionRemoved` only to people whose team may see it, and the new Rounds, Runs and Run results to the clients subscribed to its chat. Ploeg's audit pages have snapshot consistency, so the poller reads every attached person's list again each minute to catch an event committed behind its cursor. When Ploeg cannot be read, every Work Item session is marked stale (`_meta["unfold.workItem"].stale: true`, activity `Ploeg is unreachable; last known state: …`); Unfold's own sessions keep listing and opening. Read and archive marks on a Work Item session are the person's own; archiving is not cancelling. Every change other than the commands below is rejected: a message to work that is not stopped, running or queued with "Ploeg can't take instructions for running work yet. Stop it, or wait until it needs you."; Try Again on such work with "Ploeg restarts a Work Item once it stopped and needs you or went stale."; `disposeSession` with `-32009`, and any other action as read-only. A `createSession` that names a `wi-` id answers `-32003`.

While someone subscribes to a Run's chat (`ahp-chat://subagent/…/ploeg-run-<runId>`, which VS Code also subscribes to while it shows the running `ploeg_run` call) or its pod-log terminal, one poller per Run, whatever the number of viewers, reads Ploeg's `GET /api/v1/operator/runs/{id}/transcript?after=<seq>` from its cursor and the Run's pod logs every three seconds ([`src/ahp/run-live.ts`](../../src/ahp/run-live.ts)). It stops once nobody watches or the Run finishes, and backs off up to a minute while Ploeg or the log store fails; neither outage affects the session list. The transcript enters the Run's turn: `message` as Markdown, `thought` as reasoning, `plan`, `stage` and `truncated` as Markdown, and each `tool_call` as a tool call with its `title` as the invocation message and its `input` (or `paths`) as `toolInput`. A `tool_output` entry replaces that call's text content with the last 4,000 characters of its output, and a `completed` or `failed` status completes it; a call still open when the Run ends completes as unsuccessful. VS Code 1.142 nests a subagent's tool calls under its `ploeg_run` call in the Work Item's chat, and shows its Markdown and reasoning only when the Run's chat is opened. The pod logs are a `ploeg_pod_logs` tool call whose content is the read-only terminal `ahp-terminal:/wi-<workItemId>/<runId>` (`isPty: false`, `toolInput` a string, as VS Code requires to attach it): its state holds the lines read so far as one `unclassified` part, at most 64,000 characters, each line `HH:MM:SS [worker|sandbox] text`, and each later read adds a `terminal/data` increment. The pods are the sandbox pods whose lines carry the Run's trace key and, for each `sbx-<name>`, the worker pod `<name>` that claimed it. When the Run finishes, the terminal sends `terminal/exited` and keeps its lines. The transcript and logs are served through Ploeg's redaction, the known-secret redaction and the credential patterns, and only to people Ploeg's team authorization lets see the Work Item: anyone else gets `-32008` `Terminal not found`, and someone who leaves the team stops receiving output. Every client action on the terminal is rejected as read-only.

Operators and administrators whom Ploeg's team authorization lets see a Work Item may command it from its chat ([`src/ahp/work-item-commands.ts`](../../src/ahp/work-item-commands.ts)). Every command waits for the person's answer to an input request the host raises, and nothing reaches Ploeg on the click alone. A viewer is asked nothing; a Stop answers "Only an operator or administrator of `<team>` can act on its Work Items. You can follow this one." Each question is the person's own: it is sent only to their clients, listed in the session's `inputNeeded` as a `chatInput`, and kept in memory by the host, so a restart forgets an unanswered question but never a command.

- **Approve or reject.** Opening a `proposed` Work Item asks **Approve #n?** in a turn of its own: a single-select question `approve`/`reject` and an optional text question for the reason. A rejection without a reason says so, calls nothing and asks again. The answer calls Ploeg's `POST /api/v1/operator/work-items/{id}/approve` or `…/reject` with `{reason}`. A question the Work Item has moved past closes with "#n no longer waits for approval, so nothing changed."
- **Stop.** `chat/turnCancelled` is rejected with "Confirm below to withdraw #n. Nothing stops until you do." and asks, in the running Round's turn or a turn of its own, "Withdraw #n? This stops the running Run, blocks its keys and comments on the tracker. It can't be resumed." with **Withdraw #n** and **Keep it running**. Only **Withdraw #n** calls Ploeg's `POST /api/v1/operator/work-items/{id}/cancel`, which withdraws the Work Item for good ([ADR 0023](../adrs/0023-unfold-submits-work-to-ploeg-and-never-executes-it.md)); the reply gives Ploeg's own count of stopped Runs. The cancel carries `{commandId, expectedShiftId}`, where `expectedShiftId` is the Shift the person's projection showed open when Stop was asked, left out when none was. When Ploeg's open Shift is another one by then it answers 409 `shift_changed` and withdraws nothing, and the reply is "#n started a new attempt since you looked; nothing was withdrawn. Look again and stop it if you still want to." A Ploeg that refuses a cancel body (400 `invalid_request`, before Ploeg's guarded cancel) is sent the cancel again without one, and this process sends it none from then on. Stop on a done or withdrawn Work Item answers "#n already ended, so there is nothing to stop.", and Stop on the turn of a question still open dismisses that question.
- **Try Again and restart with a note.** On a `needs_human` or `stale` Work Item, a message keeps its own turn and asks "Restart from Round 1 with this note? This spends from `<team>`'s pool."; `chat/turnResume` is rejected with "Confirm below to restart #n. Nothing runs until you do." and asks the same without "with this note" in a turn of its own. A message that arrives as a pending message while a question is open replaces that question. Only **Restart from Round 1** calls Ploeg's `POST /api/v1/operator/work-items/{id}/requeue` ([Ploeg ADR-0044](../../../ploeg/docs/adrs/0044-an-operator-restarts-stopped-work-from-a-round-they-choose.md)) with `{commandId, expectedState, note?}`; **Leave it stopped** changes nothing. When the last Shift's budget ran out (reason `budget_exhausted` or `budget_exhausted_before_fix_round`), the question also offers **Restart with a `<maxBudgetUsd>` pool**, which sends `poolUsd` set to the workbench's `maxBudgetUsd`. Ploeg does not report its consumer's own `maxBudgetUsd`, so it decides: `pool_above_limit` answers "Raise the Team's budget to try again with more." Ploeg's other refusals (`not_requeueable`, `state_changed`, `operator_owned`, `command_conflict`) answer a sentence that says so. A message or Try Again on a `withdrawn` Work Item answers "Ploeg restarts a withdrawn Work Item only when its task is assigned to the team again." and calls nothing.
- **A note for the next Round.** On a `leased` or `queued` Work Item, a `chat/turnStarted` or `chat/pendingMessageSet` from the person calls Ploeg's `POST /api/v1/operator/work-items/{id}/notes` ([Ploeg ADR-0068](../../../ploeg/docs/adrs/0068-context-added-while-a-shift-runs-reaches-the-next-run.md)) with `{commandId, text, expectedShiftId}`, without asking first. `expectedShiftId` is the Shift the person's projection shows open, left out when none is, as for queued work. Ploeg briefs the Work Item's next Run with the note; the running Run never sees it. Once Ploeg stored it, the message's turn (for a pending message, a turn of its own) completes with "Saved for the next Round. The running agent won't see it until then." and stays in the person's chat. A note Ploeg did not store is rejected with a sentence: `shift_changed` "#n started a new attempt since you looked; your note was not saved. Look again and send it if you still want to.", `work_item_terminal` "#n is no longer running, so your note was not saved. Look again to see where it stands.", `operator_owned`, `command_conflict` and a missing Work Item each with their own, and an outage with "Ploeg could not be reached, so your note was not saved. Send it again to retry." A Ploeg without the notes route answers 404 without an operator error, or 405; the message is then rejected with "Ploeg can't take instructions for running work yet. Stop it, or wait until it needs you." and this process does not call the route again until it restarts.

Every command is sent as the person (`X-Ploeg-Actor` and `X-Ploeg-Acting-User` are their Unfold id). Before the call the host records the command, with a new `commandId`, under `work-item-command:<user>:<workItemId>`; it forgets the record once Ploeg answered with a result, a 4xx or a missing route, and a retry of the same command after an outage reuses its `commandId`. A requeue, a note and a guarded cancel send the `commandId`, so Ploeg replays its first answer to a retry; Ploeg's approve and reject endpoints take no `commandId`, so for them the record is Unfold's own and Ploeg's state checks make a repeat harmless. After a command changed the Work Item, the host reads it again at once, so its list entry and transcript change before the next poll.

A refused chat action still gets its `rejectionReason`, and the host also shows the reason in the chat, to the person's own clients only, because VS Code 1.142 drops `rejectionReason` for chat actions ([`src/ahp/refusals.ts`](../../src/ahp/refusals.ts)). This holds for Work Item sessions and Unfold sessions alike. A refused `chat/turnStarted` becomes a finished turn under the client's turn id, with the person's message and the reason as its Markdown reply, so the request VS Code waits on ends. A refused `chat/pendingMessageSet`, `chat/turnCancelled`, `chat/inputCompleted` or `chat/toolCallConfirmed` adds the reason as a Markdown part of the turn still open, which keeps running. When no turn is open it becomes a finished turn of its own: the queued message, or a system notice (**Stop**, **Your answer**, **Your approval**), with the reason as its reply. A refused `chat/turnResume` keeps only its `rejectionReason`, which VS Code reports as the failed request it tried to resume. Refusals of history and queue bookkeeping (`chat/truncated`, `chat/pendingMessageRemoved`), of session-channel, changeset, annotation, terminal, automation and root actions, and on a Run's read-only chat beyond a message are not shown in the chat: the client rolls back to the host's state, which is what the person sees. These replies are not kept, so a new snapshot leaves them out.

Each command a Team runs is a read-only terminal, `ahp-terminal:/<session id>/<event id>`, named after the `tool` event that first carried the command line ([ADR 0012](../adrs/0012-agent-host-protocol-host.md#update-2026-10-10-read-only-terminals)). A `tool` event names a command with a `command` field, as the demo runtime and command bridges may set it. A shell tool such as OpenCode's `bash` names it with the `command` in its input. The command's tool call gets `toolInput` with the command line, and `chat/toolCallContentChanged` adds `{type: "terminal", resource, title, isPty: false}`. Its completed result repeats that block with `result: {exitCode?, preview, truncated}`. `exitCode` is present only when the runtime reported one, and `preview` is the recorded output. Subscribing to the terminal returns a `TerminalState` with one `command` part, a `session` claim in the client's own spelling, `supportsCommandDetection: true` and `isPty: false`. While the command runs, each `tool.output` event (`{partId, offset, data}`, with the Run's `runId`) adds its output as a `terminal/data` increment: in offset order, without what a subscriber already has, a gap marked as `… N characters of output not kept …`, and only whole lines until the command ends or a line passes 4,096 characters. A command keeps at most 64,000 characters for a snapshot, and its result `preview` is the last 4,000. No runtime emits `tool.output` yet ([RFC-0006](../../../../docs/design/rfc-0006-live-command-output.md)). When the command finishes, subscribers receive `terminal/data` with output not yet sent, `terminal/commandFinished` and `terminal/exited`. A command whose Run or session stopped before it reported exits without an exit code. Command lines, titles and output are served with the event store's redaction, the API's known-secret redaction and the credential patterns applied, and with control characters other than newline and tab removed. Only the session's owner and administrators can subscribe; anyone else gets `-32008` `Terminal not found`. Every client action on a terminal is rejected with a `rejectionReason`, and `createTerminal` and `disposeTerminal` on a Team command's terminal answer `-32009`. VS Code also asks for a terminal of its own each time it shows one of this host's sessions. `createTerminal` on a channel outside `ahp-terminal:` is accepted, at most 16 per connection: it starts no shell, and subscribing returns a running terminal claimed by that client whose only content is a notice that Teams run their commands in sandboxes and each command appears on its tool call. Every action on it is rejected, only its own connection can read it, and `disposeTerminal` removes it. A tool call opened by a `pending` tool event stays streaming until the next event, so its command line arrives with `chat/toolCallReady`. A `failed` tool event completes the tool call as unsuccessful, as `error` does.

A session's `customizations` list the MCP servers its agent is configured with, read-only, and nothing else the host loads. A repository with `mcp` (the gateway's team and access groups) gives an OpenCode session one top-level server: `{type: 'mcpServer', id, uri, name: 'litellm', state, _meta}`, whose `id` and `uri` are both `mcp-top-level:unfold:<id>:litellm`, with `_meta['agentHost.mcpServerSource']: 'managed'`, `_meta['vscode.mcpServerDisplayName']: 'Gateway tools (<access groups>)'` and `_meta['dev.webgrip.unfold']: {source, repository, team, accessGroups, keyScope, clientControl: false}`. Its state is `starting` before the session runs, `ready` while it runs and `stopped` after it. A session Ploeg executes gets `error` with `errorType: 'gateway_key_unscoped'` until it ends. The entry never carries the gateway address, a header, a key or an `mcp://` channel. A tool call whose name starts with `litellm_` names the server as its `contributor`. `session/customizationToggled` and `session/mcpServer{Start,Stop,Background}Requested` are rejected. A plugin an active client publishes in `activeClient.customizations` is listed as `{type: 'plugin', …, clientId, load: {kind: 'error', message}, children: []}` and is never read. `session/customizationsChanged` announces each change. A `root/configChanged` whose `config.customizations` is not empty is rejected, which is what VS Code's **Add Remote Plugin** sends ([ADR 0012](../adrs/0012-agent-host-protocol-host.md#update-2026-10-10-mcp-servers-and-plugins)).

A message is never a dead end in the Agents window. Only a completed session's chat whose candidate no longer waits for review and that has no Work Item to ask about is `read-only`; every other chat takes a message, and the host sets no `vscode.chatInputState` block. A message either steers the Team or asks about the work ([below](#asking-from-the-agents-window)).

- **Running, queued or paused.** The message is an instruction for the next execution, as `POST /api/sessions/:id/messages` records it. Its turn keeps the client's turn id and is echoed with the client's origin, then a `systemNotification` says who reads it: "Queued for the <Role>'s next step", with what to do when that Role is not the one working now. When the next Run starts, a second `systemNotification` reads "Picked up by <Role> at HH:MM UTC".
- **Stranded, failed or cancelled.** A message no Team will read is an Ask when the session has a Work Item ([below](#asking-from-the-agents-window)). With `/steer`, in a session without a Work Item, or when no Ask can be made, it becomes a choice. The turn is accepted, a Markdown part says why no Team reads it, and an input request asks one single-select question: **Run again and start**, **Run again with this message**, **Deliver the approved work first** (only when the recovery answer lists delivery as available), **Ask instead** (only when the session can ask and asking has not just failed) and **Cancel**. The options come from `GET /api/sessions/:id/recovery` under the same owner check. Running again calls the run-again path, which keeps the brief, Team, repository, placement and budget, and records the message on the new session as its instruction; the new session is announced with `root/sessionAdded` and starts only on **Run again and start**. Delivering calls the deliver path and the turn ends with the outcome. **Cancel**, skipping the question or stopping the turn changes nothing. A newer message replaces a choice still open.
- **Failed, with Try Again.** A failed session's turn ends with an `error` part as its last part, with `resumable: true` when the run-again path accepts the session (it failed and was not imported from a tracker). VS Code shows **Try Again** under it. Pressing it dispatches `chat/turnResume` for that turn; the host echoes it with the client's origin, calls the run-again path under the same owner check (viewers are refused), announces the new session with `root/sessionAdded`, records `chat.turn_resumed` with the new session's id, adds a Markdown part saying what it created and that nothing runs until it is started, and completes the turn. The new session is `queued`; a message into it or **Start** on its session page starts it. A `chat/turnResume` for any turn but the last failed one is refused with a reason. Nothing is tried again unless a person presses it, and such a session gets no "What next?" turn, which would hide the button. A message typed into it becomes the message choice above in a turn of its own; after that the failed turn is no longer the last, so Try Again is refused and the choice carries the same Run-again path.
- **After it stops by itself.** An interrupted session's outcome says why it stopped and leaves the next steps to the choice that follows. An interrupted session's chat, or a failed one without Try Again, gets one host turn, "What next?", with the next steps the recovery answer lists as available (**Deliver the approved work**, **Resume**, **Run again and start**, **Run again, start later**, **Leave it for now**) and links to the pull request and the session page. It is offered once per stop and does nothing until answered.

A Team's question with exactly the options yes and no (in any case, without descriptions, one answer) is a `single-select` question with the options **Yes** and **No** in the Team's order, each with the id of the Team's own option, so the answer reaches the Team as the option's own label. It is never the `boolean` kind, which VS Code 1.141 shows as True and False; a `boolean` answer is refused. Every other question is `single-select`, `multi-select` or `text`. Declining a question, with `response: "decline"` or with VS Code's `cancel` from skipping or closing the questions, records `question.declined` and answers each question with "Declined by <name>: no answer will be given. Continue with your best judgement and say what you assumed."; the chat completes the request with `response: "decline"` and each answer `skipped` with that text. While the person is stopping the turn a `cancel` is refused instead, and the question stays open ([ADR 0012](../adrs/0012-agent-host-protocol-host.md)).

Spend appears as a `systemNotification` in the active turn: at the end of each Run, "Spent US$ 1,20 of US$ 8,00", unless the chat already said that same figure, and once each time the spend crosses 50, 80 or 100 % of the budget, with that share added. The figure is the settled spend, or the gateway's observed spend marked "observed, not settled"; before any is reported it reads "Spend not reported yet", and a demo reads "Demo · no model calls or spend" and never crosses a threshold. A raised budget starts the thresholds again. `chat/usage` carries tokens and their source only, no cost.

The host records a choice as session events: `choice.offered` with the options, `choice.answered` with the option and the reply, and `choice.reported` when carrying out an answer failed. They survive a restart, and an answered choice cannot be answered again. An option the host did not offer is refused.

Each Role's Run is a subagent of the session's chat, as VS Code renders one for its own hosts ([`runs.ts`](../../src/ahp/runs.ts)). `run.started` adds a running tool call `unfold_run` to the active turn, with `_meta.toolKind: "subagent"` and a `subagent` content block that names the Run's chat, `ahp-chat://subagent/<the session URI in unpadded base64url>/run-<run id>`, and `session/chatAdded` lists that chat with `origin: {kind: "tool", chat, toolCallId}` and `interactivity: "read-only"`. A Run that starts again after a stop gets `run-<run id>-<attempt>`. The Run's chat holds one turn: the Role's brief as the message, then the Run's own messages and its tool calls. `run.finished` completes the tool call with the Run's verdict and summary; a stop of the session completes it as not finished. Every action on a Run's chat is refused. A Run still working when a new turn opens is carried into that turn under the same tool call id.

A tool event is a tool call with its command line as `toolInput` when it is a command, whose output is then its read-only terminal, and otherwise with the event's `input` as `toolInput` and its `output` as text; its error and exit code are part of the result, and a `failed` or `error` status fails it. Input and output pass through the same redaction as terminals. Only what the runtime reported appears. A Run's tool events go to the Run's chat; one without a working Run stays in the session's chat. After a write Run, its native file diff appears in its chat as `unfold_changes`, one `fileEdit` per file with both sides read through `resourceRead`, when the session has only that write Run or the artifact carries the Role's name. `candidate.ready` adds `unfold_candidate` to the active turn with the candidate's files as `fileEdit`s, read from its Git bundle. A read Run's chat and a session without a write Run carry no file edits, and no reported tool call asks for confirmation or offers its input for editing.

### Asking from the Agents window

A session Ploeg executes has a Work Item, and its chat can ask about it without reaching its Team ([ADR 0012](../adrs/0012-agent-host-protocol-host.md#update-2026-10-10-mcp-servers-and-plugins), system [ADR-0031](../../../../docs/adr/adr-0031-people-ask-about-a-work-item-through-a-metered-read-only-ask-paid-from-a-monthly-allowance.md)). When the workbench has an Ask service, `initialize` answers `completionTriggerCharacters: ["/"]`, and `completions` with `kind: "userMessage"` answers a `/` typed at the start of a message with `/ask` and, where a message is already an Ask, `/steer`. Each item replaces the typed range with `/ask ` or `/steer `, and its attachment is `{type: "simple", label, _meta: {command, description, argumentHint}}`, which VS Code 1.141 shows as a command chip. Any other completion request answers no items.

A message that starts with `/ask` or `/steer`, typed or picked, says what it is. Otherwise a message into a stranded, failed, cancelled, held or completed session is an Ask, and one into a running, queued or paused session steers, as before. `/steer` in a running session is an ordinary message. An Ask goes through the same Ask service as `POST /api/ploeg/work-items/:id/asks`: a standing question is answered from the record, and any other is admitted and metered by Ploeg against the Team's Ask Allowance and answered with one model call. No Team reads it, and nothing is added to the session's events.

The answer is a Markdown part that starts with `**Ask** · not sent to the team` and ends with its spend: the cost with "(not final yet)" until Ploeg settles it, or "cost not final yet" before Ploeg reports one, and the allowance left this month with its reset day; "Answered from the record · no model call"; or, in the demo, "Demo · … nothing spent". An allowance that is used up answers "Not answered. Ask Allowance used up. It resets on <day>." with "Nothing was charged." A typed message's Ask is its own turn, echoed with the client's turn id once the answer is known. One sent as a pending steering message while a turn is open sits in that turn with the question quoted, and the pending message is removed once it is there. An Ask replaces an open "What next?" choice, which the host offers again after the answer. **Ask instead** in the message choice answers in that choice's turn.

When no Ask can be made (no Ploeg or gateway, a Work Item the person cannot see, or a session without a Work Item), the message becomes a choice that says why and sends nothing until the person picks: the message choice above in a stopped session, or **Send it to the team** and **Cancel** in one whose Team still reads messages. For each session the host keeps which Ask follows which event and the allowance read right after it, and renders the Ask again from the Ask store after a reconnect, an eviction or a restart.

### Chatting with Unfold

Proposed ([ADR 0049](../adrs/0049-the-agents-window-has-an-unfold-chat-that-reads-and-acts-on-confirm.md)); it needs a Ploeg that serves the chat routes of Ploeg ADR-0115, which is not released yet. When the workbench has a chat service, the root state lists a second agent after `unfold`: `{provider: "unfold-chat", displayName: "Unfold", models: [{id: "unfold-chat", name: "Your Team's Ask model"}], protectedResources: []}`; the demo names its model `Demo · no model calls`.

- **Sessions.** `createSession` with `provider: "unfold-chat"`, or a channel `unfold-chat:/<id>`, creates a chat that waits for its first message, as an Unfold session does; nothing is admitted or spent until then. A chat is `unfold-chat:/<id>` for a VS Code 1.141 window and `ahp-session:/<id>` for a client that declares `vscode.ahpSessionUris`; both spellings are accepted on input. It has one chat, `ahp-chat://default/<base64url of the session URI>`, and no changesets or customizations. `listSessions` lists the person's chats with `provider: "unfold-chat"`, the first message (cut at 80 characters) as the title, and `_meta["dev.webgrip.unfold"] = {kind: "chat", team}`. Only the person who started a chat sees it or acts on it; anyone else gets `-32001`.
- **Configuration.** `resolveSessionConfig` and `sessionConfigCompletions` with `provider: "unfold-chat"` answer a schema with `team`, an enum of the Ploeg Teams the person may use, each described with what is left of its chat allowance and its reset day, and `title`. `team` is `sessionMutable`: `session/configChanged` changes the Team that pays from the next message on. A Team outside the person's scope is refused.
- **A message.** `chat/turnStarted` with a message of 1 to 4,000 characters is echoed with the client's turn id and answered; there is no brief threshold. A message while an answer is still being written, a pending message, `chat/turnResume` and `chat/truncated` are refused with a reason shown in the chat. Viewers are refused, because each message spends. Each message is one Ploeg admission (`POST /api/v1/operator/teams/{team}/chats` with `{chatId, message}`, `X-Ploeg-Acting-User` the person); the turn's model calls go to the gateway's `chat/completions` with the returned key and its first model, and the turn finishes the chat in Ploeg (`POST …/chats/{chat}/finish`) however it ends. A replay that returns `credential: null` is admitted again under a new chat id. The model reads the last ten answered turns.
- **Tools.** The model's tools are the `unfold-mcp` tools except `unfold_ask`, run as the person. A read-only tool sends `chat/toolCallStart`, `chat/toolCallReady` with `confirmed: "not-needed"` and `chat/toolCallComplete` with the tool's summary as `pastTenseMessage` and its output as text content. A tool with `readOnly: false` sends `chat/toolCallReady` with `confirmationTitle` and `options: [{id: "allow", kind: "approve"}, {id: "deny", kind: "deny"}]`; the title is the tool's own planned message, which states the effect and any cost, or for `unfold_link_session` its title, input and description. The session's `inputNeeded` holds a `toolConfirmation` request, and the session and chat show input needed. `chat/toolCallConfirmed` is echoed; an allowed tool runs and completes, a denied one is cancelled with `reason: "denied"` and never runs, and the model reads that it was declined. No answer in five minutes counts as denied. A turn takes at most eight tool-call rounds.
- **The end of a turn.** An answer ends with a Markdown line naming the Team and what is left of its chat allowance, then `chat/turnComplete`. A failure ends with `chat/error`: a used-up allowance (Ploeg's 402) says when it resets, and nothing is asked. `chat/turnCancelled` (Stop) aborts the model call, counts an open confirmation as denied and finishes the key. The chat's `activity` is `Answering`, `Waiting for your confirmation`, or what is left of the Team's chat allowance.
- **History.** Unfold stores each turn's message and response parts (Markdown, tool calls with their confirmation and result, errors), so a snapshot after a reconnect or a restart shows the conversation. A turn a restart interrupted becomes an error, and its Ploeg chat is finished. Read and archive marks, `session/titleChanged` and `disposeSession`, which deletes the chat and its history, work as on other sessions.
- **Demo.** The demo answers every message with a fixed reply that says it is a demo, with no admission and no model call.

### Reviewing a candidate from VS Code

A completed session whose candidate waits for review (no review recorded, and no delivery policy that hands the review to the forge) offers three `changeset` operations: **Accept**, **Request changes…** and **Reject…**. A session under a delivery policy instead offers one operation, `accept-and-open-pull-request` (**Accept and open pull request**), once the workbench has a publisher, its local record shows the current candidate's passing receipt under the registered policy, and no pull request is published yet. Invoking it reads the candidate and receipt Ploeg holds and calls the publish route with them, under the same owner check; it answers with the pull request number and link, and the operation list empties once the pull request is published. A receipt that did not pass offers nothing. A session imported from a tracker offers no Request changes, because running it again means importing the task again. Accept records `accepted` at once. Reject and Request changes take a message, which a changeset operation cannot carry, so invoking one opens a host choice in the session's chat with one `text` question and answers with where to find it; nothing is recorded until the question is answered. A second invocation while the question is open points at it. Skipping the question or stopping the turn records nothing.

- **Reject** requires the reason and records `rejected` with it as the note, through the engine's review path and owner check, as `POST /api/sessions/:id/review` does.
- **Request changes** records `rejected` with the person's message as the note, then creates the next session with the same brief, repository, Team, placement, approval, model and budget and `previousSessionId` set, as run again does, and records one operator instruction on it: the message and every open comment on the candidate, each with its file and one-based lines. The new session is announced with `root/sessionAdded` and waits for an explicit start. With comments, the message is optional and the note says how many comments there were.

Comments are AHP annotations. The host serves each session's annotations channel, `<session URI>/annotations` in either spelling, to the people who may see the session; it accepts the five `annotations/*` actions under AHP's reducer, with at most 500 annotations of at most 50 entries of 8,000 characters, keeps them with the session and echoes them to that person's other clients. The session state carries an `annotations` summary once there is one. VS Code 1.141 sends a person's submitted feedback as a `chat/turnStarted` whose text is `/act-on-feedback` and whose attachments carry the comments (`type: "annotations"`, or `simple` with `_meta.agentFeedback.feedbackItems`). On a candidate waiting for review, that turn is accepted and opens Request changes with those comments. While a Team can still read it, the turn becomes an instruction listing each comment with its file and lines. A typed message on a candidate waiting for review is refused with a pointer to the review operations.

VS Code's Agent Merge (`session/configChanged` with only `config.agentMerge`) never accepts or publishes (owner decision, 2026-10-11): enabling it is refused with the operation to use instead, Accept, or Accept and open pull request under a delivery policy, both in the Changes view. Once a candidate is accepted or its pull request published, the session's configuration reads `agentMerge: {enabled: true}`, and disabling it is refused because a review is recorded once. Nothing is merged from the editor. VS Code 1.141 hides Agent Merge unless `chat.agentMerge.enabled` is set, which defaults to off on Stable. A session's `_meta.git` names the candidate's `branchName` and the repository's `baseBranchName`; once a gated candidate is being published, `branchName` is the publication branch, and `pullRequest: {number, url}` is added when the pull request is verified; VS Code 1.141's `sessions.agentHost.showBranchChanges` is a button on the new-session branch picker for a local checkout, so it has no Unfold session to act on.

## Workspace relay

Routes under `/api/relay/` are for sandbox workers, authenticated by per-workspace or pool bearer tokens rather than login cookies, and are not part of the operator contract.

A refused worker poll answers `401` with `error.code` `revoked` only when its token matches the workspace's revoked credential, which tells that worker to stop at once, and `unauthorized` otherwise, whether or not the workspace exists, which a worker retries for `UNFOLD_RELAY_REFUSAL_GRACE_MS` (default 120000) before it stops. A worker's upload of a relayed response is exempt from the 15-second request-body limit every other request keeps, and is cut instead when no data arrives for 60 seconds; one that ends before its body is complete is logged as `relay.response_interrupted` with the session, the relayed method and path.

Candidate access uses the same owner/administrator checks as the session. A successful export preserves a reviewable change; it does not certify independent verification, authorize publication or merge anything. Availability and limitations are explicit in the metadata. Native harness history and credentials are not portable candidate contents.

## Ploeg workbench

### Descriptions

Every Work Item in the overview lanes, the work-item pages, the detail and the proposed list carries `descriptionMarkdown` beside the untouched `description`. For a Vikunja item whose description looks like HTML it is that HTML converted to the Markdown subset the browser's renderer reads, with relative links resolved against the item's `url`. For every other item it equals `description`. Render it with the escape-first renderer; never insert `description` as HTML. [`rich-text.ts`](../../src/rich-text.ts) and [`markdown.ts`](../../src/markdown.ts) implement it.

### Now

`GET /api/ploeg/now` answers `{demo, teams, waiting, active, running, recent, runningTruncated, recentTruncated, truncatedStates, errors, fetchedAt}`. `running` and `recent` are Run rows, the same shape as `/api/ploeg/runs`: the first page of each. `runningTruncated` and `recentTruncated` are true when Ploeg holds more Runs than that page. Unfold reads every page of each team's `awaiting_review`, `needs_human`, `leased` and `queued` Work Items up to 200 per team and state, and `proposed` through the proposed list (its first page per team, at most 50). `truncatedStates` names each of those states for which Ploeg holds more than the response lists; it is empty when every list is complete. A group that fails is empty and names its failure in `errors.waiting`, `errors.active`, `errors.running` or `errors.recent`; the other groups still answer. A `needs_human` row among the first ten carries `question: {id, text, typed, role, round, runId}` when it waits on a person: a question Ploeg marks `waitingForPerson` (with its `id`), or, from an older ploegd, the stuck reason standing in for one (`id` empty) ([ADR 0050](../adrs/0050-people-write-on-the-blackboard-and-unfold-shows-questions-disagreements-and-finding-answers.md)). A waiting row carries `disagreement: {round, acting, shadow}` from Ploeg's `reviewDisagreements` for the needs-you rows Unfold read, and otherwise when, among the Runs listed in `running` and `recent`, a shadow reviewer gave another verdict than the acting reviewer. Run rows and Work Item Runs carry `shadow: true` for a shadow reviewer's Run.

`waiting` lists `awaiting_review`, then `needs_human`, then `proposed` Work Items, oldest first within each. `active` lists `leased`, then `queued` Work Items the same way, so a client can show that Ploeg holds a task it handed over before that task waits on anyone. Rows in both lists carry no description. Their fields:

| Field | Meaning |
| --- | --- |
| `id`, `team`, `state`, `title`, `url`, `createdAt`, `updatedAt` | As on the Work Item |
| `provider`, `externalId`, `priority` | The tracker, the tracker's id, and the tracker's priority. Unfold never re-ranks |
| `attempts` | Run claims so far, reader and writer alike. It is not "N of 3" |
| `infraFailures` | Infrastructure failures counted on the legacy lease path |

| `spentUsd` | The latest Shift's spend, or `null` when unknown |

Absent when Ploeg sends no field. `mergeState` is `clean`, `conflicted`, `unknown`, or `null` when Ploeg reported none ([Ploeg ADR-0040](../../../ploeg/docs/adrs/0040-a-conflicted-pull-request-becomes-a-priority-ticket-ploeg-resolves.md)) |

### Cancel

Cancel is for operators and administrators; viewers get 403. Live, Unfold asks Ploeg to cancel the Work Item as the signed-in person and answers `{workItemId, team, state, demo: false, withdrawn, shiftId, cancelledRuns, stoppedRuns, keysBlocked, message}` with Ploeg's own figures:

* `withdrawn: false` means nothing was live, and `state` keeps the Work Item's state.
* `keysBlocked: false` means Ploeg could not yet confirm that the stopped Runs' model keys are blocked; its sweep retries.
* A field that Ploeg leaves out or sends malformed is `null`, meaning unknown, never `0` or `false`. `message` is `""` unless Ploeg sends one.
* A Work Item that a workbench session drives answers 409 `ploeg_decision_conflict`: cancel that session instead.

In the demo, cancel answers 200 and changes nothing: `withdrawn: false`, `cancelledRuns: 0`, `stoppedRuns: 0`, `keysBlocked: null` and a `message` that says no Run was stopped, no model key or push token was blocked and the tracker was not told.

What Ploeg does on cancel is [journey D](../../../../docs/concepts/journeys.md#d-stopping-work).

## Card collection

The binder, packs and season pages ([ADR 0029](../adrs/0029-binders-packs-and-pulls-collect-run-cards-privately-and-fairly.md), proposed; [`collection.ts`](../../src/collection.ts)). Each route needs a login cookie, and writes pass the request-header and origin checks above. Every route reads and writes the signed-in person's own records only; none takes another person's id, so an administrator reads only their own binder and packs. Cards are assembled from Ploeg's facts list (`GET /api/v1/operator/facts?member=`, paged by `nextBefore`, up to six pages), and only cards in the caller's Teams pass. Without Ploeg's delivery facts these routes answer 503 `cards_facts_unavailable`. Errors use the codes below, or Ploeg's (`ploeg_scope` 403 for a person with no Team).

| Method and path | Request and response |
| --- | --- |
| `GET /api/me/card-identity` | `{logins, mapped, declared, verified, source, updatedAt}`. `mapped` is the forge login an administrator mapped to the person in `ploeg.forgeLogins` (the demo login `demo-operator` in the demo), and the only `verified` one: only it can make the person a card's steward. `declared` are the person's own logins, which only find cards to collect and never attribute anything. `logins` is both, mapped first. `source` is `mapped`, `setting`, `demo` or `none` |
| `PUT /api/me/card-identity` | `{logins}`, the declared logins, at most 10, each one word of letters, digits and `. _ @ + : -`; folded to lower case and deduplicated → the same shape. Anything else is 400 `card_logins` |
| `GET /api/binder` | `{demo, identity, source, now, startedAt, seenAt, copies, readouts, away, awayTotal, seenUntil, filters}`. `copies` is newest moment first, each `{card, copy: {role, roles, steward, pull, waitingIn}, lastActivityAt}`; `steward` is true only through the mapped login; `pull` is the stored first pull without its HMAC input, and `waitingIn` the unopened pack it waits in. `readouts` are personal: `cards`, `released`, `daysLive`, `daysLiveThisQuarter`, `quarter`, `mends`, `pulled`. `away` lists the moments since `seenAt`, oldest first, at most 12. `source` is `{kind: list | scan | demo, scanned, truncated}`; a live workbench answers `list` and no longer produces `scan` |
| `POST /api/binder/seen` | `{until, cards?}` → `{startedAt, seenAt}`. Creates the binder mark on the first visit and moves `seenAt` forward to `until`, never back and never past now. `cards` names up to 12 Work Items whose news the binder showed; each one's card seen mark (below), when it has one, moves forward to `until` too |
| `GET /api/cards/:id/seen` | `{workItemId, seenAt, snapshot, now}`: the person's seen mark on one card, for the effects director ([ADR 0032](../adrs/0032-an-effects-director-plays-run-card-moments-once-by-tier-within-accessibility-rules.md), proposed). `seenAt` and `snapshot` are null before their first look. The card must be in the caller's Teams (Ploeg's 404 `ploeg_not_found` otherwise); an id that is not a Work Item id is 400 `card_id` |
| `POST /api/cards/:id/seen` | `{until?, snapshot}` → the same shape. Moves `seenAt` forward to `until` (now when absent), never back and never past now, and stores `snapshot`, kept to `{grade: half-step 0–10 or null, setComplete: boolean}`. A person keeps marks for at most 2000 cards, dropping the least recently seen |
| `GET /api/cards/:id/world` | `{workItemId, demo, holds, role, world, updatedAt, facts, now, reason?}`: the person's decoration of one card's inner world ([ADR 0033](../adrs/0033-a-forge-card-s-art-window-is-an-inner-world-its-holder-may-decorate-privately.md), proposed). `holds` says whether they hold a copy and so may decorate it; `world` is their saved decoration as the card can show it now (`{v: 1, kind, tod, weather, objects: [{t, x, z, s}]}`), or null when they saved none or hold no copy, with `reason` saying why. `facts` is `{days, merged, condition}`, what unlocks the time of day and the things. The card must be in the caller's Teams (404 otherwise); an id that is not a Work Item id is 400 `card_id` |
| `PUT /api/cards/:id/world` | `{world}` → the same shape. Only a holder of a copy (403 `card_copy` for anyone else, administrators included). `world` must have only `v`, `kind` (`islands`, `deepsea`, `city`, `off`), `tod` (`auto` or a time of day the card has reached), `weather` (`clear`, `rain`, `snow`, `fireflies`) and `objects`: at most 24 `{t, x, z, s}` with `t` one of `crystal`, `lantern`, `tree`, `windmill` (card merged), `lighthouse` (180 days live), `koi` (crack mended), `x` from −4 to 4, `z` from −3 to 3 and `s` from 0 to 1. Anything else is 400 `card_world` with the reason. A person keeps at most 2000 decorations, dropping the least recently changed |
| `DELETE /api/cards/:id/world` | Forgets the person's decoration → the same shape with `world: null`. Only a holder of a copy |
| `GET /api/packs` | `{demo, identity, source, now, odds: {version}, packs}`, oldest first. Each pack is `{id, period, state: opened | sealed | filling, count, firsts, upgrades, openedAt, next, demo}`; only the one with `next: true` can be opened. Ids are `2026-W40` (ISO week, UTC) or `<team>~<sprint start>` |
| `POST /api/packs/:id/open` | `{}` → `{demo, odds, pack: {id, period, openedAt, demo, entries}}`; each entry is `{workItemId, kind: new | upgrade, moments, card, copy, pull}`. Draws and stores the first pull of every new card. 409 `pack_opened`, `pack_filling` or `pack_order` (open the older pack first); 404 `pack_not_found` |
| `GET /api/packs/:id` | An opened pack, the same shape; 404 for a pack this person has not opened |
| `GET /api/packs/odds` | `{version, scale: 10000, patterns, extras, altArtChoices}`: every probability in basis points |
| `GET /api/season?team=&quarter=` | `{demo, team, teams, quarters, quarter, justStarted, aggregates, source}` for a Team in the caller's scope (404 `team_not_found` otherwise). `aggregates` holds Team totals only: `cards`, `shipped`, `daysLiveAdded`, `finishes`, `cracks`, `mends`, `rightFirstTime` (`{share, cards}` or null), `bounceReasons` (or null), `sets` (or null) and `medians`: `leadTimeSeconds`, `firstFeedbackSeconds`, `ciMinutes` and `flowEfficiency`, each `{value, cards}` over the quarter's shipped cards that know the figure, or null. No person is named. A quarter that has not started is 400 `quarter`; without `quarter`, the first week of a quarter shows the one before and names it in `justStarted` |

Pack settings live in the configuration file under `cards`: `backfillPeriods` (0 to 12; 1, or 4 in the demo) and `teams`, a sprint per Team as `{lengthDays: 7–42, anchor: "YYYY-MM-DD"}` in place of the ISO week. The Run card rules Unfold applies live beside them:

* `cards.rules`: repositories, boards, Teams, bots, and whether to compute flow figures and rarity.
* `cards.publishPullRequestComment`: whether Unfold publishes the card comment; off by default.

## Feature flags

Flags are flagd rules evaluated in Unfold for the signed-in person ([ADR 0043](../adrs/0043-feature-flags-are-flagd-rules-evaluated-in-process-behind-openfeature-s-interface.md)). The browser only ever receives values. Targeting rules stay on the server. Each evaluation's context is `{targetingKey, userId, role, teams, tenantId, mode, labs, labsOff}`, where `labs` and `labsOff` are the flags the person opted in to and out of.

| Method and path | Response |
| --- | --- |
| `GET /api/flags` | `{values, labs}`: `values` maps each browser-visible flag to its value for the caller; `labs` lists the flags the caller may opt in or out of, each `{key, title, description, kind, expires, value, variant, reason, choice}`, with `choice` `on`, `off` or `default` and `reason` an OpenFeature resolution reason. Every role may read it |
| `PUT /api/flags/:key/choice` | `{choice: "on" \| "off" \| "default"}` → the same shape as `GET /api/flags`. Stores or clears the caller's choice; 404 `flag_not_found` for a flag not offered in Labs, 400 `flag_choice` otherwise. Every role may choose |
| `GET /api/admin/flags` | Administrators only (403 otherwise): `{flags, audit, file}`. Each flag is `{key, metadata, rule, source, override, rollout, expired, evaluation, evaluations, settled, experiment}`: its registry metadata, its effective flagd rule, the layer that last changed it (`code`, `config`, `file`, `console` or `override`), the override `{variant, reason, by, at}` or null, the authored rollout or null, whether its removal date passed, its evaluation for the caller, its evaluation counts per variant since the process started, the one variant it served at least fifty times in a row or null, and for an experiment flag or one with more than two variants `{days, exposures, conversions}` from product events. The answer also carries `segments`, `providers` (`{name, ready, error}` in the order asked), `strategy` and `console`. `audit` is the newest 50 override changes `{flagKey, action, variant, reason, actor, at}`, `file` is `{file, error}`: the watched flag file and why its last change was rejected |
| `PUT /api/admin/flags/:key/override` | Administrators only: `{variant, reason}` forces `variant` for everyone and needs a reason of at most 300 characters; `{variant: null}` clears the override. Answers like `GET /api/admin/flags`. 404 `flag_not_found`, 400 `flag_variant` for a variant the flag lacks. Each change is appended to the audit trail |
| `PUT /api/admin/flags/:key/rollout` | Administrators only: `{rollout, reason}` stores an authored rollout `{state, defaultVariant, respectLabs, rules}` and applies it at once; `{rollout: null}` removes it. Each rule is `{id, audience, window?, serve}`. `audience` holds any of `segment`, `roles`, `teams`, `users`, `tenants` and `prerequisite {flag, variants}`, and `window` is `{start?, end?}` in ISO time. `serve` is `{kind: "variant", variant}`, `{kind: "split", weights, stickiness?}` with shares in basis points adding up to 10000, or `{kind: "ramp", variant, otherwise, from, to, start, end, stickiness?}`. `stickiness` is `targetingKey`, `tenantId` or `role`. Answers like `GET /api/admin/flags`; 400 `flag_rollout` names what is wrong, 409 `flag_console_off` when `flags.console` is false |
| `PUT /api/admin/flag-segments/:name` · `DELETE` | Administrators only: `{description, audience}` stores a segment (`roles`, `teams`, `users`, `tenants`); every rollout that uses it recompiles. `DELETE` answers 409 `flag_segment_in_use` while a rollout uses it |
| `GET /api/admin/flags/export` | Administrators only: `{flags}`, the flagd rules the authored rollouts compile to, with segments inlined |
| `POST /api/ofrep/v1/evaluate/flags` | OFREP 0.4.0 bulk evaluation for the signed-in person or editor: `{context}` → `{flags: [{key, value, reason, variant, metadata}]}` with an `ETag`; `If-None-Match` with that ETag answers 304. Only browser-visible flags are listed. The context's identity attributes (`targetingKey`, `userId`, `role`, `teams`, `tenantId`, `mode`, `labs`, `labsOff`, `flagVariants`) come from the session, and a client may add up to 32 scalar attributes of its own. Needs no `X-Unfold-Request` header |
| `POST /api/ofrep/v1/evaluate/flags/:key` | OFREP single evaluation: 200 `{key, value, reason, variant, metadata}`, 404 `{key, errorCode: "FLAG_NOT_FOUND"}` for a flag clients cannot see, 400 with `errorCode` when evaluation failed |

## Static files

The server answers `GET` for the browser workbench from its public directory ([`static.ts`](../../src/static.ts)): the page, the named top-level assets in `src/http.ts`, and any `/core/`, `/views/` or `/styles/` file whose name matches `[a-z0-9][a-z0-9-]*\.(js|css)`. Anything else is 404.

* Every response carries `Cache-Control: no-cache` and a strong `ETag`: 32 base64url characters of the file's SHA-256.
* `If-None-Match` with that tag, weakly compared, or `*`, answers 304 with no body. The 304 keeps the `ETag`, `Cache-Control`, `Vary` and every security header, the Content Security Policy included.
* HTML, CSS, JavaScript, SVG and the web manifest are gzipped when `Accept-Encoding` accepts `gzip` or `x-gzip` with a non-zero quality, and only when that is smaller. The gzipped variant's tag ends in `-gzip`. These types carry `Vary: Accept-Encoding`; fonts, images and plain text are never compressed.
* File bodies and their gzip are cached in memory by path, modification time and size, up to 512 files.
