# VS Code 1.140 against Glide: what each feature touches, and the three that matter

Research date: 2026-10-01. This dossier extends [the 0.9.0 survey](2026-09-10-agent-host-protocol.md) and [the 1.138 roadmap sweep](2026-09-17-agent-host-roadmap.md) to the [1.140 release](https://code.visualstudio.com/updates/v1_140) of 30 September 2026. Sources: the release notes and every page they link, the [specification](https://microsoft.github.io/agent-host-protocol/) and [repository](https://github.com/microsoft/agent-host-protocol) at commit `2265e2e` (2026-09-30, spec still 0.9.0), `microsoft/vscode` at tag 1.140.0 (`07f806f9`) and main `038fc2b` (2026-10-01), `github/copilot-sdk` v1.0.16, and the VS Code 1.140.0 stable bundle installed on the owner's Linux machine. Method: four research agents in parallel (documentation crawl, source dig, ecosystem and absence checks, a read-only sweep of this repository), then first-hand checks of the shipped bundle and of [`src/ahp/host.ts`](../../src/ahp/host.ts).

Evidence read first-hand from the shipped build is marked **(build)**; from VS Code's source only, **(source)**. Everything else carries its link.

Landing contract: no protocol-research contract block exists in `AGENTS.md`. The destinations follow [the BAND dossier](2026-09-18-band-and-the-interaction-layer.md): this dossier, a dated sentence on the AHP row of the [protocol ledger](2026-09-11-ecosystem-alternatives.md#appendix-adjacent-components-and-communication-protocols), a dated update to [ADR 0012](../adrs/0012-agent-host-protocol-host.md), and a re-confirmation on [Ploeg backlog item 101](../../../ploeg/docs/backlog.md).

## Verdict

1.140 changes nothing about Glide's architecture. It also shows that the bet in [ADR 0012](../adrs/0012-agent-host-protocol-host.md) has never been exercised. The release is about VS Code's own Agents window. Its harness picker is still closed to third parties, and connecting a remote host still works the same way.

VS Code completes the handshake with Vloer's host, but it cannot run a session on it. Fifteen conformance findings were read from VS Code's client source and checked against the shipped bundle. Two of them leak data between users. They are listed below under "Conformance findings against the 1.140 client".

Three further things touch Glide:

1. **Another conformance defect.** 1.140's archive and mark-as-done actions are rejected by Vloer's host.
2. **A cheap, useful link.** `vscode://agents/new?prompt=` can serve the "Finish the work by hand" step on a Work Item that needs you.
3. **A door that needs a lock first.** Remote-session delegation would let a VS Code agent create Glide work. The owner asked on 2026-10-01 to use as much of the shared surface as possible. Delegation is therefore planned, but only as a proposed Work Item that waits for a person (VIK-1669).

Everything else is orthogonal, or a design reference at most. The leverage plan, journeys and market fit are in [the companion record](../../../../docs/research/2026-10-01-vscode-surface-and-agency-fit.md).

## What 1.140 actually is

The release moves the **Copilot harness** onto the agent host, the separate process introduced in 1.129 that "owns agent sessions" and speaks AHP to its clients. A *harness* is VS Code's word for the runtime that "coordinates an agent session, including tool calls, context, and code changes" ([agent harnesses](https://code.visualstudio.com/docs/agents/run/agent-harnesses)). The Copilot harness is built on the [Copilot SDK](https://github.com/github/copilot-sdk) for "consistent agent behavior across Copilot products". Around it, 1.140 adds orchestration features for one person driving many sessions: peer chats inside a session, sessions spread across folders and machines, dev-container hosts that stop when idle, and a URL that opens a pre-filled draft.

The protocol did not move. AHP is still 0.9.0 (tagged 2026-08-28; `[Unreleased]` fragments run to 2026-09-29), still owned by `* @connor4312 @roblourens`, and still without a server SDK ([#422](https://github.com/microsoft/agent-host-protocol/issues/422)). The 1.0 blocker [#366](https://github.com/microsoft/agent-host-protocol/issues/366) is still open.

### The handshake still matches

**(build)** The 1.140.0 bundle defines `SUPPORTED_PROTOCOL_VERSIONS = ["0.9.0","0.8.0","0.7.0","0.6.0","0.5.2","0.5.1"]` in both `workbench.desktop.main.js` and `agentHostMain.js`, with current version `"0.9.0"`. **(source)** The client filters out `0.8.0` before offering, so the list on the wire matches 1.138's: `0.9.0, 0.7.0, 0.6.0, 0.5.2, 0.5.1` (`src/vs/platform/agentHost/browser/agentHostProtocolClient.ts`, `CLIENT_SUPPORTED_PROTOCOL_VERSIONS`). Vloer's `/^0\.9\.\d+$/` check in [`host.ts`](../../src/ahp/host.ts) therefore still accepts it. The single-minor defect recorded in ADR 0012 is unchanged and still latent: it breaks on the first VS Code release that drops 0.9.0.

### Conformance findings against the 1.140 client

These findings were read from VS Code main `038fc2b` (`agentHostProtocolClient.ts`, `baseAgentHostSessionsProvider.ts`, `agentHostSessionHandler.ts`, `sessionState.ts`, `agentSubscription.ts`), with key lines confirmed in the 1.140.0 bundle. C1, C5, C6 and C7 were also confirmed first-hand in [`host.ts`](../../src/ahp/host.ts). None of them has been run against a desktop client. The existing [`ahp.test.ts`](../../test/ahp.test.ts) tests the host against its own expectations, and one of them, the session rename on first turn, is itself the bug C3.

| # | Finding | Effect | Ticket |
| --- | --- | --- | --- |
| C1 | VS Code names sessions `<provider>:/<uuid>` and takes the provider from the URI scheme; the host accepts only `ahp-session:/…` | `createSession` fails | VIK-1662 |
| C2 | VS Code expects `defaultChat` at creation and never calls `createChat` for the first chat; its chat URI is `ahp-chat://<chatId>/<b64url(session)>` | "no default chat" | VIK-1662 |

| C6 | Root session notifications and `activeSessions` ignore ownership | Cross-user leak of titles, budget and spend | VIK-1661 |

### The seam, re-measured

- **Harness contribution is still closed.** **(source)** `agentHostMain.ts` registers exactly `CopilotAgent`, `ClaudeAgent` (behind its flag and an SDK check) and `CodexAgent`. The docs list Local, Copilot, Claude, Codex and Cloud, and no third-party harness type.
- **Host substitution is still open, and VS Code documents it now.** The [architecture blog](https://code.visualstudio.com/blogs/2026/08/26/agent-host-architecture) says "other applications can implement either side of the same agnostic protocol". **(source)** `chat.remoteAgentHosts` still takes `{address, name, connectionToken?}`. `parseRemoteAgentHostInput` accepts `host:port`, `ws://`, `wss://`, `http://` and `https://`, and lifts a `?tkn=` query into `connectionToken`. `chat.remoteAgentHostsEnabled` still defaults to true. The public docs still name only `chat.remoteAgentHostsEnabled` and never the address form.
- **VS Code now extends the protocol privately through `_meta`.** **(source)** A host can advertise `_meta["vscode.remoteSessions"]` (required for delegation), `_meta["vscode.agentHost.resources"]` (platform, CPU, memory) and `InitializeResult._meta["vscode.devContainers"]`. These are VS Code capabilities, absent from the AHP spec. They sit alongside the `vscode/`-prefixed methods the 1.138 sweep found.
- **How the first-party harnesses run.** **(source)** Claude runs as an in-process `import()` of `@anthropic-ai/claude-agent-sdk`, either through a local Copilot proxy or natively with your own `ANTHROPIC_API_KEY`. Codex runs as a `codex app-server` child speaking NDJSON JSON-RPC to a local proxy. **None of them uses ACP**, although the AHP guide draws "AHP north, ACP south" as the target architecture. The wrapped SDKs lag their upstreams ([vscode#337382](https://github.com/microsoft/vscode/issues/337382): Opus 5.5 is rejected by the bundled Claude Code).

## The layer map after 1.140

| Seam | Claimant in Glide | VS Code 1.140's claimant | Change |
| --- | --- | --- | --- |
| Client ↔ session sync | Vloer's AHP host | AHP 0.9.0 | None. Handshake verified **(build)**. |
| Host ↔ agent runtime | Ploeg's ACP adapter and its profiles | Private SDK adapters (Copilot SDK, Claude Agent SDK, `codex app-server`) | Diverged. VS Code wraps SDKs instead of using ACP. Ploeg is unaffected. |

## The one scenario where 1.140 could matter more

If Ploeg Work Items were projected as read-only AHP sessions (planned ticket PV-081), VS Code's Agents window would become a second "Needs you" inbox:

- `InputNeeded` would carry the attention badge.
- `IsRead` would track what you have seen.
- Mark-as-done and the completion-sorted Done list would map onto `IsArchived`.
- `vscode://agents/agent-host-session/<provider>/<sessionId>` **(source)** would let Vloer's browser page open the same Work Item in the editor.

Every one of those is a 1.138–1.140 feature, and none needs a VS Code change.

The tension is with the decision in [ADR 0023](../adrs/0023-vloer-submits-work-to-ploeg-and-never-executes-it.md) (proposed):

- Ploeg steers between Runs, not inside them. An AHP chat implies that a typed message reaches the running agent.
- Archiving in VS Code is not cancelling a Work Item. It is per viewer, while cancellation is Ploeg's decision.
- The projection would therefore have to refuse `chat/turnStarted` or record it as a proposed instruction for the next Round, and keep the archive bit local.

That scenario is worth building only after ADR 0023 is decided, because the decision sets what the host projects.

## Recommendations

1. **Accept `session/isArchivedChanged` and `chat/isArchivedChanged` in the host.** [`host.ts`](../../src/ahp/host.ts) broadcasts `session/isReadChanged` and rejects every other unknown action with "Unsupported action". 1.140's archive and mark-as-done send these two actions. The rejection makes the client's write-ahead state roll back, so a Vloer session cannot be filed as Done. This was found by reading the code; it has not been exercised against a desktop client. Broadcast the actions now, as `isReadChanged` already is. Persist them with the retention work in PV-048. Add both to [`ahp.test.ts`](../../test/ahp.test.ts).
2. **Keep the single-minor negotiation defect on the list, unchanged.** 1.140 still offers 0.9.0. The fix is still a declared set with highest-wins, as ADR 0012 records.
3. **Offer "Continue in VS Code" on a Work Item that needs you.** The Work Item page tells the person to "Finish the work by hand" and attaches no action. Add a button that opens `vscode://agents/new?prompt=<…>` with a prompt built from the brief, the repository, the base branch and the reason the work stopped. **(source)** Only `prompt` and `workspace` are accepted, and an empty prompt rejects the link. The prompt is placed in the composer and never submitted, and an occupied composer is left alone. Omit `workspace`, because Vloer cannot know a local folder path. The work then happens outside Glide, so the button must say that Glide does not budget or meter it. Ploeg's authority is untouched: nothing is dispatched.
4. **Verify the session deep link before linking it.** Test `vscode://agents/agent-host-session/de-vloer/<id>` against a desktop client attached through `vloer.connectAgentHost`. If it opens the session, add it beside the browser link. The parser takes no host identifier, so it may resolve only sessions VS Code already lists.
5. **Do not advertise `_meta["vscode.remoteSessions"]` until delegation creates only proposals (VIK-1669).** That flag makes Vloer's host a target for `create_remote_session`. Any VS Code agent could then create a Vloer session, and through it budgeted Glide work, from a prompt, with only VS Code's own confirmation dialog in the way. Glide's rule is that Ploeg authorizes every Run, and [ADR-0011](../../../../docs/adr/adr-0011-glide-is-reachable-over-mcp-through-a-read-first-server.md) says proposals never dispatch. Revisit when Ploeg has an authorized work-submission route (ADR 0023's `POST /api/v1/operator/work-items`) and the delegated session can be a proposal rather than a Run.
6. **When `ploeg-mcp` ships, document a user-level entry, not a repository `.mcp.json`.** The agent host reads `$COPILOT_HOME/mcp-config.json` (falling back to `~/.copilot/mcp-config.json`) and a workspace-root `.mcp.json`, both under `mcpServers`. Claude Code reads the same `.mcp.json`. The Copilot harness reaches only "local MCP servers that don't require authentication", which ADR-0011's phase 1 (stdio, token in the environment) satisfies. A committed `.mcp.json` would put a Glide entry in every checkout, including the ones Runs clone. Runs hash the file as an instruction file, and the [MCP access dossier](../../../../docs/research/2026-09-29-mcp-access.md) found ACP profiles that may load repository MCP configuration.
7. **Adopt nothing from the Copilot SDK.** If Copilot as a Ploeg harness is ever wanted, add it as an ACP profile ([acp-profiles](../../../ploeg/docs/contracts/acp-profiles.md)). Copilot CLI has shipped ACP since 2026-01-28, per the 1.138 sweep. Do that only once its BYOK routing to LiteLLM, with a per-Run key and metered spend, is verified.
8. **Adopt nothing from HydraFusion.** Record it as corroboration for the cross-family reviewer, not as a routing design.
9. **Align future OTel with the GenAI conventions, and keep editor telemetry personal.** When Ploeg backlog item 82 starts, name spans after `invoke_agent` and `execute_tool`, so a Run trace and the owner's own VS Code trace read the same way in Tempo. The `gen_ai.*` conventions are still in Development status. Pointing VS Code's `chat.agentHost.otel.otlpEndpoint` at the home collector is a personal setting, not repository work. Identity capture matters only in the agency phase, where it is personal data.
10. **Honour Ploeg ADR 0006's review on 2026-10-31 by re-confirming it.** 1.140 adds no evidence for Ploeg speaking AHP. Every new capability lands on the host side, which Vloer owns.

## Re-evaluation triggers

| Trigger | What flips |
| --- | --- |
| A VS Code stable release drops `0.9.0` from the offered list, or AHP tags 0.10.0 | Recommendation 2 becomes urgent: Vloer's host stops attaching. |
| `chat.remoteSessions.tools.enabled` defaults to true, or delegation reaches hosts without `_meta["vscode.remoteSessions"]` | Re-check recommendation 5. Vloer must reject `createSession` from a delegating agent explicitly. |
| ADR 0023 is accepted | Decide the AHP host's future, and PV-081's read-only Work Item projection with it. |
| A third-party harness type appears in the harness picker, or an extension API for agents lands ([vscode#325827](https://github.com/microsoft/vscode/issues/325827)) | Reopen the "harness seam is closed" verdict. A Glide harness could then appear inside VS Code. |
| `vscode://agents/new` gains `harness`, `branch` or `repository` parameters | Recommendation 3 can open a checkout of the stuck branch instead of a bare prompt. |
| The agent host adopts ACP south | Ploeg's ACP profiles and VS Code's harnesses converge, which is worth checking for shared profiles. |
| HydraFusion publishes its model pool and per-model usage, or accepts BYOK routing | Re-examine it against Ploeg ADR 0039. |
| `authIssuers` is finalized and the agency phase needs one extension signed in to several tenants | Move extension sign-in to an `AuthenticationProvider` that carries the tenant's issuer. |

## Absence checks

Confirmed zero mentions, in connection with the VS Code agent host, AHP or 1.140, of: **Ploeg**, **Vloer**, **Glide**, **LiteLLM**, **Forgejo**, **Vikunja**, **OpenHands** and **OpenBao**. **opencode** appears only as the unimplemented community plugin `maxious/opencode-plugin-agent-host-protocol`.

Cloud delegation is GitHub-only: "Copilot Cloud sessions are only supported for GitHub-backed repositories" ([Agents window](https://code.visualstudio.com/docs/copilot/agents-app)). No forge integration for Forgejo, Gitea or GitLab exists. Copilot's tracker integrations (Jira, Linear) feed the GitHub cloud agent, not the agent host. No shipped AHP artifact was found from JetBrains, Zed, OpenHands, official opencode, Anthropic, OpenAI or Cline; all of them ship ACP or nothing. The 2026-09-26 orchestration landscape's "AHP has zero adoption across the eleven tools verified" still holds for major tools. Small community hosts and clients exist: `Qusic/pi-ahp`, `softov/ahpd`, `Qusic/agent-console` and `softov/ahpc`.

## Method and limits

- Visual Studio Magazine returned 403, so its two articles were read from search snippets only.
- No HN or Reddit discussion specific to the agent host, the Agents window or HydraFusion was found.
- The HydraFusion model pool is undisclosed.
- No BYOK statement exists for the Copilot harness itself.
- The `isArchivedChanged` rejection and the session deep link come from reading code. Neither was exercised against a running desktop client.
- Bundle evidence comes from `/usr/share/code` at 1.140.0, commit `07f806f9`.
