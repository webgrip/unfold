# CI and release workflows

Unfold uses Webgrip's event-named entry points. The executable definitions live in the root [workflow directory](../../.forgejo/workflows/). Forgejo reads workflows only from the repository root, so the applications have no workflow directories of their own.

| Entry point | Trigger | Responsibility |
| --- | --- | --- |
| [on_source_change.yml](../../.forgejo/workflows/on_source_change.yml) | Push to `development` or `main`; manual validation | Validate Unfold, the pinned Ploeg, container build contexts and release policy, and check that the Ploeg pin is on Ploeg's `main`. An enabled push to `development` can then release Unfold and a site candidate; an enabled push to `main` releases only a stable site version. |
| [on_pull_request.yml](../../.forgejo/workflows/on_pull_request.yml) | Pull request; manual validation | Run the same application, Ploeg pin and release-policy jobs without release credentials or versioning jobs. |
| [on_schedule.yml](../../.forgejo/workflows/on_schedule.yml) | Weekly on Monday; manual rerun | Report broken external links in current docs with lychee, which blocks nothing. Smoke-test the [local demo](../workflows/local-demo.md). Fail when Forgejo no longer holds every imported release note (`scripts/verify-import.py` with `UNFOLD_REQUIRE_IMPORT_NOTES=true`), so a deletion like those of September 2026 is seen within a week even without pushes. It publishes nothing. |
| [on_dns_change.yml](../../.forgejo/workflows/on_dns_change.yml) | Push to `development` that changes `apps/site/ops/dns/`; daily at 05:45 UTC; manual | Preview the `unfoldhq.dev` DNS records, or fail on drift, with a read-only token fetched from OpenBao over OIDC. It never applies them. The [site deploy guide](../../apps/site/docs/deploy.md#dns) explains it. |
| [on_docs_change.yml](../../.forgejo/workflows/on_docs_change.yml) | Documentation or docs-tooling changes on `development`; manual validation | Validate the combined documentation, then publish Zensical and Markdown when the docs gate is enabled. |
| [on_release_preview.yml](../../.forgejo/workflows/on_release_preview.yml) | Manual, on `development` | Check the mirror, credential access and Unfold signing identity; preview the next Unfold version with `dry-run: 'true'`. |
| [on_release_published.yml](../../.forgejo/workflows/on_release_published.yml) | Published release; manual retry for an exact tag | Publish Unfold's artifacts for a `unfold-v…` tag. Ploeg's artifacts come from [github.com/ploeg-hq/ploeg](https://github.com/ploeg-hq/ploeg). |

## Shared checks and the Ploeg pin

`apps/ploeg` is a Git submodule pinned to a release of [github.com/ploeg-hq/ploeg](https://github.com/ploeg-hq/ploeg) ([ADR-0019](../adr/adr-0019-unfold-pins-ploeg-from-its-own-repository-and-releases-only-vloer.md)). Every checkout that verifies, builds the documentation or runs the demo initialises it, and `mise run setup` runs `git submodule update --init --recursive`. [The pin check](../../scripts/ploeg-pin.mjs) fails on vendored source, another repository, or an uninitialised or modified checkout. The `ploeg-pin` job runs it with `--published`, which also requires the pinned commit to be the commit of the release tag `.gitmodules` names (`branch = v0.x.y` or `v0.x.y-rc.N`), and the `release` job waits for it. A pull request that pins an unreleased Ploeg change therefore stays red until Ploeg publishes a release that contains it. Move the pin in a commit scoped `ploeg`, for example `build(ploeg): pin Ploeg v0.2.0-rc.1`; such a commit never releases Unfold.

Source changes and pull requests use the same local [verification action](../../.forgejo/actions/verify/action.yml) and [release-policy action](../../.forgejo/actions/release-policy/action.yml). Each caller checks out the repository before invoking a local action. A pull request runs the release-policy action as its own job. A push to `development` runs it as the first step of the `release` job, which uses the same container, so a push needs one runner pod fewer. The existing application gates remain in [mise verification](../../scripts/verify.mjs), including generated docs, Helm goldens and deterministic integration. The dedicated docs workflow gives documentation changes their own result; the source gate still validates the complete tree.

Verification runs independent gate groups in parallel: Unfold, the Unfold extension, the hosted demo replay, Ploeg, the site, Helm, release tests, integration and docs. The Ploeg group runs the pin check, Ploeg's own `scripts/verify.sh` at the pinned commit, and a build of the unified demo's Go helper against it. Gates inside a group stay sequential. Each gate's output is buffered and printed in group order with its result and duration, followed by a summary. The first failure cancels the running gates, skips the pending ones and names the failed gate. Each Ploeg database test package starts its embedded PostgreSQL on a port the operating system assigns, so checkouts can verify at the same time, and a server orphaned by a cancelled gate does not block the next run. The verification action restores the mise tool installs, the Go module and build caches, the npm download cache and the site's pnpm store, and sets `GOFLAGS=-count=1` so Go never reports a cached test result. The mise key is the hash of the `mise.toml` and `mise.lock` files. On a miss the action restores the nearest older entry, mise installs only the tools that changed, and the result is saved under the new key. The Go key adds the hash of Ploeg's Go sources to `go.sum`, so every source change saves a fresh build cache and the next run restores the nearest one, falling back to any Go version's cache after a toolchain bump; a key on `go.sum` alone hits exactly, skips the save, and leaves the build cache frozen at the last dependency change.

Verification also keeps a result cache of gates that passed, in `~/.cache/unfold-verify`. A gate's key hashes the committed Git trees of its group's inputs, the root, Unfold and site `mise.toml` files and both verify scripts, the tool versions mise resolves in each scope, the `GOFLAGS` and `UNFOLD_TEST_TIMEOUT_SCALE` settings, the gate's command and the platform. A gate whose inputs have uncommitted or untracked changes gets no key. The Unfold group reads `apps/unfold` and `docs`, the extension group `apps/unfold`, the Ploeg group the pinned commit at `apps/ploeg`, `.gitmodules`, the pin check and the unified demo helper, the site group `apps/site` plus Unfold's `public`, `src`, `examples`, recorder and `package.json`, because its build records the demo replay and copies `public` into `/demo`, and the Helm group `apps/unfold/ops/helm`. A submodule's tree in the superproject is its pinned commit, so the Ploeg gates rerun only when the pin moves. The release, integration and docs groups span the whole tree and always run. Every CI run records its passes. Only a pull request reuses them (`UNFOLD_VERIFY_REUSE`): a push to `development`, the release gate, runs every gate. An npm update in Unfold therefore skips the Ploeg gates in its pull request. Locally, set `UNFOLD_VERIFY_RESULTS` to a directory and `UNFOLD_VERIFY_REUSE=true` to get the same skips; without them, `mise run verify` runs everything. [The cache tests](../../scripts/verify-cache.test.mjs) state which changes keep a key and which change it. Markers unused for 14 days are removed.

`UNFOLD_VERIFY_CPUS` caps each gate's parallelism: it sets `GOMAXPROCS`, `go -p` and Unfold's `--test-concurrency`. Without it the tools start one worker per host core. A runner pod requests 250m CPU but sees every core of its node, so seven parallel groups each fanning out to all cores contend with each other and with the other runners on the node. CI sets 4, a starting value to tune against job duration. The Unfold test scripts also set `--test-timeout=120000` and `--test-force-exit`, so a test that never settles fails after two minutes instead of holding the runner until the job timeout.

## Warnings

Forgejo has no warning result for a job: a job either succeeds or fails. A warning printed by a passing step would otherwise stay buried in a green log. The verification action therefore saves the output of its three `mise install` steps, `mise run setup` and `mise run verify`, and its last step, which runs even after a failure, passes that output to [the warnings scanner](../../scripts/ci-warnings.mjs). The scanner recognizes the warning formats of npm, pnpm, mise, uv, Node, Python, Go, Actions annotations and build tools, so a test name or a JSON log line that contains the word "warn" is not reported. It reports each distinct warning once and writes the list to the `checks` job's `warnings` output. A separate `warnings` job prints that list and fails when it is not empty. The commit then shows a red `warnings` check while `checks`, `release` and publication carry on: no job waits for `warnings`. Fix the cause, or accept a warning in [the allowlist](../../scripts/ci-warnings-allow.json) with a pattern and the reason it is accepted. A pull request that reuses cached gate results does not print those gates' output, so a push to `development` is the complete check.

The root `mise.lock` is committed and written by mise 2026.9.17, the version CI pins. `min_version` in the root `mise.toml` refuses an older mise. Ploeg's `mise.lock` belongs to Ploeg's repository. When the two lockfiles disagree on openspec's install, every `mise install` replaces the copy the other one made and prints `mise WARN missing: npm:@fission-ai/openspec`. Regenerate the root lockfile with `mise lock`; fix Ploeg's upstream and move the pin. Renovate's runner has mise 2026.7.7, so it cannot relock a mise tool bump yet: commit `mise lock`'s result on its branch until the runner image carries a newer mise.

The weekly [demo smoke action](../../.forgejo/actions/tutorial-smoke/action.yml) runs [the tutorial smoke script](../../scripts/tutorial-smoke.sh): it starts `mise run demo-unified`, waits for `unified-demo.ready`, stops it with `SIGTERM`, then runs the documented `--smoke` check. It is deterministic, with no model calls or credentials. When the runner has no PostgreSQL `initdb` and `postgres`, or runs as root, the job logs what is missing and passes without starting the demo. The host-mode `ci-runner` has neither, so on every push and pull request the job only occupied a runner; it runs on the schedule instead, and no release job depends on it.

The Unfold version is the application's ([ADR-0019](../adr/adr-0019-unfold-pins-ploeg-from-its-own-repository-and-releases-only-vloer.md), which supersedes the joint version of [ADR-0004](../adr/adr-0004-unfold-releases-one-version.md)). Ploeg is versioned and published by [github.com/ploeg-hq/ploeg](https://github.com/ploeg-hq/ploeg). The pinned Webgrip semantic-release monorepo composite runs [the Unfold configuration](../../apps/.releaserc.cjs) with `package-path: apps`, so only commits that touch an application count. Moving the Ploeg pin touches `apps/ploeg`, so the configuration never releases a commit scoped `ploeg`. The [marketing site](../../apps/site/README.md) lives under `apps/` but is not part of the Unfold version ([ADR-0012](../adr/adr-0012-the-marketing-site-releases-and-deploys-on-its-own.md)): a commit scoped `site` never releases Unfold, and neither train reads the other's tags. Its own train, [apps/site/.releaserc.cjs](../../apps/site/.releaserc.cjs), cuts `unfold-site-v…` releases that deploy the site to Cloudflare; its `site-release` job runs after Unfold's `release` job, and a published `unfold-site-v…` release deploys the site through the shared `cloudflare-deploy` workflow, as the [site deploy guide](../../apps/site/docs/deploy.md) describes. Unfold's publication jobs accept only `unfold-v…` tags, so a site release publishes no image, chart or extension. Tags are `unfold-v<version>`, the notes go to `apps/CHANGELOG.md`, and [the prepare script](../../scripts/release-prepare.mjs) sets Unfold's chart, manifests and extension to the same version. The annotated tag `glide-v0.3.0` is the baseline where the last imported candidates met. Releases before the rename carry the old `glide-v` and `glide-site-v` names; when the product was renamed ([ADR-0013](../adr/adr-0013-the-product-is-named-unfold.md)), `unfold-v` and `unfold-site-v` baseline tags were placed on the same commits as the newest old tags, so the versions continue. Both source checks and release-policy checks must pass before versioning.

`UNFOLD_RELEASES_ENABLED` must equal `true` to version or publish. A manual source-validation run never releases, even with the gate enabled. Release-channel notes live on Forgejo only; nothing copies them to GitHub. CI runs the import verifier with `UNFOLD_REQUIRE_IMPORT_NOTES=true`, so missing notes fail the source gate instead of being skipped as they are locally. A [release test](../../scripts/test_release_refs.py) fails if any workflow, action, script or mise task prunes, mirrors or deletes refs, or pushes notes. The [notes-loss record](../research/2026-09-23-forgejo-notes-loss.md) explains why. Keep the `main` release baseline required by the shared preset; `development` remains trunk and the only automatic release branch. Use the [first cutover playbook](first-cutover.md) before enabling publication.

## Dependency updates

Renovate follows the org preset and its [automerge-non-major overlay](https://forgejo.webgrip.dev/webgrip/renovate-config/src/branch/main/automerge-non-major.json), with Unfold's own managers and exceptions in [renovate.json](../../renovate.json). Minor, patch, digest and pin updates need no dashboard approval. They land in one `all non-major dependencies` branch, and Renovate merges the pull request once its checks are green. Renovate reads the combined commit status itself, so a merge never depends on branch protection. Lock-file maintenance and vulnerability fixes also merge themselves. Unattended updates keep the preset's soak of three days for a minor and one day for a patch. `internalChecksFilter: strict` leaves an unsoaked update out of the group, so it cannot hold the whole branch. Majors, Go toolchain minors and preset bumps still wait for a tick on the dependency dashboard. Ploeg's pin is the exception: when Ploeg publishes a newer release, release candidates included, Renovate proposes it in a `build(ploeg)` pull request that never merges itself, because each move changes the engine Unfold runs on. When that branch fails docs-check on a stale combined glossary or decision register, Ploeg's domain model or ADR ledger changed; run `mise run domain` and `mise run docs-decisions` on it. Renovate needs the `git-submodules` manager on its runner, which [homelab-cluster](https://forgejo.webgrip.dev/webgrip/homelab-cluster/src/branch/main/kubernetes/apps/renovate/renovate-operator/jobs/configmap-forgejo.yaml) enables for repositories that opt in. It ignores mise's generated `.mise` lock directories. Go keeps minor and patch apart, because combined Renovate would offer only the minor and the patch would never come; Go patches merge themselves in their own `Go toolchain patches` branch.

`rebaseWhen: conflicted` rebases a Renovate branch only when it conflicts. With the preset's `behind-base-branch`, every push to `development` rebased every open Renovate branch, and each rebase started a full pull request run. The runner pool cannot absorb that.

## Publication and recovery

A `unfold-v…` release runs Unfold's artifact jobs. Unfold accepts only zero-major release candidates: a breaking change raises the minor version, and a `verifyRelease` guard in [scripts/release-policy.cjs](../../scripts/release-policy.cjs) refuses anything but `0.x.y-rc.N` from `development`. Unfold's distribution job is the only publisher, so it takes the GitHub release out of draft itself. A manual publication retry requires the selected workflow ref to be the same tag as its `tag` input. Publication runs for the same tag are serialized; a newer invocation does not cancel a partially completed publication.

Forgejo 15 can lose a release to a race. semantic-release pushes the tag and immediately asks for the release. Meanwhile Forgejo's own push handler inserts a tag-only row for the same tag, so the release request fails with HTTP 500 (`UQE_release_n`, a duplicate key). The tag and the release commit stay, but the release never exists, so no publication starts. This happened to `glide-v0.4.0-rc.26` on 2026-10-01. When the Semantic Release step fails, the `release` and `site-release` jobs run [the release repair script](../../scripts/release-repair.mjs). If HEAD carries the job's release tag and that tag has no release, the script creates one with the release commit's body as notes, the same notes semantic-release would have sent. That release starts publication as usual. The job stays red, because the Semantic Release step did fail. The script creates nothing when HEAD has no release tag or the release already exists.

Application publication uses normal, explicitly gated jobs and the existing pinned build/sign composites. This avoids the [Forgejo reusable-workflow flattening trap](https://forgejo.webgrip.dev/webgrip/workflows/src/branch/main/AGENTS.md). The [artifact guide](artifacts.md) defines source mirroring, package paths, cryptographic verification and retry behavior.

The naming and separation follow the original [front-end entry points](https://forgejo.webgrip.dev/webgrip/de-vloer/src/commit/c5718cde7e1c7520927c64613c38beee11e087f7/.forgejo/workflows/) and the [infrastructure monorepo](https://forgejo.webgrip.dev/webgrip/infrastructure/src/branch/main/.forgejo/workflows/). Forgejo's [workflow reference](https://forgejo.org/docs/latest/user/actions/reference/) describes the event, dependency and composite-action syntax. Shared actions and reusable workflows retain their existing pinned versions; Renovate owns updates.

## Release floors

[scripts/release-floors.json](../../scripts/release-floors.json) records, per application, the highest version any destination already holds (the floor), the versions above it that can never be used again, and the tag prefixes that have carried the application. Ploeg and Unfold both have the floor `0.4.0-rc.34`; Ploeg's withdrawn `1.0.0-rc.1` is still published and listed as never reusable. Ploeg's record is retired: no train may version Ploeg again, and the record keeps every version Unfold published for it, up to `0.4.0-rc.35`, out of reach. The [audit record](../research/2026-10-03-release-floors-and-identity.md) shows where each version lives.

The release policy's `verifyRelease` refuses a computed version that is at or below Unfold's floor, or at or below any existing tag under a prefix that has carried the application, such as `vloer-v` or `glide-v`. It lists every tag in the checkout, including tags a stale merge left unreachable from `development`, so a recomputed version stops before semantic-release commits or tags anything. The Unfold publishers refuse a version at or below Unfold's floor before they read a registry or the forge, and refuse to publish Ploeg before any Git, network or file access. A retry of an existing release checks out its own tag and therefore keeps the floors it was cut with. [release_floors.py](../../scripts/release_floors.py) and [release-floors.cjs](../../scripts/release-floors.cjs) implement the same comparison and run the same [cases](../../scripts/fixtures/release-floor-cases.json). Raise a floor only with new audit evidence, and never lower one.

## Validation and remaining qualification

Run `mise run verify` and `mise run release-check`. The latter executes the [release-policy tests](../../scripts/release-policy.test.cjs), [release-isolation tests](../../scripts/release-isolation.test.cjs) and [workflow routing tests](../../scripts/workflow-policy.test.cjs) in the pinned release container. They cover application-tag rejection, manual ref matching, disabled publication, CVE gates before signing, the absence of Ploeg publication, dependency integrity, release floors and orphaned tags. Set `UNFOLD_RELEASE_HISTORY=true` to also compute the next version from the actual history and check it against the floors and the repository's tags; this needs a full clone, not a worktree, because the container mounts only the checkout.

The [documentation publisher](docs-publishing.md) has its own `UNFOLD_DOCS_PUBLISH_ENABLED` gate and dedicated Garage bucket. It uses the shared TechDocs generation and Zensical deployment workflows at `v2.7.1`. Its scoped credentials cannot publish application packages. Application destination permissions and complete artifact delivery still require the evidence listed in the [cutover preparation gates](first-cutover.md#2-close-the-release-blockers). Passing workflow tests or a release preview does not close those gates.
