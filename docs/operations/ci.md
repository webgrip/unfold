# CI and release workflows

When a run fails in a way this page does not explain, see [Troubleshoot CI and releases](ci-troubleshooting.md).

Unfold uses Webgrip's event-named entry points. The executable definitions live in the root [workflow directory](../../.forgejo/workflows/). Forgejo reads workflows only from the repository root, so the applications have no workflow directories of their own.

| Entry point | Trigger | Responsibility |
| --- | --- | --- |

A newer `development` push cancels the older run. It versions nothing on `development`; an enabled push to `main` releases a stable site version. |
| [on_release_train.yml](../../.forgejo/workflows/on_release_train.yml) | Hourly at minute 7 on `development`; manual | The [release train](#the-release-train): when an application has unreleased commits, run the push's checks and Ploeg pin check on the development head, then release Unfold and a site candidate from that head if `development` has not moved since. |
| [on_pull_request.yml](../../.forgejo/workflows/on_pull_request.yml) | Pull request; manual validation | Run the same application, Ploeg pin and release-policy jobs without release credentials or versioning jobs, plus `opencode-contract` ([dependency updates](#dependency-updates)), `agent-trace` ([Agent Trace summary](#agent-trace-summary)) and `ploeg-docs`, which checks only the pages generated from the domain models and the ADR ledgers and the documentation links into the pinned Ploeg ([the Ploeg pin pull request](#the-ploeg-pin-pull-request)), and a `gate` job that sums them up ([the pull request gate](#the-pull-request-gate)). |

## The pull request gate

The `gate` job of [on_pull_request.yml](../../.forgejo/workflows/on_pull_request.yml) waits for every other pull request job except the advisory `agent-trace` and `warnings`, runs even when one of them failed, and succeeds only when each of them succeeded. Its context, `[Workflow] On Pull Request / gate (pull_request)`, is the one a branch rule needs to require: a job added to the workflow joins the gate instead of a list of contexts in the branch rule. The required contexts of `development` live in the repo-config model of [webgrip/homelab-cluster](https://forgejo.webgrip.dev/webgrip/homelab-cluster/src/branch/main/kubernetes/apps/repo-config/repo-config/model/repos.yaml), not in this repository. [The workflow policy test](../../scripts/workflow-policy.test.cjs) fails when a new pull request job is neither in the gate nor named advisory there, and runs the gate's script against passing, failed, cancelled, skipped and missing results.

## Gating a reusable workflow

A job that calls a reusable workflow (`uses:` at job level) is turned off through the workflow's `enabled` input, never through `if:`. Forgejo 15.0.2 flattened such a caller's `with:` and ignored its `if:` (run 456, October 2026): a `with:` that read the outputs of a skipped job failed the whole run before any job started, with nothing in a log, and the run page held the reason only in `state.run.preExecutionError`. The gate job therefore always runs and writes `false` instead of skipping, as `authorize-publication` in [on_docs_change.yml](../../.forgejo/workflows/on_docs_change.yml) and `site-release-tag` in [on_release_published.yml](../../.forgejo/workflows/on_release_published.yml) do.

## Shared checks and the Ploeg pin

Unfold depends on one release of [github.com/ploeg-hq/ploeg](https://github.com/ploeg-hq/ploeg), pinned three times ([ADR-0039](../adr/adr-0039-unfold-depends-on-a-released-ploeg-through-its-contract-bundle-and-go-module.md), [ADR-0043](../adr/adr-0043-an-unfold-release-is-one-chart-that-carries-the-ploeg-it-was-tested-with.md)): [apps/unfold/ploeg-release.json](../../apps/unfold/ploeg-release.json) pins Ploeg's contract bundle `ghcr.io/ploeg-hq/ploeg-contract` by version and manifest digest, [the demo helper's go.mod](../../apps/unfold/scripts/unified-demo/go.mod) pins the Go module `github.com/ploeg-hq/ploeg` at the same version, and [the Unfold chart](../../apps/unfold/ops/helm/unfold/Chart.yaml) depends on the chart `ploeg` from `oci://ghcr.io/ploeg-hq/charts` at that version, locked in its `Chart.lock`. [scripts/ploeg-contract.py](../../scripts/ploeg-contract.py) `fetch` pulls the bundle anonymously, checks the manifest against the pinned digest and the layer against the manifest, and unpacks it into `apps/ploeg`, which Git ignores. `mise run setup` runs it, and so does every job that reads Ploeg's contract or documentation before it reads them. `check` fails when the pins name different releases, when `Chart.yaml` or `Chart.lock` names another `ploeg` release or registry, or when `apps/ploeg` holds another bundle; `mise run verify` runs it. The `ploeg-pin` job runs it with `--published`, which also requires the registry tag to still be the pinned digest, and the `release` job waits for it. A pull request that pins an unreleased Ploeg therefore stays red until Ploeg publishes it. `UNFOLD_PLOEG_CONTRACT_REGISTRY` points the fetch at a mirror such as `harbor.webgrip.dev/ghcr/ploeg-hq`; the digests make the source irrelevant. `chart` downloads the locked Ploeg chart into the chart's `charts/` directory, which Git ignores; `mise run setup` runs it, because `helm lint`, `helm template` and Unfold's chart tests need it even with `ploeg.enabled=false`. It pulls anonymously, with a throwaway registry configuration, so a stale `ghcr.io` login in a local credential store cannot refuse the public chart. Move all three with `mise run ploeg-pin 0.x.y-rc.N`, in a `fix(ploeg)` commit, which releases Unfold. It needs `go` and `helm`, which mise installs, and network access to `ghcr.io`: it writes `Chart.lock` with `helm dependency update` rather than by hand, because Helm refuses a lock whose digest of the requirements it cannot reproduce. Renovate leaves all three alone.

Source changes and pull requests use the same local [verification action](../../.forgejo/actions/verify/action.yml) and [release-policy action](../../.forgejo/actions/release-policy/action.yml). Each caller checks out the repository before invoking a local action. A pull request runs the release-policy action as its own job. The release train runs it as the first step of its `release` job, which uses the same container, so the train needs one runner pod fewer. The existing application gates remain in [mise verification](../../scripts/verify.mjs), including generated docs, Helm goldens and deterministic integration. CI splits them over two jobs on separate runner pods: `checks-unfold` runs the Unfold group, whose test suite is the longest gate, and `checks` runs every other group. The action's `only` and `except` inputs set `UNFOLD_VERIFY_ONLY` and `UNFOLD_VERIFY_EXCEPT`, which name the groups a run keeps or leaves out. Under contention a pod's CPU share follows its request, so two pods on a busy node get twice the share of one. A third job, `build-contexts`, runs the [build-contexts action](../../.forgejo/actions/build-contexts/action.yml): it builds both Unfold images to the build cache only, side by side on the node's Docker daemon, and needs no toolchain setup. The dedicated docs workflow gives documentation changes their own result; the source gate still validates the complete tree.

Verification runs independent gate groups in parallel: Unfold, the AHP client run, the Unfold extension, the hosted demo replay, Ploeg, the site, Helm, release tests, integration and docs. The Ploeg group runs the pin check, its tests, and `go vet` and a build of the unified demo's Go helper against the pinned module. Unfold no longer runs Ploeg's own `scripts/verify.sh`; Ploeg's CI does. Gates inside a group stay sequential. Each gate's output is buffered and printed in group order with its result and duration, followed by a summary. The first failure cancels the running gates, skips the pending ones and names the failed gate. The managed qualification's embedded PostgreSQL starts on a port the operating system assigns, so checkouts can verify at the same time, and a server orphaned by a cancelled gate does not block the next run. The verification action restores the mise tool installs, the Go module and build caches, the npm download cache and the site's pnpm store, and sets `GOFLAGS=-count=1` so Go never reports a cached test result. The mise key is the hash of the `mise.toml` and `mise.lock` files. On a miss the action restores the nearest older entry, mise installs only the tools that changed, and the result is saved under the new key. The Go key is the hash of the helper module's `go.sum` and its Go files, so a Ploeg bump or a helper change saves a fresh build cache and the next run restores the nearest one, falling back to any Go version's cache after a toolchain bump.

Verification also keeps a result cache of gates that passed, in `~/.cache/unfold-verify`. A gate's key hashes the committed Git trees of its group's inputs, the root, Unfold and site `mise.toml` files and both verify scripts, the tool versions mise resolves in each scope, the `GOFLAGS` and `UNFOLD_TEST_TIMEOUT_SCALE` settings, the gate's command and the platform. A gate whose inputs have uncommitted or untracked changes gets no key. The Unfold group reads `apps/unfold` and `docs`, the AHP client and extension groups `apps/unfold`, the Ploeg group the pin file, the unified demo helper module and the pin check with its tests, the site group `apps/site` plus Unfold's `public`, `src`, `examples`, recorder and `package.json`, because its build records the demo replay and copies `public` into `/demo`, and the Helm group `apps/unfold/ops/helm`. Both pins live under `apps/unfold`, so the Unfold and Ploeg gates rerun when either moves, and the unpacked bundle, which Git ignores, never counts as an uncommitted change. The integration group reads `apps/unfold`, `scripts/integration.mjs` and `scripts/fake-litellm.mjs`. The release and docs groups span the whole tree and always run. Every CI run records its passes. Only a pull request reuses them (`UNFOLD_VERIFY_REUSE`): a push to `development`, the release gate, runs every gate. An npm update in Unfold therefore skips the Ploeg gates in its pull request. Outside CI, `mise run verify` uses `~/.cache/unfold-verify` and reuses its passes by default, so a gate whose committed inputs already passed on this machine is skipped. Set `UNFOLD_VERIFY_REUSE=false` to run every gate, or `UNFOLD_VERIFY_RESULTS` to use another directory, which then reuses only with `UNFOLD_VERIFY_REUSE=true`, as in CI. [The cache tests](../../scripts/verify-cache.test.mjs) state which changes keep a key and which change it. Markers unused for 14 days are removed.

`UNFOLD_VERIFY_CPUS` caps each gate's parallelism: it sets `GOMAXPROCS`, `go -p` and Unfold's `--test-concurrency`. Without it the tools start one worker per host core. A runner pod requests 250m CPU but sees every core of its node, so seven parallel groups each fanning out to all cores contend with each other and with the other runners on the node. CI sets 4, a starting value to tune against job duration. `UNFOLD_VERIFY_GROUPS` caps how many gate groups run at once; unset, all of them start together. Groups start in the order `scripts/verify.mjs` lists them, which is longest first as measured in CI (docs, site, integration, the AHP client run, the extension, then the short ones), so the two slots of the `checks` job do not end with one long group running alone. Every Node gate shares a V8 compile cache in the system temporary directory (`NODE_COMPILE_CACHE`, unless already set), so the test suite's 270 processes compile Unfold's modules once instead of each; it cut the suite's CPU time by about a third. The runner's memory request is sized by the peak of this job: measured on 2026-10-10 with warm caches, all ten groups at once peaked at 2.10 GiB (3.21 GiB cold), three at 1.79 GiB and two at 1.12 GiB, for 78, 71 and 90 seconds. CI sets 2, so the job fits the homelab runners' memory request with room to spare. The Unfold test scripts also set `--test-timeout=120000` and `--test-force-exit`, so a test that never settles fails after two minutes instead of holding the runner until the job timeout.

## Warnings

Forgejo has no warning result for a job: a job either succeeds or fails. A warning printed by a passing step would otherwise stay buried in a green log. The verification action therefore saves the output of its three `mise install` steps, `mise run setup` and `mise run verify`, and its last step, which runs even after a failure, passes that output to [the warnings scanner](../../scripts/ci-warnings.mjs). The scanner recognizes the warning formats of npm, pnpm, mise, git and uv (both print a bare `warning:` line, so the report labels it `git or uv`), Node, Python, Go, Actions annotations and build tools, so a test name or a JSON log line that contains the word "warn" is not reported. It reports each distinct warning once and writes the list to its verification job's `warnings` output. A separate `warnings` job prints the lists of `checks` and `checks-unfold` and fails when either is not empty. The commit then shows a red `warnings` check while `checks` carries on and the release train still releases: no job waits for `warnings`, and the train has none. Fix the cause, or accept a warning in [the allowlist](../../scripts/ci-warnings-allow.json) with a pattern and the reason it is accepted. A pull request that reuses cached gate results does not print those gates' output, so a push to `development` is the complete check.

The root `mise.lock` is committed and written by mise 2026.9.17, the version CI pins. `min_version` in the root `mise.toml` refuses an older mise. Regenerate it with `mise lock`. Renovate relocks `mise.lock` itself when it bumps a tool.

The [browser flows](../../apps/unfold/scripts/browser-check.mjs) drive Unfold's deterministic demo in Chromium with Playwright. They run in [the browser suite action](../../.forgejo/actions/browser-suite/action.yml) every night from [the nightly workflow](../../.forgejo/workflows/on_nightly.yml) and on command: start that workflow by hand in Forgejo, or run `mise run browser` locally. They do not run on a push. The suite needs CPU more than memory: measured on 2026-10-14 in the CI image, it peaks at 0.9 GiB and takes about 1 minute on a free workstation, 8 minutes with 2 CPUs, and fails within 2 minutes with 1 CPU. The shared runners' Docker hosts request almost no CPU, so every run since the suite reached CI on 2026-10-14 failed, including the quiet 02:23 runs. CI therefore sets `UNFOLD_BROWSER_TIMEOUT_SCALE` to 3, which triples each flow's default wait, and gives the job 45 minutes. Each flow logs when it starts and how long it took, so a run that hits the limit shows where it was. The job runs in Microsoft's Playwright image through Harbor's `mcr` proxy. The image's tag must equal the `playwright` version in `apps/unfold/package.json`, because each Playwright release expects its own Chromium build, and [the workflow policy test](../../scripts/workflow-policy.test.cjs) fails when the two differ. When Renovate moves one, move the other in the same pull request. The browser flows gate no release and are not part of `mise run verify` or pull requests.

The AHP client run (`mise run ahp-e2e`, the `ahp-sdk` group of `mise run verify`) drives Unfold's deterministic demo with Microsoft's own client, [`@microsoft/agent-host-protocol`](https://www.npmjs.com/package/@microsoft/agent-host-protocol), and judges the host's state with the SDK's reducers. [The harness](../../apps/unfold/test/sdk-e2e/ahp-e2e.mjs) starts the demo on a free local port with an empty data directory and an environment stripped down to `PATH`, `HOME`, the temp directory and the locale, so no model key, provider URL or `.env` file reaches it. It refuses to run when the server does not report demo mode. It then connects as five profiles: VS Code 1.142 (offers `1.0.0, 0.10.0, 0.9.0`, sends `_meta["vscode.ahpSessionUris"]`, creates sessions on `ahp-session:/<uuid>`), VS Code 1.141 (`unfold:/<uuid>`, no `_meta`), a plain AHP client using the SDK's typed helpers, a version-negotiation probe and the SDK's multi-host layer. It prints one line per check, the failing ones with their evidence, and a pass count per profile; the wire logs and the full results go to a temporary directory it names. A whole run takes about 40 seconds. Every wait has its own timeout, a turn gets 90 seconds, and the run as a whole gets 240 seconds (`UNFOLD_AHP_E2E_TIMEOUT_MS`), each multiplied by `UNFOLD_TEST_TIMEOUT_SCALE`; when the budget runs out the run fails, kills the demo and exits. The SDK is an exact-pinned devDependency of `apps/unfold`, so Renovate moves it and the image never ships it.

[unfold-mcp's end-to-end suite](../../apps/unfold/test/e2e/mcp-over-https.e2e.ts) signs people in through a real Authentik and drives the HTTP MCP endpoint with the official MCP client ([what it checks](../how-to/serve-unfold-mcp-over-https.md#test-it-end-to-end)). [The nightly workflow](../../.forgejo/workflows/on_nightly.yml) runs it every night and on command in the same Playwright image, through [its action](../../.forgejo/actions/mcp-e2e/action.yml), with Postgres, the Authentik server and the Authentik worker as job services; locally `npm run test:mcp-e2e` starts the same Authentik and Postgres with Docker Compose. Renovate reads the compose file's two images under the job's Harbor names, so one update moves both pins, and the workflow policy test fails when they differ. Its credentials are throwaway values for an instance that only the job reaches. Like the browser flows, it reports and gates no release, and it is not part of `mise run verify`, because Authentik takes about a minute to start. On a busy runner the Authentik server can take longer than its image's health check allows (about two and a half minutes), and the runner then fails the job before a step runs. The server service therefore runs with `--no-healthcheck`, and the suite's own readiness check, which waits up to four minutes for the health endpoint, the API and the default blueprints, decides instead.

The weekly [demo smoke action](../../.forgejo/actions/tutorial-smoke/action.yml) runs [the tutorial smoke script](../../scripts/tutorial-smoke.sh): it starts `mise run demo-unified`, waits for `unified-demo.ready`, stops it with `SIGTERM`, then runs the documented `--smoke` check. It is deterministic, with no model calls or credentials. When the runner has no PostgreSQL `initdb` and `postgres`, or runs as root, the job logs what is missing and passes without starting the demo. The host-mode `ci-runner` has neither, so on every push and pull request the job only occupied a runner; it runs on the schedule instead, and no release job depends on it.

The Unfold version is the application's ([ADR-0019](../adr/adr-0019-unfold-pins-ploeg-from-its-own-repository-and-releases-only-its-application.md), which supersedes the joint version of [ADR-0004](../adr/adr-0004-unfold-releases-one-version.md); [ADR-0039](../adr/adr-0039-unfold-depends-on-a-released-ploeg-through-its-contract-bundle-and-go-module.md) keeps it). Ploeg is versioned and published by [github.com/ploeg-hq/ploeg](https://github.com/ploeg-hq/ploeg). The pinned Webgrip semantic-release monorepo composite runs [the Unfold configuration](../../apps/.releaserc.cjs) with `package-path: apps` in the `harbor.webgrip.dev/webgrip/semantic-release` 2.x toolchain image. The configuration is `@webgrip/semantic-release-config` 2.x with the train `unfold` (`monorepo: { name: 'unfold' }`), so only commits that touch a file under `apps/` count, and every commit in the release range must be a conventional commit or a merge (`ENONCONVENTIONAL` otherwise). Moving the Ploeg release touches `apps/unfold`, so its `fix(ploeg)` commit cuts the next Unfold candidate. The [marketing site](../../apps/site/README.md) lives under `apps/` but is not part of the Unfold version ([ADR-0012](../adr/adr-0012-the-marketing-site-releases-and-deploys-on-its-own.md)): a commit scoped `site` never releases Unfold, and neither train reads the other's tags. The configuration adds that rule after the shared rules and lowers the shared breaking rule from major to minor. The analyzer stops at the first major it finds, so a breaking rule left at major would release Unfold for a `feat(site)!` commit before the `site` rule is read. A rule passed through `extraReleaseRules` does not work for this: those rules come first, and a later matching rule overrides a `release: false`. During 0.x the shared `initialDevelopment` lowers a breaking change to minor anyway, and the release policy refuses 1.x. Its own train, [apps/site/.releaserc.cjs](../../apps/site/.releaserc.cjs), cuts `unfold-site-v…` releases that deploy the site to Cloudflare; its `site-release` job runs after Unfold's `release` job in the release train, and a published `unfold-site-v…` release deploys the site through the shared `cloudflare-deploy` workflow, as the [site deploy guide](../../apps/site/docs/deploy.md) describes. Unfold's publication jobs accept only `unfold-v…` tags, so a site release publishes no image, chart or extension. A release is the tag alone ([homelab ADR-0078](https://forgejo.webgrip.dev/webgrip/homelab-cluster/src/branch/main/docs/techdocs/docs/adr/adr-0078-one-release-recipe-four-kinds.md)): semantic-release tags the commit the train checked, `unfold-v<version>`, and writes the notes to the Forgejo release page. It commits nothing, so `apps/CHANGELOG.md`, the chart, the manifests and the extension keep the version of the last release commit, `0.4.0-rc.114`. A `@semantic-release/git` step added to the configuration fails the release with `ERELEASECOMMIT`. Publication sets the version: the chart and extension jobs run [the stamp script](../../apps/unfold/scripts/stamp-version.mjs) on their checkout of the tag before they package, the image build runs it on the application manifests from its `IMAGE_VERSION` argument, because the shared build action checks the tag out again, and `publish_chart.py` packages with `--version` and `--app-version` and refuses a packaged chart whose metadata differs from the stamped metadata at the release version. The release builds no VSIX before it tags: the train's `checks` package the extension (`extension:package` in `scripts/verify.mjs`) on the same head. Renovate moves the `unfold-agent` image that the agent sandbox warm pool and the live local example name to the newest candidate on Harbor, in a `chore(agent-image)` commit that releases nothing. The annotated tag `glide-v0.3.0` is the baseline where the last imported candidates met. Releases before the rename carry the old `glide-v` and `glide-site-v` names; when the product was renamed ([ADR-0013](../adr/adr-0013-the-product-is-named-unfold.md)), `unfold-v` and `unfold-site-v` baseline tags were placed on the same commits as the newest old tags, so the versions continue. Both source checks and release-policy checks must pass before versioning.

`UNFOLD_RELEASES_ENABLED` must equal `true` to version or publish. A manual source-validation run never releases, even with the gate enabled; dispatch the release train instead. Release-channel notes live on Forgejo only; nothing copies them to GitHub. CI runs the import verifier with `UNFOLD_REQUIRE_IMPORT_NOTES=true`, so missing notes fail the source gate instead of being skipped as they are locally. A [release test](../../scripts/test_release_refs.py) fails if any workflow, action, script or mise task prunes, mirrors or deletes refs, or pushes notes. The [notes-loss record](../research/2026-09-23-forgejo-notes-loss.md) explains why. Keep the `main` release baseline required by the shared preset; `development` remains trunk and the only automatic release branch. Use the [first cutover playbook](first-cutover.md) before enabling publication.


## Agent Trace summary

The `agent-trace` job of a pull request says which lines of its commits an agent wrote. It fetches `refs/notes/agent-trace` from `origin` into the same local ref, without force, and goes on when `origin` has none. Then it runs the plugin's [report script](../../apps/unfold/extensions/claude-code/scripts/agent-trace-report.mjs) on the pull request's base and head commits and writes the Markdown to the job summary and the log. The notes reach `origin` when people push them, by hand or with the plugin's `UNFOLD_PUSH_AGENT_TRACE=1` ([how-to](../how-to/link-claude-code-sessions.md#show-reviewers-which-lines-an-agent-wrote)); no workflow pushes, prunes or deletes them. The job blocks nothing: every step ends in `|| echo`, no job needs it, and it is not a required context. [The workflow policy test](../../scripts/workflow-policy.test.cjs) checks all three.
## Dependency updates

Renovate follows the org preset, its [automerge-non-major overlay](https://forgejo.webgrip.dev/webgrip/renovate-config/src/branch/main/automerge-non-major.json) and its [first-party overlay](https://forgejo.webgrip.dev/webgrip/renovate-config/src/branch/main/first-party.json), with Unfold's own managers and exceptions in [renovate.json](../../renovate.json). Minor, patch, digest and pin updates need no dashboard approval. They land in one `all non-major dependencies` branch, and Forgejo merges the pull request as soon as [the gate](#the-pull-request-gate) is green: the [platform-automerge overlay](https://forgejo.webgrip.dev/webgrip/renovate-config/src/branch/main/platform-automerge.json) has Renovate schedule Forgejo's merge when it opens the pull request, so the merge waits for no Renovate run ([homelab-cluster ADR-0084](https://forgejo.webgrip.dev/webgrip/homelab-cluster/src/branch/main/docs/techdocs/docs/adr/adr-0084-a-branch-rule-requires-one-gate-and-forgejo-merges-renovate-on-it.md)). A pull request Forgejo did not schedule, such as one opened before the overlay, Renovate still merges itself on its next run. Lock-file maintenance and vulnerability fixes also merge themselves. Unattended updates keep the preset's soak of three days for a minor and one day for a patch. `internalChecksFilter: strict` leaves an unsoaked update out of the group, so it cannot hold the whole branch. Webgrip's own packages, such as the `harbor.webgrip.dev/webgrip/*` images and `@webgrip/*` packages, leave that branch for a `webgrip dependencies` branch of their own. It skips the soak and merges itself on green, so a broken third-party update never holds back a Webgrip release, and the reverse. A major of a Webgrip package opens without a tick and waits for a person to merge it. Preset bumps merge themselves in their own branch. Third-party majors and Go toolchain minors still wait for a tick on the dependency dashboard. Ploeg is the exception: Ploeg's own release opens its pull request, described in [the next section](#the-ploeg-pin-pull-request). Renovate ignores mise's generated `.mise` lock directories. After it moves the pnpm that `apps/site/package.json` names, it runs `corepack pnpm install --lockfile-only` in that directory, so the lockfile's record of pnpm moves too; the homelab's `allowedCommands` must list the command ([Troubleshoot CI and releases](ci-troubleshooting.md)). Go keeps minor and patch apart, because combined Renovate would offer only the minor and the patch would never come; Go patches merge themselves in their own `Go toolchain patches` branch.

The `opencode-contract` pull-request job runs `mise -C apps/unfold run opencode-contract`. It fetches the OpenCode build that [the agent image](../../apps/unfold/ops/agent/Dockerfile) pins, starts it against a local fake model that calls `grep`, and requires Unfold's OpenCode adapter to complete a turn with and without a permission round-trip ([test](../../apps/unfold/test/opencode-contract.test.ts)). An OpenCode update that breaks how Unfold reads or answers permissions therefore stays red. It runs on pull requests, including Renovate's, but not on a direct push to `development`.

The `opencode-ai` rule names the package's source repository, because the npm package names none and Renovate otherwise puts no release notes in the pull request. The release notes are what a person merging reads first, and what a Run that explains the update reads: once the pinned Ploeg carries [Ploeg ADR-0106](https://github.com/ploeg-hq/ploeg/blob/development/docs/adrs/0106-a-dependency-update-pull-request-is-explained-on-the-pull-request-by-a-teams-reading-roles.md) and the homelab opts `webgrip/unfold` in, Ploeg's reviewer explains every Renovate pull request on the pull request itself, and the repository skill [explain-a-dependency-update](../../.agents/skills/explain-a-dependency-update/SKILL.md) tells it where each pin is used here. Until then that skill only serves a person or an interactive agent reviewing one.

`rebaseWhen: conflicted` rebases a Renovate branch only when it conflicts. With the preset's `behind-base-branch`, every push to `development` rebased every open Renovate branch, and each rebase started a full pull request run. The runner pool cannot absorb that.

## The Ploeg pin pull request

When Ploeg publishes a release candidate and its contract bundle, Ploeg's release workflow opens the pin pull request itself ([ADR-0041](../adr/adr-0041-a-ploeg-release-opens-unfolds-pin-pull-request-by-running-unfolds-recipe.md), [Ploeg ADR 0119](https://github.com/ploeg-hq/ploeg/blob/development/docs/adrs/0119-a-release-opens-each-consumers-update-by-running-the-consumers-own-recipe.md)). Its `consumers` job clones `development`, runs [`scripts/consume-ploeg-release.sh <version>`](../../scripts/consume-ploeg-release.sh), commits what changed as `fix(ploeg): update Ploeg to <version>` on the branch `ploeg/<version>`, and opens the pull request. With `"merge": "by-consumer"` in its `RELEASE_CONSUMERS` entry Ploeg leaves the merge to [the release train](#the-release-train), which merges the newest green pin at the start of its next run; without it Ploeg asks Forgejo to merge when the required checks of `development` succeed. The merge cuts the next Unfold candidate (homelab ADR-0069). A newer Ploeg release closes the previous pull request with a comment naming its successor. The author is a Forgejo user that may write only this repository.

The recipe moves the three pins with `scripts/ploeg-contract.py pin`: the bundle's tag and digest in `apps/unfold/ploeg-release.json`, `github.com/ploeg-hq/ploeg` in the demo helper's `go.mod`, followed by `go mod tidy`, and the `ploeg` dependency of the Unfold chart, followed by `helm dependency update`, which rewrites `Chart.lock`. It then runs [`scripts/renovate-ploeg-docs.sh`](../../scripts/renovate-ploeg-docs.sh), which regenerates the decision register, Unfold's domain pages and the combined glossary from the new bundle, so a Ploeg release that adds an ADR arrives green. It installs Go, uv, Helm and Node from `mise.toml` on Ploeg's GitHub runner, which must reach `ghcr.io`, the Go module proxy, PyPI, the npm registry and Playwright's browser download. To move the pin by hand, run the same script, or `mise run ploeg-pin 0.x.y-rc.N` and then the regeneration.

Renovate no longer touches either pin: `renovate.json` disables both packages, so two writers never race on one file. Forgejo merges on the required contexts of `development` only, so `ploeg-docs` must be one of them or a job [the gate](#the-pull-request-gate) waits for, or a pull request with a term clash merges red.

The [landscape explorer](../landscape/explorer.html) embeds the glossary, so a Ploeg release that changes the glossary also makes the explorer stale. The script rebuilds it when the machine has Node, Unfold's npm packages and Playwright's Chromium, so the recipe installs Node from `mise.toml`, runs `npm ci` in `apps/unfold` and installs Chromium before it pins. When that install fails, the recipe prints a notice and still pins, and the pull request needs `mise run landscape` from a person. Run 2291 (rc.57, 2026-10-24) is the failure this prevents.

The combined glossary cannot be regenerated when the new Ploeg model defines a term that Unfold's model also defines. The script then keeps the old glossary, writes the generator's explanation to `ploeg-glossary-conflicts.txt` at the repository root and exits 0, so the pull request still carries everything it could regenerate together with the report. The report never makes the pull request green: `scripts/docs.py --domain-check` fails while the report exists or the clash remains.

The `ploeg-docs` job runs that check (`mise run domain-check`) on every pull request. It covers the landscape explorer too, so `ploeg-docs` cannot pass while `checks` fails on a stale landscape. It then runs `scripts/docs.py --stage-only`, which resolves every documentation link without building the site, so a Ploeg release that moves or deletes a page's link target fails here as well: 0.2.0-rc.40 moved `pkg/worker/task.go` and broke four links that only `checks` caught. Both take seconds, because they skip the documentation build, so a broken pin shows as its own named red check instead of one more failure inside `checks`, and a pin pull request is safe to merge once `ploeg-pin` and `ploeg-docs` are green. `checks` runs the same check as part of `mise run docs-check`. When `ploeg-docs` fails, its log says which case applies:

- **A stale page** (`Stale generated domain view`, `Stale combined glossary`, a stale decision register, `Stale landscape`): run `mise run domain`, `mise run docs-decisions` and `mise run landscape` on the branch and push.
- **A missing link target** (`Missing documentation targets` naming a path under `apps/ploeg`): the new Ploeg moved or deleted a file an Unfold page links. Point the link at the file's new path in the bundle, or drop it, and push.
- **A term clash** (`Combined glossary conflicts`): two models define one term. Ploeg owns a term when Ploeg stores it or its API names it; otherwise Unfold owns it. The message names both models and suggests the owner. When Ploeg owns it, add the term to the Ploeg entry under `imports` in `docs/domain/model.yaml`, delete Unfold's copy, and move any clause that only Unfold meant into an Unfold term that links to it, as [#339](https://forgejo.webgrip.dev/webgrip/unfold/pulls/339) did for Tenant and Client. When Unfold owns it, Ploeg's model changes upstream instead. Then run `mise run domain`, delete `ploeg-glossary-conflicts.txt` and push to the `ploeg/<version>` branch.

The weekly `ploeg-ahead` job in [on_schedule.yml](../../.forgejo/workflows/on_schedule.yml) unpacks the bundle of Ploeg's newest release (`scripts/ploeg-contract.py fetch-unpinned latest`) and, separately, a bundle built from the head of Ploeg's `development` with Ploeg's own `scripts/contract-bundle.sh build`, runs the same script with `UNFOLD_PLOEG_CONTRACT_UNPINNED=true` so it keeps that bundle, runs the same check without the landscape explorer (`--without-landscape`) and the same link check, and fails when a clash or a broken link would reach the next Ploeg pull request. Nothing opens an issue for it; the red scheduled run is the signal. The nightly `ploeg-behind` job in [on_nightly.yml](../../.forgejo/workflows/on_nightly.yml) runs `scripts/ploeg-contract.py behind` and fails when GHCR lists a newer Ploeg release than the pin: a release whose pull request is still red, or whose `consumers` job never ran.

## Publication and recovery

## The release train

Unfold is versioned by [on_release_train.yml](../../.forgejo/workflows/on_release_train.yml), not by the push of a merge ([ADR-0046](../adr/adr-0046-an-hourly-release-train-versions-unfold-from-a-checked-development-head.md)). Pull requests merge minutes apart, and the checks take about 45 minutes, so a release inside each push run waited in a queue that grew with every merge, and stopping those queued runs to free runners stopped the release with them.

The train runs every hour at minute 7 and on command, only on `development` and only while `UNFOLD_RELEASES_ENABLED` is `true`. Its concurrency group, `release-train`, is its own: a push neither cancels nor queues it, and a second train waits for the first.

1. `merge-pin` runs [scripts/release_train_pin.py](../../scripts/release_train_pin.py) with `PLOEG_RELEASE_TOKEN`, the `ploeg-release` bot's token, because `development` lets only that bot and people merge ([2026-10-30 amendment](../adr/adr-0046-an-hourly-release-train-versions-unfold-from-a-checked-development-head.md#amendment-2026-10-30-merge-pin-merges-as-ploeg-release-the-account-the-branch-rule-lets-merge)). It asks Forgejo to merge the newest open `ploeg/<version>` pull request from `ploeg-release` whose required checks passed, trying older ones while Forgejo refuses, then closes the pins older than the one it merged. With no green pin it merges nothing. Its failure shows red but does not stop the train ([ADR-0046](../adr/adr-0046-an-hourly-release-train-versions-unfold-from-a-checked-development-head.md#amendment-2026-10-24-the-train-merges-the-waiting-ploeg-pin-first)).
2. `pending` checks out the branch head once `merge-pin` is done, so a merged pin is in it, and runs [scripts/release-train.sh](../../scripts/release-train.sh) `pending`. It counts the commits since the newest `unfold-v` tag under `apps/` outside `apps/site`, and since the newest `unfold-site-v` tag under `apps/site`, When both are zero the train ends. A release adds a tag and no commit, so a release tag is on the commit it released and nothing after it is release output.
3. `checks`, `checks-unfold`, `build-contexts` and `ploeg-pin` run the push's jobs on that head. The verification action reuses no earlier gate result outside a pull request, so every gate runs.
4. `release` checks out the branch again, runs the release-policy action, then `release-train.sh current <checked head>`: semantic release runs only when the branch head is still the checked commit. When `development` moved during the checks, the job passes, versions nothing and says so, and the next train checks the newer head. `site-release` repeats the head check, which still holds because the Unfold release added only a tag, and releases a site candidate after it.

A busy stretch with merges less than about 50 minutes apart therefore releases nothing until it ends. To release sooner, dispatch **[Workflow] On Release Train** on `development` once the last merge has landed. A merge in the minute semantic release itself runs still meets the composite's reset onto the newer head; that window is the release job's duration.

A `unfold-v…` release runs Unfold's artifact jobs. Unfold accepts only zero-major release candidates: a breaking change raises the minor version, and a `verifyRelease` guard in [scripts/release-policy.cjs](../../scripts/release-policy.cjs) refuses anything but `0.x.y-rc.N` from `development`. Unfold's distribution job is the only publisher, so it takes the GitHub release out of draft itself. A manual publication retry requires the selected workflow ref to be the same tag as its `tag` input. Publication runs for the same tag are serialized; a newer invocation does not cancel a partially completed publication.

Forgejo 15 can lose a release to a race. semantic-release pushes the tag and immediately asks for the release. Meanwhile Forgejo's own push handler inserts a tag-only row for the same tag, so the release request fails with HTTP 500 (`UQE_release_n`, a duplicate key). This happened to `glide-v0.4.0-rc.26` on 2026-10-01. The Forgejo release step of `@webgrip/semantic-release-config` (`lib/forgejo-release.cjs`, since 1.3.2) handles it: it adopts a release that already exists for the tag, and retries a 409, 429 or 5xx up to six times with backoff, after which the request takes Forgejo's path that converts the tag-only row. The repair step that created the release from the release commit's body after a failed run is gone with the release commit. If every retry fails, the job is red and the tag has no release; create the release on the tag by hand, from the composite's job summary link, and publication starts from it.

A chart in a registry is a complete release ([ADR-0043](../adr/adr-0043-an-unfold-release-is-one-chart-that-carries-the-ploeg-it-was-tested-with.md)), so publication runs in this order:

1. `unfold-release-distribute-harbor` builds, CVE-gates, signs and pushes each image of the release to Harbor, one matrix leg per image (`unfold` and `unfold-agent`). Its "Resolve the published digest" step writes the digest under the leg's own name, `digest-<image>`, and the job exposes them as `unfold-digest` and `unfold-agent-digest`. Forgejo merges the outputs of a matrix's legs and keeps the value that is not empty, so the names must differ per leg.
2. `unfold-release-publish-chart` needs that job, so a failed or cancelled image leaves no chart for the release. [scripts/publish_chart.py](../../scripts/publish_chart.py) receives the two digests as `UNFOLD_IMAGE_DIGEST` and `UNFOLD_AGENT_IMAGE_DIGEST`, refuses a digest that is empty or that Harbor's tag no longer resolves to, and packages a copy of the chart whose defaults are `image.tag` and `workspaceAgentImage.tag: <version>`, `image.digest: <unfold digest>` and `workspaceAgentImage.digest: <agent digest>`, so the workspace renders as `ghcr.io/webgrip/unfold-agent:<version>@<agent digest>`. It runs `helm dependency build` first, so the package vendors the Ploeg chart that `Chart.lock` names, and it refuses to push a package that renders an Unfold image without a digest or carries another Ploeg chart. After the push it signs the chart's Harbor digest with the OpenBao Transit key that signs the images, through the job's Forgejo OIDC token and the `cosign-signer` role, then runs `cosign verify` against the [committed public key](../../ops/security/cosign.pub). A signature that key cannot verify fails the job. A rerun skips signing when the digest already verifies. Flux `OCIRepository.spec.verify` in a consumer checks this signature before it follows a candidate.
3. `unfold-release-distribute` copies the images and then the chart to Forgejo and GHCR. Each copy keeps its digest, so the chart's defaults resolve in every registry. The chart copy carries the manifest and blobs only; the chart signature exists in Harbor.

[The workflow policy test](../../scripts/workflow-policy.test.cjs) fails when the chart job does not need every job that pushes an image, or when an image job's digest does not reach the chart job's environment. The Ploeg chart's own images are Ploeg's to pin.

Application publication uses normal, explicitly gated jobs and the existing pinned build/sign composites. This avoids the [Forgejo reusable-workflow flattening trap](https://forgejo.webgrip.dev/webgrip/workflows/src/branch/main/AGENTS.md). The [artifact guide](artifacts.md) defines source mirroring, package paths, cryptographic verification and retry behavior.

The naming and separation follow the original [front-end entry points](https://forgejo.webgrip.dev/webgrip/unfold/src/commit/c5718cde7e1c7520927c64613c38beee11e087f7/.forgejo/workflows/) and the [infrastructure monorepo](https://forgejo.webgrip.dev/webgrip/infrastructure/src/branch/main/.forgejo/workflows/). Forgejo's [workflow reference](https://forgejo.org/docs/latest/user/actions/reference/) describes the event, dependency and composite-action syntax. Shared actions and reusable workflows retain their existing pinned versions; Renovate owns updates.

## Release floors

[scripts/release-floors.json](../../scripts/release-floors.json) records, per application, the highest version any destination already holds (the floor), the versions above it that can never be used again, and the tag prefixes that have carried the application. Ploeg and Unfold both have the floor `0.4.0-rc.34`; Ploeg's withdrawn `1.0.0-rc.1` is still published and listed as never reusable. Ploeg's record is retired: no train may version Ploeg again, and the record keeps every version Unfold published for it, up to `0.4.0-rc.35`, out of reach. The [audit record](../research/2026-10-03-release-floors-and-identity.md) shows where each version lives.

The release policy's `verifyRelease` refuses a computed version that is at or below Unfold's floor, or at or below any existing tag under a prefix that has carried the application, such as `vloer-v` or `glide-v`. It lists every tag in the checkout, including tags a stale merge left unreachable from `development`, so a recomputed version stops before semantic-release tags anything. The Unfold publishers refuse a version at or below Unfold's floor before they read a registry or the forge, and refuse to publish Ploeg before any Git, network or file access. A retry of an existing release checks out its own tag and therefore keeps the floors it was cut with. [release_floors.py](../../scripts/release_floors.py) and [release-floors.cjs](../../scripts/release-floors.cjs) implement the same comparison and run the same [cases](../../scripts/fixtures/release-floor-cases.json). Raise a floor only with new audit evidence, and never lower one.

## Validation and remaining qualification

Run `mise run verify` and `mise run release-check`. The latter executes the [release-policy tests](../../scripts/release-policy.test.cjs), [release-isolation tests](../../scripts/release-isolation.test.cjs) and [workflow routing tests](../../scripts/workflow-policy.test.cjs) in the pinned release container. They cover application-tag rejection, manual ref matching, disabled publication, CVE gates before signing, the absence of Ploeg publication, dependency integrity, release floors and orphaned tags. Set `UNFOLD_RELEASE_HISTORY=true` to also compute the next version from the actual history and check it against the floors and the repository's tags; this needs a full clone, not a worktree, because the container mounts only the checkout.

The [documentation publisher](docs-publishing.md) has its own `UNFOLD_DOCS_PUBLISH_ENABLED` gate and dedicated Garage bucket. It uses the shared TechDocs generation and Zensical deployment workflows at `v2.7.1`. Its scoped credentials cannot publish application packages. Application destination permissions and complete artifact delivery still require the evidence listed in the [cutover preparation gates](first-cutover.md#2-close-the-release-blockers). Passing workflow tests or a release preview does not close those gates.
