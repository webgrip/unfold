# Troubleshoot CI and releases

Symptoms seen on Unfold's Forgejo Actions, what caused them and what fixed them. [CI and release workflows](ci.md) explains how the pipeline is meant to work.

## Read a run without a token

The repository is public. Without a Forgejo token you can still read:

* the task list: `https://forgejo.webgrip.dev/api/v1/repos/webgrip/unfold/actions/tasks`
* a job's raw log: `https://forgejo.webgrip.dev/webgrip/unfold/actions/runs/<run>/jobs/<index>/attempt/1/logs`
* a run's real state: fetch the job page with `curl -L` and read `state.run` in the `data-initial-post-response` attribute (HTML-escaped JSON).

Re-running a job needs the web interface.

## Symptoms

| Symptom | Cause | Fix |
| --- | --- | --- |
| A run is red but every job log looks fine or says "job is not started" | A pre-execution error, which no log shows. Read `state.run.preExecutionError` on the job page. On Forgejo 15.0.2 a reusable-workflow caller's `with:` that read a skipped job's outputs caused it (run 456). | Gate the called workflow through its `enabled` input; see [Gating a reusable workflow](ci.md#gating-a-reusable-workflow). |
| Red with "job is not started" or `context canceled`, a few seconds after the start | Forgejo cancels a run only for a workflow whose `concurrency` sets `cancel-in-progress: true`: pull requests, nightly, schedule, and `on_source_change.yml` on every ref but `main`, where a newer push cancels the older run. Any other cancellation was sent from the web interface: every cancelled source run from 2026-10-02 to 2026-10-24 (runs 1218, 1559, 1588, and 2265 to 2316 among them) matches a `POST /webgrip/unfold/actions/runs/<n>/cancel` in Forgejo's log, sent by a signed-in browser, on 2026-10-24 in bursts of up to 20 runs from the Actions list's bulk Stop. A cancelled run also shows as a red commit status. Check `state.run.status`. | Stopping a push run is harmless: since [ADR-0046](../adr/adr-0046-an-hourly-release-train-versions-unfold-from-a-checked-development-head.md) the release train, not the push, ships a merge. Don't stop a running **[Workflow] On Release Train** run unless you mean to skip that hour's release. To find who cancelled, search Forgejo's log for `actions/runs/<n>/cancel`. |
| `release` tagged a head that never passed `checks` | Before ADR-0046 a push run released after `development` had moved on: the semantic-release composite resets onto the newer head and versions it (run 1218, rc.56). | Fixed by the release train: its `release` job runs semantic release only while the branch head is still the commit its checks passed. The remaining window is a merge during the release job itself. |
| Every hourly **[Workflow] On Release Train** run is `skipped`, while a dispatched one runs | Forgejo 15 gives a scheduled run the bare branch name as `github.ref` (`development`, not `refs/heads/development`; `services/actions/notifier_helper.go` stores `Repo.DefaultBranch`), so a job gated on `github.ref == 'refs/heads/development'` never runs on a schedule. Every train from 2026-10-24 17:07 to 2026-10-25 08:07 was skipped this way. | Gate on `github.ref_name == 'development'`, which both events set; `scripts/workflow-policy.test.cjs` evaluates the train's gates with a scheduled context of `ref: 'development'`. |
| No new `unfold-v` tag for hours although application commits merged; **[Workflow] On Release Train** runs are green | Each train's `release` job printed `development moved past <commit>, the commit the checks passed`: merges kept landing during the train's checks. Or a train's `checks` or `ploeg-pin` failed, which shows red. | Wait for a quiet hour, or dispatch **[Workflow] On Release Train** on `development` after the last merge. Fix a red `checks` on `development` first; on 2026-10-24 run 2291 failed `docs.py --check` with `Stale landscape` after the rc.57 pin until #559 rebuilt the landscape. |
| `checks` runs for about 40 minutes; the summary shows groups `CANCELLED` and none `FAILED` | A gate in a later, unprinted group failed, and a cancelled gate never exited (run 538). | Fixed by [`scripts/verify-gate.mjs`](https://forgejo.webgrip.dev/webgrip/unfold/src/branch/development/scripts/verify-gate.mjs): a cancelled gate is killed after a grace period and an orphaned process counts as a failure. |
| `warnings` is red with "job is not started" while `checks` passed | The dependent job was never scheduled while another pull request's run was active (runs 1131, 1183, 1184). Not a real warning. | Re-run the job in the web interface; a re-push can hit the same race. |
| `fatal: tag '<x>' already exists` in `release` | Up to `unfold-v0.4.0-rc.114`, an orphaned release commit: the tag points at a release commit that is no longer on `development` (`git merge-base --is-ancestor <tag> origin/development` fails). Releases have committed nothing since the move to tags-only releases, so a new tag is always on the checked head of `development`. | Revert the duplicate release commit, then `git merge --no-ff` the orphan so the tag is reachable again. Never move a published tag. The release policy already refuses a version at or below any tag in the checkout, reachable or not. |
| `release` fails with HTTP 500 right after `Created tag` | Forgejo inserted the tag's release row while semantic-release created the release (`duplicate key … UQE_release_n`). The release step retries a 5xx six times with backoff and adopts a release that already exists, so this shows only when every retry failed. The tag is fine. | Create the release on the existing tag by hand, through the link in the job summary; its publication workflow starts from that release. A re-run cuts nothing, because semantic-release sees the tag. |
| Setup fails at `corepack pnpm install --frozen-lockfile` with `ERR_PNPM_FROZEN_LOCKFILE_WITH_OUTDATED_LOCKFILE` right after Renovate moved `packageManager` in `apps/site/package.json` | pnpm 11 and later record the pnpm that `packageManager` names in the lockfile's first document, `packageManagerDependencies`, and a frozen install refuses a record that disagrees. The self-hosted Renovate image runs its own global pnpm 10 (`binarySource=global`), which switches to the new pnpm with package-manager management turned off, so the rest of the lockfile moves and the record keeps the old version ([#593](https://forgejo.webgrip.dev/webgrip/unfold/pulls/593), run 2423; reproduced byte for byte with Renovate's own lockfile step in `renovate/renovate:44.176.2-full`). | `renovate.json` runs `corepack pnpm install --lockfile-only --ignore-scripts --ignore-pnpmfile` in the moved package's directory after a pnpm update, which rewrites the record. The homelab Renovate runs it only once its `allowedCommands` lists `^corepack pnpm install --lockfile-only --ignore-scripts --ignore-pnpmfile$`; until then the pull request reports `has not been added to the allowed list`. By hand, run `corepack pnpm install --lockfile-only` in `apps/site` and commit the lockfile, as [#596](https://forgejo.webgrip.dev/webgrip/unfold/pulls/596) did. `scripts/workflow-policy.test.cjs` names the mismatch. |
| `release-policy` fails `unfold-mcp's end-to-end suite runs … an Authentik of the homelab's version` with `CI and the local compose file run the same Authentik` after a Renovate update | Renovate moved the nightly job's Authentik (`harbor.webgrip.dev/ghcr/goauthentik/server`) and not `apps/unfold/test/e2e/authentik.compose.yaml`: `ignorePaths` held `**/test/**`, which hid the compose file from every manager, and the docker-compose manager does not read a file named `authentik.compose.yaml` (#593; [#597](https://forgejo.webgrip.dev/webgrip/unfold/pulls/597) aligned them by hand). The compose file's Postgres had drifted the same way. | `renovate.json` ignores only `**/test/fixtures/**` and reads the compose file with two regex managers that name each image after the job's Harbor image, so both pins are one dependency and one update. A Renovate 44.176.2 `--dry-run=extract` lists both files under the same names. The workflow policy test fails when the pins differ or a pin escapes Renovate. |
| `ploeg-pin` or another short job hits its `timeout-minutes` while mise downloads Node, Go and Helm, although its `mise-action` sets `install_args: uv` | `mise exec -- <command>` installs every missing tool in `mise.toml` before it runs, so the job downloads the whole toolchain (release train run 2898, mise 2026.10.22). | Name the tool: `mise exec uv -- uv run …`. A job that installs one tool runs only that tool. |
| `checks` dies in under a minute with `<tool>@<version> is not in the lockfile` | A tool version in a `mise.toml` changed without `mise.lock`, and CI's install refuses a tool the lockfile does not hold. | Run `mise install` from the root and commit `mise.lock` with the change. |
| A `fix(ploeg)` pull request has a red `ploeg-docs` with `Stale decision register`, a stale combined glossary or `Stale landscape`; Renovate reports `Artifact file update failure` | The new Ploeg release adds an ADR or changes its domain model, and these pages are generated from the pinned contract bundle (run 1400, rc.16). On [#369](https://forgejo.webgrip.dev/webgrip/unfold/pulls/369) Renovate logged `Post-upgrade command './scripts/renovate-ploeg-docs.sh' has not been added to the allowed list in allowedCommands` and ran nothing. | Since [ADR-0041](../adr/adr-0041-a-ploeg-release-opens-unfolds-pin-pull-request-by-running-unfolds-recipe.md), Ploeg's release runs the script through `scripts/consume-ploeg-release.sh`. For the landscape, which needs a browser, and whenever the script could not regenerate a page, run `mise run domain`, `mise run docs-decisions` and `mise run landscape` on the branch and push. |
| A `build(ploeg)` pull request has a red `ploeg-docs` with `Combined glossary conflicts` and adds `ploeg-glossary-conflicts.txt`; Renovate may also report an artifact failure on older branches | The new Ploeg release defines a term Unfold's model also defines (rc.17: Tenant and Client). No regeneration can fix that. | Follow [the term clash steps](ci.md#the-ploeg-pin-pull-request) on the Renovate branch, as [#339](https://forgejo.webgrip.dev/webgrip/unfold/pulls/339) did, then delete the report. |
| The nightly `ploeg-behind` job fails with `pins Ploeg <x>, but <y> is the newest release` | Ploeg published a release whose pin pull request has not merged: it is open and red, or Ploeg's `consumers` job did not run (its `RELEASE_CONSUMERS` variable or `RELEASE_CONSUMER_TOKEN_FORGEJO` secret is missing, or the job failed, such as Cloudflare answering its requests with error 1010). | Open the `ploeg/<y>` pull request and fix what holds it. A green pin waits for the next **[Workflow] On Release Train**, whose `merge-pin` job merges it; its log says why it skipped one. When there is none, dispatch Ploeg's `Release consumers` workflow with `v<y>`, which runs the current delivery script, or run `scripts/consume-ploeg-release.sh <y>` on a branch and open the pull request by hand. |
| A unit test fails only in CI with a fixed short limit in its message, such as `opencode serve inside registry.example/agent:1.18.30 did not answer /global/health within 8s` (release train run 2399), or compares against a time taken when the module loaded (run 2362, fixed in [#580](https://forgejo.webgrip.dev/webgrip/unfold/pulls/580)) | The test bounded real work (a fake engine, a relay, a spawned process, loopback HTTP) with a literal that fits an idle workstation. The shared runners are short of CPU, so the work finishes, just later than the literal. | Bound waits with `scaledTimeout`, `deadlineAfter`, `waitFor` or `testTimeout` from `apps/unfold/test/timeframes.ts`; CI's verify action sets `UNFOLD_TEST_TIMEOUT_SCALE` to 2. A limit a test means to hit, against a fake that never answers, still fires, only later. Keep observation windows whose idle limit is fixed (the relay's idle-cut test) literal: a longer window there exposes more of the runner's pauses. `test/test-bounds.test.ts` fails on a test-level `timeout:` that is a literal. |
| Unit tests that take well under a second locally time out after 30 or more seconds in `checks-unfold`, a different few each run (release train runs 3173 and 3201) | The runner's node writes to a saturated system disk: on 2026-10-31 fringe-workstation's `sda` was 79–98% busy while every other node's disks were under 6%. Each test's data directory, SQLite file and fsync then wait on that disk. | The verification action keeps `TMPDIR` in memory under `/mnt/ci-shared`; its log says `Scratch files go to …`. When it says the mount is not writable, the runner pod lost that volume in homelab-cluster. Check disk busy time with `rate(node_disk_io_time_seconds_total[2m])` in Grafana before raising a timeout. |
| A test waiting for a process to disappear times out only in CI | The runner's PID 1 never reaps orphans, so a killed process stays a zombie and `kill(pid, 0)` keeps succeeding. | Treat state `Z` in `/proc/<pid>/stat` as gone. Reproduce with `unshare --user --map-root-user --pid --fork --mount-proc node --test <file>`. |
| A publish step answers `GET ghcr.io … 401` at the anonymous pull check | The GitHub package exists but is private; new GHCR packages start private. | Check with `curl -s -o /dev/null -w '%{http_code}' "https://ghcr.io/token?service=ghcr.io&scope=repository:webgrip/<package>:pull"` (200 public, 401 private, 403 absent). The owner changes the visibility in GitHub, then re-runs the job. |
| A release hangs about 30 minutes, then `context deadline exceeded` | Something still addressed the old repository name: Forgejo's redirect turned a POST into a GET, and a `git ls-remote` to a deleted repository waited for credentials (run 750). | Use `webgrip/unfold` everywhere; the publisher sets `GIT_TERMINAL_PROMPT=0` and fails on a redirected write. |
| Release assets answer HTTP 500 `unable to seek`, registry pushes answer 400, or a job is reaped after "Job succeeded" | Forgejo's object storage is full or failing; writes appear to succeed. | Not a pipeline problem. Free the storage (cluster runbook), then re-run the failed publish jobs. |
