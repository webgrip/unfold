## Verdict

**T3 Code is an adjacent product, not a dependency and not a substitute. Do not build Unfold's developer cockpit to compete with it. Meet it from above: make a T3 Code thread show up in Unfold as a Linked Session, give its agents `unfold-mcp`, and mine five of its designs into the review and Linked Session work.**

T3 Code is a single person's control surface for the coding agents on their own machines: an Electron desktop app, a web app, iOS and Android apps, and a `t3` server that drives ten harnesses, Claude through the Claude Agent SDK and Codex through `codex app-server` among them. It is free, MIT-licensed, and fast-moving. It has no Work Item, no tracker on `main`, no money budget, no team identity, and no sandbox of its own. It covers the **interactive half** of what Unfold does, for one person, very well. It does not touch the half that Unfold and Ploeg exist for: an authorized, budgeted Run against a Work Item that ends in a pull request a different person reviews.

The two verdict axes, stated separately:

* **Maturity** is high in velocity and low in governance. 771 releases since March, a stable every one to five days since v0.1.0 on 15 October, about 40,000 stars and about 2.1 million installer downloads. One founding engineer writes 34 % of the last 30 days' commits and Theo Browne 11 %; outside contributions are "(mostly) not accepted", there is no CLA, and the stable line is still 0.1.
* **Fit** decides. T3 Code claims the seat in front of the developer that Unfold's Session page and VS Code Agents window also want. It claims none of the seats Ploeg holds. The overlap is real, the competition is lopsided, and the honest response is to stop competing at the cockpit and integrate with it.

**Absences.** Across T3 Code's code, docs and issues there are zero mentions of Unfold, Ploeg, Vikunja, Kubernetes, KEDA or A2A. LiteLLM appears only as the source of a model price table, not as a gateway. Linear, Jira and every other tracker are absent from `main`; five open pull requests propose them. Multi-user self-hosting was closed as not planned. **Forgejo and Gitea are supported**, through the `fj` and `tea` CLIs, which puts T3 Code on our own forge. Name collisions to keep apart: create-t3-app and the T3 Stack, T3 Chat, `t3.gg`, the `t3` npm package, and look-alike forks.

Summary:

1. **What it is.** "An agent harness control surface" that "enables control of the agents on your machine" from desktop, web and mobile, over an event-sourced SQLite server ([section 1](#1-what-t3-code-is)).
2. **Overlap is the interactive Session.** Live transcript, diffs per turn, approvals, model choice, steering and PR creation are all in T3 Code, plus things Unfold lacks: a terminal, plan mode, checkpoints with revert, a mobile app and ten providers ([section 3](#3-feature-by-feature)).
3. **Money.** T3 Code estimates cost after the fact from LiteLLM's public price table and enforces no budget anywhere ([1.3](#13-money)).
4. **Isolation.** One environment, one owner. The default permission mode is Full access, and sandboxing is left to each provider ([1.4](#14-security-in-its-own-words)).
5. **Danger: it takes the developer's seat.** Developers who live in T3 Code, the Codex app or Claude Code desktop will not open Unfold to steer an agent ([section 4](#4-dangers)).
6. **Opportunity: north of it.** Unfold already reports Claude Code, Codex, OpenCode and ACP sessions as Linked Sessions. T3 Code drives exactly those harnesses, and its Claude threads load the repository's Claude Code settings, so its threads probably report already; its agents can call `unfold-mcp`; and every gap it leaves (budgets, teams, trackers, Kubernetes, review gates) is a column Unfold and Ploeg fill ([section 5](#5-the-one-honest-scenario)).
7. **Worth taking.** Review guides with "Look closely" stops, a diff that shows only one turn's work, PR watching that settles the thread on merge, scoped per-session MCP credentials, and read-only guest links ([section 6](#6-design-worth-mining)).

## 1. What T3 Code is

### 1.1 Self-description and surfaces

The [README](https://github.com/pingdotgg/t3code/blob/main/README.md) says: "T3 Code is an "agent harness control surface". It enables control of the agents on your machine with a best-in-class mobile app (iOS, Android), web app and Electron-based desktop app." Its `AGENTS.md` says: "T3 Code is a minimal GUI for coding agents. A Node WebSocket server wraps provider CLIs and agents … and serves web, desktop, and mobile clients." The [homepage](https://t3.codes) calls it "The open-source control plane for coding agents." It names its own inspirations: "the Codex desktop app, Conductor, Claude Desktop and Cursor Glass, but none met our bar."

| Surface | What it is | Relevant to Unfold as |
| --- | --- | --- |
| `t3` server and CLI | npm `t3` (0.1.6, about 115,000 downloads a month); `t3 serve`, `t3 up`, `t3 service install` on a laptop or a VPS | Where the agents actually run: the developer's machine |
| Desktop app | Electron 44, bundles the server | The cockpit a developer opens instead of Unfold |
| Web app | React 19, served locally or from `app.t3.codes` | Same |
| Mobile apps | Expo / React Native, iOS and Android, remotes onto an environment | Push on "finished, failed, needs approval, asks for input" |
| Remote access | LAN, Tailscale, SSH, or T3 Connect (a Ping-hosted Cloudflare relay with Clerk sign-in) | Remote-first; no self-hostable relay found |
| Orchestrator MCP | `/mcp` on the server with OAuth: create, list, read, message, steer, wait on and interrupt threads; delegate a task to a child agent on any provider | A way for an outside agent to drive T3 Code |
| Providers | Codex (`codex app-server` over JSON-RPC), Claude (`@anthropic-ai/claude-agent-sdk`), Cursor (`@cursor/sdk`), OpenCode (SDK, 1.x and 2.x), Pi, Muse, and Grok, Antigravity, fx and any ACP Registry agent over ACP | The harness breadth Ploeg's `acp` adapter is building towards on the server side |

Its abstractions, as its [glossary](https://github.com/pingdotgg/t3code/blob/main/docs/internals/glossary.md) spells them: Environment, Client, Project, Workspace root, Worktree, Thread, Turn ("a V2 run"), Activity, Provider, Driver, Provider instance, Adapter, Session, Runtime mode (the permission policy), Interaction mode (planning), Checkpoint ("stored as a hidden Git ref"), Turn diff, Pull request link. A Thread is the closest thing to our Session; a Turn is closer to one prompt-and-response than to a Run, because it carries no budget and no outcome.

### 1.2 Architecture

A pnpm workspace in TypeScript on Effect 4, on Node. Every wire type is an Effect Schema in `packages/contracts` (106 files, 209 RPC methods), carried over Effect RPC on a WebSocket. Clients read a snapshot at a sequence number and stream newer events. State is event-sourced into `statev2.sqlite`: the orchestrator decides events without I/O, one transaction commits the event, its projections, the command receipt and an outbox entry, and a worker runs side effects after the commit ([2-repo-dig.md](evidence/2026-11-02-t3code/2-repo-dig.md), section 3). Checkpoints are hidden git refs under `refs/t3/orchestration-v2/checkpoints`. Worktrees are one per thread. The terminal is `node-pty` on the server, rendered in the browser with libghostty compiled to WebAssembly.

Pull requests are opened per forge: GitHub through its REST API, GitLab through `glab`, Forgejo and Gitea through `fj` or `tea`, Azure DevOps through `az`, Bitbucket through its API. The server watches each linked pull request, polling every two minutes, wakes the agent on review activity, and settles the thread when the pull request merges or after three idle days.

### 1.3 Money

T3 Code shows tokens per turn and a Usage page with an estimated cost at API prices. It reads the prices from LiteLLM's public `model_prices_and_context_window.json`, lets the user override them per environment, and also reads Claude's own `costUSD`. Its docs say: "These estimates are not your subscription bill." It reads the provider's subscription windows as percentages and resumes a thread when a limit resets. It enforces no budget: there is no per-thread, per-project or per-person cap, and the Claude Agent SDK's budget option is not used. The most-discussed issue, [#7338](https://github.com/pingdotgg/t3code/issues/7338), reports Claude usage "~3x-5x higher than the native Claude app" through the Agent SDK; the FAQ now concedes the difference. Per-thread cost display ([Ideas #13073](https://github.com/pingdotgg/t3code/discussions/13073)) and gateway spending budgets ([Ideas #15042](https://github.com/pingdotgg/t3code/discussions/15042)) are open ideas.

### 1.4 Security, in its own words

Four permission modes: Supervised, Auto-accept edits, Auto, and Full access. "The initial default is **Full access**" ([permission-modes.md](https://github.com/pingdotgg/t3code/blob/main/docs/user/permission-modes.md)). T3 Code has no sandbox of its own; each provider enforces permissions its own way, and its managed policy "is not a sandbox". A pairing token issued without scopes carries every permission, and a full-access agent on the host can reach those permissions too. Outside MCP agents default to read-only. Webhook payloads are marked untrusted, without a guarantee that the agent ignores them. The security policy of 15 July 2026 puts the user in charge of "Reviewing commands, source changes, and other agent output". Telemetry is on by default and goes to PostHog through `ingest.t3.codes`, with provider, model, permission mode and token counts and without prompts or code; [#4123](https://github.com/pingdotgg/t3code/issues/4123) notes this contradicts an earlier opt-in promise.

### 1.5 Maturity and governance

Created 8 February 2026, first alpha 2 March, open to everyone around 7 March, v0.1.0 "Orchestrator V2 is now stable" on 15 October, v0.1.6 on 31 October with 521 changes from 137 contributors. Releases per month climbed from 27 in March to 163 in October, most of them nightlies. 40,062 stars, 9,010 forks, 1,533 open issues and 2,606 open pull requests on 2 November. All-time, the founding engineer holds 44 % of counted commits and the six named maintainers 64 %. Licence: MIT, "Copyright (c) 2026 T3 Tools Inc." No funding round was found beyond a 2022 pre-seed reported by aggregators. User counts are self-reported and growing: 60,000 in June, 100,000 in August, "500,000 devs" on the homepage now; none can be checked ([3-ecosystem-and-absences.md](evidence/2026-11-02-t3code/3-ecosystem-and-absences.md)).

### 1.6 Reception and its dependence on the labs

Added 3 November 2026 from a second, reception-focused search. The picture is warm among users and fragile underneath.

* **Users.** Reviews are positive with caveats. Flavio Copes' [deep dive](https://flaviocopes.com/t3-code/) (updated 1 November 2026) says "T3 Code gives me one place to see and direct the coding agents I already use", and warns "expect bugs, unfinished edges, and frequent changes", "Full access gives the agent full access on that machine" and "A checkpoint is not a backup"; it lists "hosted multi-user teams" as a poor fit. On Hacker News it appears only in passing, listed next to Goose and Paseo as a similar product ([item 49944576](https://news.ycombinator.com/item?id=49944576)) and offered as a Linux alternative to Conductor. No Hacker News launch thread was found. Reddit could not be searched from this environment.
* **The Anthropic dependency is the biggest risk.** T3 Code's Claude support runs on the Claude Agent SDK with the user's own subscription. In April 2026 some T3 Code users reported Claude bans, which Theo Browne's contacts at Anthropic called an error ([daily.dev](https://daily.dev/posts/t3-code-got-banned-from-claude--fwselnkdq)). In May, Anthropic announced that Agent SDK use would move to a separate monthly credit on 15 June. Browne said it cut T3 Code users' value "by 25 to 40 times" and called it "an attack on open source" ([BigGo summary](https://finance.biggo.com/news/382b1ef1c37acfb3), 14 May 2026). Anthropic paused the change on 15 June ([Zed](https://zed.dev/blog/anthropic-subscription-changes)) and on 7 October added monthly API credits for Agent SDK work on Max and Team plans, while subscription use stays allowed ([Startup Fortune](https://startupfortune.com/anthropic-quietly-separates-claude-agent-sdk-usage-from-subscription-limits/), 26 October 2026). Anthropic's own [legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) still says advertised plan limits "assume ordinary, individual usage of Claude Code and the Agent SDK", that third-party developers may not "route requests through Free, Pro, Max, or Ultra plan credentials on behalf of their users", and that Anthropic "may do so without prior notice" when it enforces. T3 Code works because each user signs in on their own machine. That is the same line [ADR 0047](../../apps/unfold/docs/adrs/0047-people-link-their-own-agent-sessions-through-a-plugin-agent-trace-and-telemetry-never-a-claude-sign-in.md) draws for Unfold.
* **No revenue.** Browne, on 29 October 2026: "we don't make any money off it", it is "quite expensive for us to run", and a paid tier for more than three T3 Connect devices is coming so as not to "bankrupt ourselves on an open source project" ([episode summary](https://finance.biggo.com/podcast/fc37ed5cc8193fef)). The project relies on the labs continuing to allow subscription use in third-party tools.
* **Telemetry and defaults draw pushback.** Telemetry on by default led to fork pull requests that switch it off ([t3-devcontainer-feature #1](https://github.com/Portals/t3-devcontainer-feature/pull/1), [t3code-nix #3](https://github.com/Airradda/t3code-nix/pull/3)), a privacy rebuild with telemetry removed and an egress sandbox ([t3blackout](https://github.com/bmjcoding/t3blackout)), and an upstream toggle proposal that keeps the default on ([#21248](https://github.com/pingdotgg/t3code/pull/21248)). No CVE or security advisory for T3 Code was found.
* **Open-source governance is closed in practice.** [CONTRIBUTING.md](https://github.com/pingdotgg/t3code/blob/main/CONTRIBUTING.md) says the project is "not actively seeking outside contributions", that opening a pull request creates no obligation to review it, and that pull requests are closed when Gemini or Muse Wonder wrote the code. Forks carry what upstream will not take.
* **The other labs copy it.** One podcast summary says the Codex team publicly cited T3 Code as inspiration for features in its own app ([BigGo](https://finance.biggo.com/news/fc37ed5cc8193fef)). Its strongest features have a short half-life as differentiators.

What this changes for Unfold: the honest scenario in section 5 holds, but recommending T3 Code to an Agency's developers inherits Anthropic's enforcement risk on their personal subscriptions. An Agency guide should prefer API keys under the Agency's own Console organization for client work. And T3 Code's cockpit lead is contested by the labs' own apps, which strengthens recommendation 4: do not compete at the cockpit.

## 4. Dangers

1. **The developer's seat is taken, for free.** A developer who already lives in T3 Code, the Codex app, Claude Code desktop or Cursor will not open Unfold's Session page to steer an agent. T3 Code ships a stable every few days and covers ten harnesses on three device classes. Unfold's interactive surface ([ADR 0044](../../apps/unfold/docs/adrs/0044-sessions-run-in-ploeg-with-a-harness-chosen-per-session-and-interaction-kept.md), [ADR 0012](../../apps/unfold/docs/adrs/0012-agent-host-protocol-host.md)) is worth building only for work that needs Ploeg's authority, not as a general cockpit.
2. **Linked Sessions depend on how T3 Code starts each harness.** Unfold reports Claude Code through its plugin, Codex through hooks in `~/.codex/hooks.json`, OpenCode 1.x through a plugin in its plugins folder, and ACP agents through `unfold-acp` ([linked-sessions.ts](../../apps/unfold/src/linked-sessions.ts), [Link your OpenCode and Codex sessions](../how-to/link-opencode-and-codex-sessions.md)). T3 Code starts Claude through the Agent SDK, Codex through `codex app-server`, OpenCode through `opencode serve` and ACP agents itself. Whether each of those paths runs our reporter is unproven. If none does, a Work Item worked in T3 Code leaves no state, Agent Trace or cost in Unfold. Cursor, Pi and Muse threads have no reporter at all.
3. **Cost numbers from T3 Code's Claude threads may disagree with the native app.** If #7338 holds, a Claude Code session run through T3 Code burns three to five times the tokens of the same work in the native app. A Linked Session's cost estimate would then be right about the session and wrong about the developer's normal cost. Say so on the session page if the plugin reports that it runs under the Agent SDK.
4. **Agency hygiene.** For an Agency's developers working on client code, T3 Code defaults to Full access, has no sandbox, and sends telemetry to a US analytics service by default. None of that is ours to fix, but an agency onboarding guide should name the two settings: a non-Full-access default and `T3CODE_TELEMETRY_ENABLED=false`.
5. **The flip toward our loop.** The day T3 Code merges an issue tracker ([#19259](https://github.com/pingdotgg/t3code/pull/19259), [#19261](https://github.com/pingdotgg/t3code/pull/19261) with Forgejo, [#19274](https://github.com/pingdotgg/t3code/pull/19274) Linear), Docker sandboxes ([#15350](https://github.com/pingdotgg/t3code/pull/15350), by Theo) and remote environments ([Ideas #18019](https://github.com/pingdotgg/t3code/discussions/18019)), it becomes a single-player version of "ticket to thread to pull request". It still would have no budget before spend, no second person who reviews, and no tenant. Those three are the moat to keep sharp, and section 8 makes each of them a trigger.

## 5. The one honest scenario

**A developer works a Work Item in T3 Code; Unfold sees it as a Linked Session and the agent reads the Work Item through `unfold-mcp`.** Nothing Ploeg-shaped runs, and nothing new is built for T3 Code specifically.

Why it probably half-works today: T3 Code's Claude adapter passes `settingSources: ["user", "project", "local"]` to the Claude Agent SDK, or `["project", "local"]` when the thread uses a custom home (`ClaudeAdapterV2.ts`, lines 4591 and 4621). The repository-level `.claude/settings.json` path in [Link your Claude Code sessions](../how-to/link-claude-code-sessions.md) is therefore read in both cases, and the user-level `env` block with `UNFOLD_URL` and `UNFOLD_TOKEN` in the default case. Whether the Agent SDK then loads an enabled plugin's hooks, and whether the plugin's events can tell a T3 Code thread from a terminal session, is **not verified**; it is the first ticket in section 10.

The other harnesses are open in the same way. Codex hooks load from the user's Codex home, but whether `codex app-server` runs them as the CLI does is not documented in either project. An OpenCode 1.x plugin in `~/.config/opencode/plugins/` loads in `opencode serve`, which is what T3 Code talks to, so that path is likely; OpenCode 2 is not supported by our plugin. T3 Code is itself an ACP client, so it would have to start `unfold-acp` in front of an agent for that path, which it does not offer. The probe in ticket 1 covers Claude, Codex and OpenCode in one sitting.

The tension, named: a Linked Session is a session "Unfold never starts, steers or pays for" ([glossary](../reference/glossary.md#linked-session)). T3 Code's orchestrator MCP would let Unfold start and steer threads on a developer's machine. That would break the definition and put unbudgeted, unsandboxed execution under Unfold's name. The shape that survives is read-only in Unfold's direction: T3 Code's thread reports to Unfold; Unfold never calls T3 Code's MCP with write tools. A person may of course give a T3 Code agent `unfold-mcp`, whose actions already need confirmation ([ADR-0037](../adr/adr-0037-people-act-on-work-through-either-mcp-server-and-every-action-names-its-person-channel-and-confirmation.md)).

## 6. Design worth mining

1. **Review guide with "Look closely" stops.** "Each stop points at the lines worth reading, and a stop marked **Look closely** has a call only a maintainer can make. Mechanical changes such as renames and snapshots are grouped at the end, and every changed file appears somewhere on the tour" ([source-control.md](https://github.com/pingdotgg/t3code/blob/main/docs/user/source-control.md)). That is the developer-facing twin of ADR-0054's Walkthrough, which is aimed at a non-technical reviewer. Two properties are worth copying exactly: every changed file is accounted for, and the stops that need a human judgement are marked as such. This fits [ADR-0010](../adr/adr-0010-pull-requests-are-small-whole-and-explained.md) and Ploeg ADR-0125's Walkthrough report.
2. **A diff that shows only one step's work.** T3 Code's Turn diff is computed between checkpoints, so a reviewer sees what one turn changed rather than the branch so far. The Unfold equivalent is a per-Run diff on a multi-Run Shift: what the reviewer Role's fix changed on top of the writer's work. Ploeg already records the Candidate per Run; this is a presentation choice.
3. **PR watching that wakes the agent and settles on merge.** `watch_pull_request` polls every two minutes, wakes the agent on review activity, and settles the thread on merge or after three idle days. Unfold just made an approved Work Item with an open pull request wait for the merge (#527). The missing half is the wake-up: review comments on the open pull request becoming a bounded follow-up Run. That half belongs in Ploeg and is close to the CI-repair proposal in the [C4 views](../landscape/c4.md).
4. **MCP credentials scoped to one session.** T3 Code mints a credential per provider session, scoped to the environment, the thread, the provider instance and the session, expiring when idle and revoked when the session ends ([orchestrator-mcp-server.md](https://github.com/pingdotgg/t3code/blob/main/docs/orchestration-v2/orchestrator-mcp-server.md)). A Linked Session today uses the person's 30-day `vle_` editor credential. A per-session credential minted at `SessionStart` would limit what a leaked hook token can do. It is worth one look when ADR 0047 moves from proposed to accepted.
5. **Read-only guest links.** An HMAC link that shows one thread read-only for 24 hours. For phase 2 this is the cheapest version of "show the Client what was done" before any Client Portal exists ([ADR-0007](../adr/adr-0007-clients-approve-ready-work.md)), and it maps onto a Work Item page with the Walkthrough. It must never expose cost or other Clients' work.

Not worth taking: the Electron and mobile apps, the interactive terminal, the multi-provider fan-out from one prompt (N times the spend for one Work Item, against the Shift Budget), event sourcing in SQLite (Ploeg is the system of record), and T3 Connect (a third-party relay in front of client code).

## 7. Implementation path, cheapest first

1. **Probe the three paths.** Run one short T3 Code thread each with Claude, Codex and OpenCode, with our reporters installed as the how-tos describe, and check which appear as Linked Sessions. Zero spend beyond three short sessions on the owner's own subscriptions.
2. **Document what works** in the Linked Sessions how-to: "From T3 Code" with the settings that matter, including the two agency settings from danger 4. Add `unfold-mcp` to the outside-agents setup next to it.
3. **Fix only what the probe shows broken**, as change tickets on the existing Linked Sessions epic.
4. **Mine 6.1 and 6.2** into the Walkthrough and review work, when that work is next picked up.
5. **Raise 6.3** in ploeg-hq as a proposal next to the CI-repair item.

Never:

* Call T3 Code's orchestrator MCP with write tools from Unfold or Ploeg. A Linked Session is never started or steered by Unfold.
* Build a desktop, mobile or terminal cockpit to match T3 Code.
* Read cost from T3 Code's Usage page as a settled figure. It is an estimate at public API prices.
* Route an Agency's Run through a developer's T3 Code environment. It has no budget, no sandbox and no tenant.
