## 3. Kanban task lifecycle, worker lifecycle, budgets, review, decomposition, PR gates

All from https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban unless noted.

**Status enum (verbatim):** `triage | todo | ready | running | blocked | review | done | archived`.

**Transitions (from the "Event reference", "Core concepts" and CLI sections):**
- `created` → task inserted (`triage` via `--triage`/dashboard Triage column, `todo` when parents open, `ready` when assigned with no open parents).
- `triage` → **decompose** (built-in decomposer, `kanban.auto_decompose: true` default) produces child graph; original task "becomes the parent of every leaf […] and then promotes back to `ready`"; or **specify** ("one-shot spec rewrite […] and promotes to `todo`"). Children "automatically promoted to `ready`" when `kanban.auto_promote_children: true` (default).
- `promoted`: `todo → ready` "because all parents hit `done`".
- `claimed`: `ready → running` (dispatcher atomic claim; creates a `task_runs` row).
- `completed`: `running → done` via `kanban_complete` (or CLI `complete`, dashboard "mark done").
- `review_requested`: `running → review` via `kanban_request_review` ("this is not a block"); CLI `request-review` accepted "from `ready` as well as `running`".
- `changes_requested`: `review → ready/todo` ("routes the task to its original implementer without block-loop accounting"); `review_reopened` via `hermes kanban reopen-review`.
- Reviewer approve: `review → done` via `kanban_complete`.
- `blocked`: `running → blocked` via `kanban_block(kind=needs_input|capability|transient)`; `kind=dependency` with an open parent → `dependency_wait` → `todo` (auto-resumes); with no open parent recorded as `needs_input`.
- `block_loop_detected`: unblocked and re-blocked for the same reason `BLOCK_RECURRENCE_LIMIT` times (default 2) → routes to `triage`.
- `unblocked`: `blocked → ready` (or `todo` if parents open; or `review` — "restore a blocked task to its source phase (`review` or `ready`)").
- `reclaimed` (claim TTL expired, dead PID) / `crashed` / `timed_out` / `stale` / `reconciled` / `spawn_failed` / `protocol_violation` (below bound) → back to `ready`.
- `gave_up` (circuit breaker) → `blocked`; `terminal_provider` variant is "sticky — `recompute_ready` will not auto-resume it".
- `respawn_guarded`, `skipped_nonspawnable`, `rate_limited` → stays `ready`.
- `status` (dashboard drag, e.g. `todo → ready`, `done → ready` re-queue; dragging off `running` closes the run as `outcome='reclaimed'`); `archived` (hidden; running task's run reclaimed).
- Completion refuses when a direct parent is not `done`/`archived` ("there is no force path through the dependency gate"); live-claim guard: a `running` task is completed only by its worker or `--force`.

**Worker lifecycle terminators** (https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-worker-lanes): "Every claim must end in exactly one of: `kanban_complete(summary=..., metadata=...)` […] `kanban_request_review(summary=..., metadata=..., reviewer=...)` […] `kanban_block(reason=...)` […] The worker process exits without a tool call. The kernel reaps it and emits `crashed` (PID died) or `gave_up` (consecutive-failure breaker tripped) or `timed_out` (max_runtime exceeded)." Reviewers end with `kanban_complete` or `kanban_request_changes` (or `kanban_block` for external escalation). Exit codes (kanban page): exit `0` while still `running` = `protocol_violation`; `1` ordinary failure; `75` (`EX_TEMPFAIL`) provider rate-limit/5xx/billing wall → run `rate_limited`, requeued "without counting a failure"; `78` (`EX_CONFIG`) credential/model/TLS rejection → `crashed` with `exit_kind: terminal_provider`, breaker trips on first occurrence. "Agent-side prevention: […] up to two synthetic nudges when it detects the model is about to stop without a terminal board tool call" (disable `HERMES_KANBAN_STOP_NUDGE=0`).

**Iteration budget / `budget_warning_ratio`:** "Dispatcher-owned workers get one checkpoint notice near 90% of their finite iteration budget, attached to a fresh tool result while another tool-capable call remains. Use `agent.budget_warning_ratio` to choose an earlier threshold. […] A commit or diff alone never automatically completes a task. The hard cap, toolless final summary, and consecutive-failure circuit breaker are unchanged […] This is a reporting opportunity, not a guarantee that a model will heed the notice. Ordinary conversations and delegated children do not inherit the automatic Kanban checkpoint; their iteration warning remains opt-in." Configuration page: "`agent.max_turns` is **unlimited by default**" (`max_turns: none`), "`agent.budget_warning_ratio` is off by default […] When set to a value strictly between `0` and `1` alongside a finite `max_turns`, Hermes appends one model-visible checkpoint notice". **Docs inconsistency:** the same page's prose says "it can burn through its iteration budget (default: 500 turns)" and "when the budget is actually exhausted (500/500), Hermes injects one message asking the model to wrap up and allows a single **grace call**". Subagents: "iteration limit (default: 250)" (`delegation.max_iterations`, delegation page) vs "capped at `delegation.max_iterations` (default 50)" (agent-loop page) — second inconsistency. — https://hermes-agent.nousresearch.com/docs/user-guide/configuration ; https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation ; https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop

**Circuit breaker:** "After `kanban.failure_limit` consecutive spawn failures on the same task (default: 2) the dispatcher auto-blocks it"; per-task `--max-retries N` overrides ("`--max-retries 1` blocks the task on the first non-successful attempt"); protocol violations bounded by `_PROTOCOL_VIOLATION_FAILURE_LIMIT` (default 3) consecutive; automatic reclaim "counts as one non-successful attempt"; `stale` "does NOT tick the failure counter"; respawn guard reasons `blocker_auth`, `recent_success`, `active_pr`, `rate_limit_cooldown`, `infrastructure_cooldown` (`HERMES_KANBAN_RATE_LIMIT_COOLDOWN_SECONDS` default 300 s). Tutorial Story 4 shows `spawn_failed → spawn_failed → gave_up`. — https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-tutorial

**`max_runtime`:** CLI `--max-runtime 30m|2h|1d|<seconds>`; "**Per-task max runtime** — `task.max_runtime_seconds` hard-caps wall-clock time per run, regardless of PID liveness"; `timed_out` = "dispatcher SIGTERM'd (then SIGKILL'd after 5 s grace) and re-queued". No default value documented. Related timers: claim TTL `DEFAULT_CLAIM_TTL_SECONDS` 15 min (only dead PIDs reclaimed); `kanban.dispatch_stale_timeout_seconds` default 4 h with no `kanban_heartbeat` in the last hour; `kanban.stranded_threshold_seconds` default 30 min; `kanban.max_in_progress`/`max_in_progress_per_profile` unset = unlimited.

**Goal-mode cards:** "Pass `--goal` (CLI) or `goal_mode=True` […] after every turn an auxiliary judge checks the worker's output against the card's title + body […] the worker keeps going **in the same session** until the judge agrees, the worker terminates the task itself, or the budget runs out (which **blocks** the card for human review rather than exiting silently). If the judge rules the goal **unachievable** as written, the card is blocked immediately". `--goal-max-turns N` "optional; default 20". "If the judge call itself fails — relay error, auth, timeout — the handoff is allowed". "Goal-mode cards borrow the `/goal` engine — they don't connect to it". `/goal` itself: turn budget `goals.max_turns` default 20; judge verdicts `done | blocked | continue | wait`; "Fail-open semantics […] a broken judge never wedges progress. The **turn budget** is the real backstop."; quality gates = deterministic shell commands that must exit 0 (3 retries, 5-min timeout each). — https://hermes-agent.nousresearch.com/docs/user-guide/features/goals

**What "review" means:** "Same-card review: call `kanban_request_review(...)`. The task enters `review` without touching block recurrence accounting. The dispatcher claims it with the bundled `sdlc-review` skill by default. The reviewer approves with `kanban_complete`, calls `kanban_request_changes(reason=...)` to close the review run and route the task back to its original implementer, or blocks only for a genuine external escalation." "Human-only boards: set `kanban.review_dispatch: false`." Hierarchy: "Reviewer = human or human-proxy that gates 'done'". Reviewer provenance: "the persisted reviewer provenance routes the re-review back to the same reviewer profile". — https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-worker-lanes ; https://hermes-agent.nousresearch.com/docs/user-guide/skills/bundled/devops/devops-sdlc-review
**sdlc-review skill** (v1.1.0, bundled, `skills/devops/sdlc-review`): "Independently verify work handed from a Kanban implementation run to the review lane, then approve it, request changes, or escalate." "Treat the handoff as a claim to verify, not as proof that the work is correct." Round-based lenses: round 1 Artifact (read the diff cold), round 2 Execution (check out and run it), round 3+ Contract (audit against original acceptance criteria and all prior `changes_requested`). Verdict table: Approve → `kanban_complete`; Request changes → `kanban_comment` then `kanban_request_changes`; Escalate → `kanban_block`.

**`auto_decompose`:** "**Auto (default)** — `kanban.auto_decompose: true`. The gateway-embedded dispatcher runs the **decomposer** on each tick, capped by `kanban.auto_decompose_per_tick` (default 3 tasks per tick) so a bulk-load of triage tasks doesn't burst-spend the auxiliary LLM. The decomposer uses […] the `auxiliary.kanban_decomposer` model path, reads your installed profiles + their descriptions, and asks the LLM to produce a JSON task graph". "The decomposer NEVER lands a child task with `assignee=None`". "**Important boundary:** Manual mode disables only the built-in Triage decomposer. It does not prevent a profile from calling `kanban_create`". Other keys: `orchestrator_profile`, `default_assignee`, `auto_subscribe_on_create` (default true), `auto_promote_children` (default true).

**PR completion contracts — what gates completion (verbatim):** "After publishing, pass `metadata.published_pr` to completion. The first matching URL binds the card permanently; retries cannot substitute a green sibling PR." "The shared `complete_task` boundary covers worker tools, CLI, review approval and dashboard completion. It reads classic branch protection and active ruleset required contexts, paginates exact-head check runs and legacy statuses, then re-reads the PR head/base. Optional failed/skipped telemetry does not veto accepted required checks. Missing, pending, failed, cancelled, timed-out, stale, skipped or neutral **required** evidence cannot complete the card. Neither can zero-run acceptance, unreadable policy or GitHub API failures. A repository without required checks needs a local-only contract. `gh` must be authenticated with read access to the repository's checks and rules; no remote writes are performed by this gate. Acceptance reads run as the **assignee profile's** `gh` login". "Rejection retains the active card and workspace. Durable `pr_acceptance` events store PR URL, SHA, required contexts, check IDs/URLs, classifications and recovery instructions". "The final GitHub read is a completion-time snapshot, not a distributed transaction or a continuous post-completion monitor. This is a single-user lifecycle guard, not OS isolation against arbitrary direct database writes. GitHub Enterprise is not covered. […] local verification and publication alone are not remote acceptance."

**Multi-gateway:** "Only one gateway owns the kanban dispatcher. […] every other gateway sets [`kanban.dispatch_in_gateway`] to `false`." "Review feedback never creates, unblocks, requeues, or otherwise mutates a task." — https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-multi-gateway
**Out of scope (verbatim):** "Kanban is deliberately single-host. `~/.hermes/kanban.db` is a local SQLite file and the dispatcher spawns workers on the same machine. Running a shared board across two hosts is not supported". Dashboard "Scope boundary": "Auto-assignment, budgets, governance gates, and org-chart views remain user-space — a router profile, another plugin, or a reuse of `tools/approval.py`". "Adding an external CLI worker lane […] is *not yet a paved path*" (worker-lanes page; refs issue #19931, closed PR #19924).

## 5. Security and isolation model

**Stated trust model (SECURITY.md, https://github.com/NousResearch/hermes-agent/blob/main/SECURITY.md):**
- "Hermes Agent is a single-tenant personal agent. Its posture is layered, and the layers are not equally load-bearing."
- "**The only security boundary against an adversarial LLM is the operating system.** Nothing inside the agent process constitutes containment — not the approval gate, not output redaction, not any pattern scanner, not any tool allowlist."
- Two postures: "Terminal-backend isolation" ("What this does **not** confine: everything the agent does in its own Python process. That includes the code-execution tool (spawned as a host subprocess), MCP subprocesses […], plugin loading, hook dispatch, and skill loading") and "Whole-process wrapping" (own Docker image/Compose, or NVIDIA OpenShell). "Operators running the default local backend with untrusted input surfaces, or running a terminal-backend sandbox and expecting it to contain code paths that don't go through the shell, are operating outside the supported security posture."
- Credential scoping: "This reduces casual exfiltration. It is not containment."
- In-process heuristics "are useful. They are not boundaries." (approval gate, output redaction, Skills Guard). "skills execute arbitrary Python at import time."
- Plugins "run with full agent privileges"; "A malicious or buggy plugin is not a vulnerability in Hermes Agent itself."
- External surfaces: "An allowlist is required for every enabled network-exposed adapter."; "Session identifiers are routing handles, not authorization boundaries."; "**Within the authorized set, all callers are equally trusted.** Hermes Agent does not model per-caller capabilities inside a single adapter. Operators who need capability separation should run separate agent instances with separate allowlists."
- Out of scope: "Bypasses of in-process heuristics", "Prompt injection per se", "Consequences of a chosen isolation posture", "Documented break-glass settings", "Community-contributed skills and plugins", "Public exposure without external controls". "**Hermes Agent does not operate a bug bounty program.**"

**Security page (https://hermes-agent.nousresearch.com/docs/user-guide/security):**
- "The security model has eight layers": user authorization; dangerous command approval; file write safety; container isolation; MCP credential filtering; context file scanning; cross-session isolation; input sanitization.
- **Approval modes** `approvals.mode: smart | manual | off` (default `smart`: "Use an auxiliary LLM to assess risk. Low-risk commands […] are auto-approved for that command only. Genuinely dangerous commands are auto-denied. Uncertain cases escalate to a manual prompt."); `timeout: 300`; `cron_mode: deny`, `single_query_mode: deny`, `unattended_mode: deny` ("webhook, msgraph_webhook, api_server […] `deny` blocks the command instantly […] Exception: an api_server session whose client can answer the card (`/v1/runs` and streaming chat completions, via `POST /v1/runs/{id}/approval`) still gets the approval request."). **YOLO**: `--yolo`, `/yolo`, `HERMES_YOLO_MODE=1`; "saved with the session, so it survives a restart".
- **Hardline Blocklist (Always-On Floor)**: refuses "**regardless** of `--yolo` […] `approvals.mode: off` […] Cron jobs running in headless `approve` mode […] User explicitly clicking 'allow always'"; patterns `rm -rf /`, `--no-preserve-root`, fork bomb, `mkfs.*` on mounted root, `dd […] of=/dev/sd*`, "Piping untrusted URLs to `sh`"; "fails closed on a command whose shell quoting cannot be parsed". Also `approvals.deny` user rules, permanent `command_allowlist`, and `hermes approvals suggest` which "scans the session database (`~/.hermes/state.db`) for dangerous-classified commands that actually executed".
- **Container bypass (verbatim):** "When running in `docker`, `singularity`, `modal`, `daytona`, or `vercel_sandbox` backends, dangerous command checks are **skipped** because the container itself is the security boundary. Destructive commands inside a container can't harm the host." Tips page: "dangerous command checks are **skipped** because the container is the security boundary. Make sure your container images are properly locked down." (https://hermes-agent.nousresearch.com/docs/guides/tips). Work-machine guide: "`docker` | Container — the container itself is the security boundary"; "Deny rules are a guardrail against an honest-but-wrong agent […] They are not a sandbox against a deliberately adversarial process" (https://hermes-agent.nousresearch.com/docs/guides/secure-hermes-on-a-work-machine).
- **Terminal backends table:** local (None — runs on host, check ✅), ssh (Remote machine, ✅), docker/singularity (Container, ❌ skipped), modal/daytona (Cloud sandbox, ❌), vercel_sandbox (Cloud microVM, ❌). Docker flags: `--cap-drop ALL` (+`DAC_OVERRIDE`,`CHOWN`,`FOWNER`), `no-new-privileges`, `--pids-limit 256`, size-limited `/tmp`, noexec `/var/tmp`; `container_cpu: 1`, `container_memory: 5120`, `container_disk: 51200`; `docker_forward_env: []` "Explicit allowlist only; empty keeps secrets out of the container". Seven backends are listed in README (local, Docker, SSH, Singularity, Modal, Daytona, Vercel Sandbox); third-party backends via plugins with `skip_container_guards`, `strip_env_keys` flags (https://hermes-agent.nousresearch.com/docs/developer-guide/terminal-environment-plugin).
- **Secrets handling:** "Both `execute_code` and `terminal` strip sensitive environment variables from child processes"; `execute_code` blocks names containing `KEY, TOKEN, SECRET, PASSWORD, CREDENTIAL, PASSWD, AUTH`; Docker/SSH/Modal "No host env vars by default"; MCP "Blocks everything except safe system vars + explicitly configured `env`"; skills' `required_environment_variables` auto-passthrough; `required_credential_files` mounted read-only into Docker; "Hermes infrastructure secrets […] should never be added to `env_passthrough` […] Such a name is refused when declared". Borrowed CLI logins (`~/.codex/auth.json`, `~/.claude/.credentials.json`) `auth.adopt_external_logins` default true. Secret sources: Bitwarden, 1Password, command helper; "Terminal commands, `execute_code` sandboxes and `no_agent` cron scripts run with a sanitized environment" (https://hermes-agent.nousresearch.com/docs/user-guide/secrets/index). Credential vault: model never sees passwords. Managed scope limits: "**Enforcement is filesystem permissions only.**"; "**The managed `.env` is world-readable** (`0644`)"; "v1 is a management-convenience boundary against a normal user, not an un-escapable sandbox."
- **Egress controls:** iron-proxy "This release wires the egress proxy into the Docker backend only. Modal, Daytona, SSH, and Singularity do **not** receive proxy env vars or CA mounts yet."; "The threat model is the *sandbox*, not the host."; residual: "iron-proxy in-memory secret zeroisation […] Out of scope for this layer." Network isolation (Docker compose networks): "The terminal backend is the primary execution boundary." — https://hermes-agent.nousresearch.com/docs/user-guide/egress/iron-proxy ; https://hermes-agent.nousresearch.com/docs/user-guide/egress/network-isolation
- **DM pairing:** unknown DM → "8-character pairing code" → `hermes pairing approve <platform> <code>`; `unauthorized_dm_behavior: pair`; platform allowlists, `GATEWAY_ALLOW_ALL_USERS` ("never use […] in production").
- **Context-file injection scanner**: "These patterns are heuristics, not semantic intent detection."; own `SOUL.md` hits warn but load.
- Other bounding statements: kanban "This is the trusted-local-user threat model; kanban is single-host by design." and "This is a single-user lifecycle guard, not OS isolation against arbitrary direct database writes."; worker-lanes "This is cooperative runtime scoping, **not OS confinement**"; kanban dashboard "plugin routes are unauthenticated by design because the dashboard binds to localhost by default […] reachable from any process on the host"; cron pause "is not a security boundary against an operator who can run jobs"; plugin registration network block "is not a sandbox" (https://hermes-agent.nousresearch.com/docs/developer-guide/plugins/index); dashboard basic auth "not suitable for exposing a dashboard directly to the public internet" (https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard).
- **Audit log — partial, no unified feature.** Present: Kanban `task_events` ("Every transition appends a row") + per-task worker logs `<board-root>/logs/<task_id>.log` ("Logs and audit trail", worker-lanes); curator "`hermes curator ledger` — list the per-mutation audit ledger (all actors)"; A2A "**Audit log** — every exchange appends to `~/.hermes/a2a_audit.jsonl`" (https://hermes-agent.nousresearch.com/docs/user-guide/messaging/a2a); approval decisions are recoverable from `state.db` via `hermes approvals suggest`; Docker image "container-boot audit log" (https://hermes-agent.nousresearch.com/docs/user-guide/docker); dashboard OAuth path has "the audit log"; iron-proxy pre-creates `audit.log` (0o600) but "On the pinned v0.39 the daemon never writes this file" (https://hermes-agent.nousresearch.com/docs/developer-guide/egress-internals); unattended `-contributor` model use prints the warning "so worker logs retain an audit trail" (https://hermes-agent.nousresearch.com/docs/user-guide/configuring-models). Absent: no documented tamper-evident or centralized audit log for tool calls/approvals; hooks docs suggest building one yourself ("Example — tool call audit log", https://hermes-agent.nousresearch.com/docs/user-guide/features/hooks).

## 7. Learning loop

- Skill auto-creation trigger (foreground): "The system prompt asks the agent to record a non-trivial workflow with `skill_manage` for future reuse. In practice that covers: When it worked out a multi-step workflow worth repeating; When it hit errors or dead ends and found the working path; When the user corrected its approach." Actions `create | patch | delete | write_file | remove_file`; advisory linter (`incident-log-shape`, `references-sprawl`, `oversized-body`) "They warn; they never block a write." — https://hermes-agent.nousresearch.com/docs/user-guide/features/skills
- Background mechanism (exact counters, from the Codex-runtime page): "Hermes' background self-improvement fires on counter thresholds: Every 10 user prompts → a forked review agent looks at the conversation and decides whether anything should be saved to memory. Every 10 tool iterations within a single turn → same idea but for skills (`skill_manage` writes)." Config keys `memory.nudge_interval` / `skills.creation_nudge_interval` (memory page); `auxiliary.background_review.enabled: false` disables the fork; memory page: "This is Hermes' consent-aware learning loop: repeated corrections and durable workflow lessons become compact memory entries or procedural skills". — https://hermes-agent.nousresearch.com/docs/user-guide/features/codex-app-server-runtime ; https://hermes-agent.nousresearch.com/docs/user-guide/features/memory
- **Human review before a self-written skill loads next session: not by default.** "By default the agent writes skills freely — including from the background self-improvement review […] If you'd rather approve every skill write first […] turn on the write-approval gate: `skills: write_approval: false # false = write freely (default) | true = require approval`". When on, "every `skill_manage` write […] is **staged** instead of committed […] Staged writes survive restarts under `~/.hermes/pending/skills/`" reviewed with `/skills pending|diff|approve|reject`. Same for memory: `memory.write_approval` default `false`. Separate content scanner `skills.guard_agent_created` "is **off by default** — real agent workflows that legitimately touch `~/.ssh/` or mention `$OPENAI_API_KEY` were tripping the heuristic too often." — skills page; https://hermes-agent.nousresearch.com/docs/user-guide/configuration
- "/learn": "`/learn <what to learn from>` | Distill a reusable skill from anything you describe — a directory, a URL, the workflow you just walked the agent through, or pasted notes." Large sources "become knowledge-base skills". — https://hermes-agent.nousresearch.com/docs/reference/slash-commands ; skills page
- Skills Hub install scan: "All hub-installed skills go through a **security scanner** that checks for data exfiltration, prompt injection, destructive commands, supply-chain signals, and other threats." "`--force` does **not** override a `dangerous` scan verdict." Trust levels `builtin | official | trusted (openai/skills, anthropics/skills, huggingface/skills, NVIDIA/skills) | community`. Project skills need `hermes skills trust`; "Scan-time quarantine" blocks `dangerous` project skills; "Cron jobs and other non-interactive surfaces inherit your interactive trust decision — they never prompt and never auto-trust." Optional "Advisory SkillEvaluator scan" ("advisory only"). — skills page
- Memory writes: strict char caps (2,200 / 1,375), "Memory does **not** auto-compact: when a write would exceed the limit, the `memory` tool returns an error"; "Memory entries are scanned for injection and exfiltration patterns before being accepted"; `session_search` over FTS5 past sessions. — memory page
- Curator: "**never auto-deletes** — the worst outcome is archival"; stale 14 d, archive 30 d, interval 7 d, idle 2 h; LLM consolidation `curator.consolidate: false` default; pinned skills off-limits "to both the curator's auto-transitions and the agent's own `skill_manage` tool"; snapshots/rollback; first run deferred one full interval. — https://hermes-agent.nousresearch.com/docs/user-guide/features/curator
- Honcho: "a catalog Memory Provider Plugin […] maintained by Plastic Labs"; "**Dialectic reasoning**: After each conversation turn (gated by `dialecticCadence`), Honcho analyzes the exchange and derives insights about the user's preferences, habits, and goals." Memory providers moved to catalog plugins in v0.22.0. — https://hermes-agent.nousresearch.com/docs/user-guide/features/honcho
- README framing: "the only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, and builds a deepening model of who you are across sessions." — https://github.com/NousResearch/hermes-agent/blob/main/README.md

## 9. Integration surfaces

- **ACP server:** protocol = Agent Client Protocol (zed-industries); library pinned `agent-client-protocol==0.9.0` (pyproject extra `acp`); adapter calls `acp.run_agent(agent, use_unstable_protocol=True)`; "The ACP adapter wraps Hermes' synchronous `AIAgent` in an async JSON-RPC stdio server."; "Stdout is reserved for ACP JSON-RPC transport." Launch: `hermes acp` / `hermes-acp` / `python -m acp_adapter`. Toolset: "Hermes runs with a curated `hermes-acp` toolset […] file tools […] terminal tools […] web/browser tools, memory, todo, session search, skills, execute_code and delegate_task, vision. It intentionally excludes […] messaging delivery and cronjob management." Per-run/per-platform narrowing: "`platform_toolsets.acp` replaces the `hermes-acp` default, and `agent.disabled_toolsets` removes toolsets from every ACP session" (so the `memory` and `skills` *toolsets* can be removed for ACP sessions; no per-session flag to suppress MEMORY.md/USER.md injection is documented — that is the global `memory_enabled`/`user_profile_enabled` config). MCP: config servers started unless host sets `HERMES_ACP_SKIP_CONFIGURED_MCP=1`; servers from `session/new` always added. Model/provider: "ACP mode uses the same Hermes configuration as the CLI: `~/.hermes/.env`, `~/.hermes/config.yaml`, `~/.hermes/skills/`, `~/.hermes/state.db`. Provider resolution uses Hermes' normal runtime resolver"; Buzz picker ids `provider:model` or `custom:<name>:<model>` for custom OpenAI-compatible endpoints. Custom base URL + key via env is supported generally: `OPENAI_BASE_URL` "Base URL for custom endpoint (VLLM, SGLang, etc.)" and `OPENAI_API_KEY` "the key for a custom OpenAI-compatible endpoint when `OPENAI_BASE_URL` is set; bound that way, it is sent only to that URL's exact origin". Home per profile: `HERMES_HOME` "Select the configuration and user-data home […] Defaults to `~/.hermes` […] the official Docker image uses `/opt/data`"; the ACP page does not document `-p <profile>` for `hermes acp`. Sessions persisted to Hermes DB; cwd bound to editor workspace; approvals rendered as ACP permission requests, "Session-scoped edit auto-approval". Hosts: VS Code (ACP Client ext), Zed, JetBrains, Buzz. — https://hermes-agent.nousresearch.com/docs/user-guide/features/acp ; https://hermes-agent.nousresearch.com/docs/developer-guide/acp-internals ; https://hermes-agent.nousresearch.com/docs/reference/environment-variables ; https://raw.githubusercontent.com/NousResearch/hermes-agent/main/pyproject.toml
- **API server:** "OpenAI-compatible HTTP endpoint"; endpoints `POST /v1/chat/completions` (stateless), `POST /v1/responses` (`previous_response_id` server-side state), `GET/DELETE /v1/responses/{id}`, `GET /v1/models`, `GET /v1/capabilities`, `GET /health`, **Runs API** `POST /v1/runs` → `{"run_id","status":"started"}`, `GET /v1/runs/{id}` (poll), `GET /v1/runs/{id}/events` (SSE), `POST …/stop`, `POST …/approval`; `Idempotency-Key` header "Hermes durably reserves the key"; Jobs API `/api/jobs`; Sessions API; `GET /api/skills`, `/api/toolsets`. **So yes: an external system can submit a task and get a result** (sync via chat completions, or async via runs + polling/SSE, with approval answering).
