# Abuse and incentive problems in pay-on-acceptance pricing: vectors and defenses (as of September 2026)

Scope: Glide charges tokens per attempt (cost plus markup, capped) and a delivery fee in credits only when the agency accepts the pull request (merge or explicit acceptance; 10 working days of silence counts as accepted). This note lists the ways customers can avoid the delivery fee and the defenses that have been shown to work.

Method and source caveats (read first):
- The sandbox egress proxy blocked direct fetches of git-scm.com, docs.github.com, intercom.com, fin.ai, support.upwork.com and nldigital.nl. Only raw.githubusercontent.com could be fetched in full (the git-patch-id documentation).
- Findings marked **[search summary]** come only from web-search result summaries and were not read in full. Check them before quoting them externally.
- Statements marked **[background, unverified this session]** come from the researcher's prior knowledge and were not confirmed against a source this session. They appear only under Inferences or Gaps.

## 1. How can code taken without acceptance be detected technically?

### Takeaway
No single signal survives every evasion, so detection should be layered and should grow more expensive to evade at each layer:
- exact SHA match
- the forge's own merge metadata
- git patch-id (catches cherry-picks and rebases)
- per-file and per-hunk similarity (catches squashes and partial copies)
- winnowing-style fingerprints (catches edited copies)

Provenance signatures and trailers prove where a commit came from when they are kept, but anyone can strip them. Watermarking AI-generated code is too fragile to use as evidence for billing.

### Cited Findings
- **git patch-id**: "A 'patch ID' is nothing but a sum of SHA-1 of the file diffs associated with a patch, with line numbers ignored." `--stable` makes the ID independent of the order of file diffs. `--unstable` (the default) ignores whitespace. `--verbatim` does not strip whitespace. — [git-patch-id docs (git/git master)](https://raw.githubusercontent.com/git/git/master/Documentation/git-patch-id.adoc)
- **The squash and rebase problem on GitHub**: when commits are amended, squashed, rebased or cherry-picked, their SHAs change, so GitHub cannot tell that the work was effectively merged unless something like a commit-message trailer says so. A squash merge can be traced back to its PR from the commit message. A rebase merge appends the commits directly to the base branch, so this is not possible. **[search summary]** — [GitHub community discussion #6414](https://github.com/orgs/community/discussions/6414); [discussion #37585](https://github.com/orgs/community/discussions/37585)
- **GitHub REST `merge_commit_sha`**: after a squash merge it holds the SHA of the squashed commit on the base branch. This lets a platform link an in-forge squash merge to its PR without guessing. **[search summary]** — [GitHub REST pulls docs](https://docs.github.com/en/rest/pulls/pulls); [GitHub pull request merges](https://docs.github.com/en/pull-requests/reference/pull-request-merges)
- **Forgejo and Gitea**: upstream Gitea has changed the content of squash-merge messages, specifically how they credit all commit authors (PR #35247). Squash-message content, including co-author trailers, is therefore a usable but platform-specific signal. **[search summary]** — [go-gitea/gitea PR #35247](https://github.com/go-gitea/gitea/pull/35247)
- **Winnowing and MOSS**: winnowing (Schleimer, Wilkerson and Aiken, SIGMOD 2003) hashes k-grams and keeps the minimum hash in each window. It is guaranteed to detect any shared run of at least K+W−1 tokens and is the basis of MOSS for detecting code plagiarism. Its performance is within 33% of the theoretical lower bound. **[search summary]** — [Winnowing, ACM DL](https://dl.acm.org/doi/10.1145/872757.872770); [Semantic Scholar entry](https://www.semanticscholar.org/paper/Winnowing:-local-algorithms-for-document-Schleimer-Wilkerson/73acc491ec7eb8f0a29e0f06397cb517b79e658b)
- **Provenance signing**:
  - Sigstore gitsign signs commits "keyless": each signature uses a short-lived certificate from Fulcio, bound to an OIDC identity, and is recorded in the Rekor transparency log.
  - A gitsign proposal would add in-toto attestations (`cosign.sigstore.dev/attestation/gitsign/v1`) generated by walking the commit history.
  - Community tools such as agent-attest provide an "attested at run time, verified against git history" chain of custody for commits written by AI agents.
  - One 2026 source says GitHub has signed Copilot commits since April 2026 but "gates on nothing for third-party agents".
  - **[search summary]** — [Security Boulevard, gitsign in practice (Sept 2026)](https://securityboulevard.com/2026/09/sigstore-gitsign-in-practice-sign-commits-keyless-and-verify-them-in-ci/); [sigstore/gitsign issue #105](https://github.com/sigstore/gitsign/issues/105); [agent-attest](https://github.com/zhengqiuyang/agent-attest)
- **Commit IDs can be forged**: a 2026 arXiv paper, "Git Hash Chain Malleability", appeared in the search results. It suggests commit identity alone is weak evidence. Only the title was seen. **[search summary]** — [arXiv 2607.02820](https://arxiv.org/pdf/2607.02820)
- **Watermarking AI-generated code is fragile**:
  - The ICLR 2024 robustness study found that true-positive rates fall below 50% in many cases after minor, semantics-preserving edits to Python. With 5 WrapTryCatch edits, TPR dropped to 0.22 (UMD watermark) and 0.11 (Unigram).
  - SWEET, which watermarks only high-entropy tokens, reportedly cut pass rate from 63.12% to 43.21% on one benchmark and made generation much slower.
  - An EMNLP 2025 Findings paper also evaluates how well these watermarks survive attack.
  - **[search summary]** — [arXiv 2403.17983 (ICLR 2024)](https://arxiv.org/html/2403.17983v3); [arXiv 2402.07518](https://arxiv.org/pdf/2402.07518); [Watermark under Fire, EMNLP 2025 Findings](https://aclanthology.org/2025.findings-emnlp.1148.pdf)

### Inferences
- **Recommended detection ladder** for "PR closed or ignored, but the code landed". Run it on the base branch for N days after a PR closes:
  1. Any PR commit SHA is reachable from the base branch (plain merge or fast-forward outside the UI).
  2. The forge reports `merged`, or its `merge_commit_sha` / `squash_commit_sha` exists.
  3. The `git patch-id --stable` of each PR commit, and of the whole PR diff, matches that of a base-branch commit (catches cherry-picks and rebase merges). `git cherry` does this comparison natively. **[background, unverified this session]**
  4. Per-file and per-hunk similarity: the share of added lines in the PR that appear in base-branch commits after the PR was closed (catches squashes of several PRs and partial copies).
  5. Winnowing fingerprints over normalized tokens, with identifiers renamed and whitespace and comments stripped (catches edited copies).

  Each rung raises the evidence tier ("exact", "equivalent", "substantially similar"). Only the first two or three rungs should bill automatically. The others should open a review or dispute and never bill silently.
- **Commit trailers** (for example a `Glide-Run:` or `Glide-Shift:` trailer, or `Co-authored-by: glide[bot]`) survive a GitHub squash when they sit in the commit bodies that GitHub concatenates. They are lost if the user edits the squash message. A trailer is cheap corroboration, not proof. **[background, unverified this session]**
- **Signing Glide's own commits** with gitsign or Sigstore, plus an in-toto attestation per Run (hash of the diff, Work Item, Run ID), proves where *Glide's* output came from. It proves nothing about a copy the customer re-commits. Its value is in disputes ("this diff existed at time T, signed by Glide") and in transparency.
- **Do not rely on watermarking to bill.** The false-negative rates above are too high, and it could affect code quality.
- **Detection needs read access** to the customer's repository after the PR closes. A customer can move the code to a repository Glide cannot see (a mirror or another org). That evasion cannot be detected technically and has to be handled by contract (section 4).
- **False positives**: a trivial one-line fix, or a fix any competent developer would write the same way, will match by coincidence. Use minimum-size thresholds (in the same spirit as winnowing's K+W−1 guarantee) and exclude generated, lockfile and formatting-only hunks.

### Gaps
- The exact current GitHub, GitLab and Forgejo field semantics for closed-but-unmerged PRs, rebase-merge detection and timeline events could not be fetched because the documentation domains were blocked. [Background, unverified this session: GitLab MR API exposes `squash_commit_sha` and `merge_commit_sha`, and `git cherry-pick -x` appends "(cherry picked from commit …)".]
- No published false-positive rates were found for patch-id or winnowing specifically on AI-agent diffs.
- The claim that GitHub signs Copilot commits comes from one secondary source and is not verified.

## 2. How do marketplaces and outcome-priced services stop "take the work, don't pay"?

### Takeaway
Every durable model does three things:
- **Fund or deposit before work starts**: escrow (Upwork), a deposit (Toptal), up-front payment (Fiverr).
- **Release on a deemed-acceptance timer**: Upwork 14 days, Fiverr 3 days, Intercom about 24h. Glide's 10 working days is at the generous end.
- **Send rejections to mediation or a reputation penalty**, not to unilateral non-payment.

Pure "pay only if satisfied" works only when the provider controls re-matching and can absorb the loss (Toptal trial), or when the outcome is measured by the provider's own system (Intercom Fin).

### Cited Findings
- **Upwork (fixed-price)**:
  - The client funds a milestone into escrow before work starts.
  - After the freelancer clicks "Submit Work", the client has 14 days to approve, request changes or do nothing. Silence releases the funds automatically.
  - The clock starts only on the formal Submit action, not on delivery by chat, Drive or repository. Requesting changes resets it.
  - Mediation is free. Arbitration costs $337.50 per side.
  - Freelancers must file a dispute within 7 days of a refund request.
  - **[search summary; the support.upwork.com fetch was blocked]** — [Upwork: How payments for milestones work](https://support.upwork.com/hc/en-us/articles/211063718-How-payments-for-milestones-and-fixed-price-contracts-work); [Upwork: file a dispute](https://support.upwork.com/hc/en-us/articles/211068528-How-to-file-a-dispute-when-your-client-doesn-t-pay-a-milestone); [GigRadar arbitration explainer 2026](https://gigradar.io/blog/upwork-payment-protection-fixed-price)
- **Fiverr**:
  - The buyer pays up front.
  - A digital delivery auto-completes if the buyer does nothing for 3 days (14 days for shipped goods).
  - The buyer can reject a delivery to request revisions.
  - Cancellation needs the seller's consent, or Customer Support mediation, and "Buyers need to provide a satisfactory explanation, and proof".
  - Sellers report that buyers cancel after receiving completed work, including months later, in community threads. This is anecdotal evidence of the "take and cancel" vector.
  - **[search summary]** — [Fiverr: order statuses and process](https://help.fiverr.com/hc/en-us/articles/37332473202065-The-complete-guide-to-your-Fiverr-order-Statuses-and-process); [Fiverr: cancellations for clients](https://help.fiverr.com/hc/en-us/articles/12864193979793-How-cancellations-work-for-clients); [community thread](https://community.fiverr.com/public/forum/boards/freelancer-lounge-sry/posts/340602-the-buyer-canceled-the-order-after-receiving-the-completed-work)
- **Toptal**:
  - A trial of up to two weeks. "If you're not completely satisfied, you won't be billed."
  - A client can trial up to three individuals per position.
  - A $500 deposit (applied to the first bill) and a reported $79/month platform fee.
  - **[search summary; the fee amounts come from third-party reviews]** — [Toptal FAQ](https://www.toptal.com/faq); [TFC Toptal pricing 2026](https://www.thefrontendcompany.com/posts/toptal-pricing)
- **Intercom Fin (outcome pricing)**:
  - $0.99 per outcome.
  - A resolution is "confirmed" (the customer says the answer helped) or "assumed" (the customer leaves without asking for more help, reportedly after 24h of inactivity).
  - If the customer later returns to the same conversation asking for more help, the resolution "will be deducted and not charged", even across billing periods.
  - Outcomes can include some procedure handoffs.
  - **[search summary; intercom.com and fin.ai fetches blocked]** — [Intercom: Fin AI Agent outcomes](https://www.intercom.com/help/en/articles/8205718-fin-ai-agent-outcomes); [Fin pricing: Outcomes](https://fin.ai/help/en/articles/10772642-fin-ai-agent-resolutions); [Intercom: How Fin pricing works](https://www.intercom.com/help/en/articles/7837512-how-fin-pricing-works)
- **HackerOne (bug bounty)**:
  - Rules for duplicates and "Not Applicable" reports are enforced through reputation:
    - Not Applicable costs −5 reputation and lowers Signal.
    - A duplicate of a resolved report filed before disclosure earns +2.
    - A duplicate of an N/A report costs −5.
    - Duplicates of one's own reports are neutral.
    - Self-closed, Duplicate and Informative states do not affect Signal.
  - Signal (validity rate) and Impact are used to gate invitations to private programs.
  - **[search summary]** — [HackerOne docs: Reputation](https://docs.hackerone.com/en/articles/8369865-reputation); [Signal & Impact](https://docs.hackerone.com/en/articles/8369891-signal-impact); [Report States](https://docs.hackerone.com/en/articles/8475030-report-states)
- **Algora (open-source bounties)**:
  - The contributor adds `/claim #<issue>` to the PR.
  - "AutoPay" pays when the PR is merged. Funds arrive 1–3 business days after the org pays.
  - Payouts go through Stripe Express with KYC.
  - Many repositories ban low-effort AI-generated PRs.
  - **[search summary]** — [Algora docs: bounty workflow](https://docs.algora.io/bounties/workflow); [Taskman issue on Algora KYC](https://github.com/joyelgeorge/Taskman/issues/196)

### Inferences
- **Glide's model inverts the escrow direction.** The customer holds the value (the code lands in their repository) and Glide holds the claim. That is the Fiverr "cancel after delivery" risk profile, not Upwork's. It is closer to the Intercom model: the provider's own instrumentation defines the outcome, and reversal rules are published.
- **Borrow from Intercom**: a precise, published definition of "accepted", including the deemed-acceptance timer, plus a published reversal rule (for example, a PR reverted within X days, or a fix issue reopened, is not charged). This makes deemed acceptance feel fair, because it has a symmetric way back.
- **Borrow from Upwork**: the timer starts on a formal "ready for review" event, not on the PR opening. A "request changes" action resets it. Disputes go to a structured mediation step with an explicit fee or cost for escalation.
- **Borrow from HackerOne**: rejections are allowed but carry a reputation signal. A high rejection rate gates access to premium features or deeper trust tiers rather than triggering a direct penalty.
- **Borrow from Toptal**: the "no charge if not satisfied" promise is bounded by a deposit and a limited number of trials per Work Item.

### Gaps
- No primary-source text was obtained for Gitcoin bounty dispute rules, or for any 2026 changes to Intercom's resolution definition.
- The 24h assumed-resolution window is only in search summaries and blog posts.
- Contingency and "no cure no pay" terms (for example, Dutch salvage-style or recruitment success fees) were not researched for lack of budget.
  - [Background, unverified this session: Dutch advocates are barred from pure no-cure-no-pay in most matters. Recruitment agencies commonly use a guarantee period with a fee refund or replacement.]

## 3. Which incentive designs deter abuse, and which feel fair to honest customers?

### Takeaway
The defenses honest users accept best are:
- transparent, symmetric rules (deemed acceptance paired with a reversal right)
- a small floor fee (always paying for tokens)
- reputation that customers can see

Punitive defenses (clawbacks and hard penalties) are best kept for evidence-backed cases, and customers should be able to contest them in a lightweight dispute.

### Cited Findings
- **Deemed acceptance by silence is standard**: Upwork 14 days, Fiverr 3 days, Intercom about 24h. **[search summary]** — see the section 2 sources.
- **Deposits**: Toptal takes $500 applied to the first invoice. **[search summary]** — [TFC](https://www.thefrontendcompany.com/posts/toptal-pricing)
- **Reputation and validity thresholds**: HackerOne's Signal is "an aggregate representation of report validity" and filters who gets private-program invitations. **[search summary]** — [HackerOne Signal & Impact](https://docs.hackerone.com/en/articles/8369891-signal-impact); [HackerOne blog](https://www.hackerone.com/blog/expanding-reputation-introducing-signal-and-impact)
- **Neutral outcomes protect fairness**: HackerOne keeps duplicates of one's own reports, and self-closed or informative reports, out of Signal. Honest structural outcomes are not penalized. **[search summary]** — [HackerOne Reputation](https://docs.hackerone.com/en/articles/8369865-reputation)
- **A formal dispute route with costs**: Upwork mediation is free and arbitration is paid ($337.50 per side). The cost deters frivolous escalation. **[search summary]** — [GigRadar](https://gigradar.io/blog/upwork-payment-protection-fixed-price)
- **KYC gating**: Algora requires Stripe Express KYC before payout. **[search summary]** — [Taskman issue](https://github.com/joyelgeorge/Taskman/issues/196)

### Inferences
Catalogue of abuse vectors mapped to defenses. Defenses marked * are already chosen by Glide.

| Abuse vector | Primary defense | Secondary defense | Honest-user fairness note |
|---|---|---|---|
| Close the PR, copy the diff by hand | Detection ladder (§1) on the base branch for N days after close* | Contract: licence granted only on acceptance or payment (§4); deemed acceptance when matching code lands | Notify first ("we detected code matching Run X on `development`; mark as accepted or dispute"), never bill silently |
| Cherry-pick or rebase outside the UI | patch-id match* | Trailers | Same as above |
| Squash-merge with other work, or squash elsewhere | Hunk-level similarity and winnowing | Customer attests "not used" when closing | Bill pro rata for the matched share, or open a dispute |
| Move the code to a repository Glide cannot see | Contract term plus audit right | Acceptance-rate anomaly flags | Only the contract can enforce this. Keep it proportionate |
| Reject to avoid the fee | Always charge tokens*; acceptance rate shown* | Rejection-reason codes; low acceptance rate lowers the trust tier or requires a deposit | Structured reasons ("wrong scope", "tests fail") are also useful product feedback |
| Leave the PR open indefinitely | Deemed acceptance after 10 working days* | Timer starts at "ready for review"; changes requested pauses it | Reminders before the timer expires |
| Split tickets to stay under the cap or fee tiers | Fee tied to diff or complexity size, not ticket count; per-Work-Item minimum fee | Detect near-identical Work Items or sequential PRs touching the same files | A minimum fee is widely understood (compare the paid-discovery norm below) |
| Mis-size tickets (declare a large one small) | Measure size after delivery from the diff, not the customer's declaration | Re-quote when the measured size far exceeds the estimate | Show the size calculation |
| Reuse refinement or plan output without running delivery | Charge refinement as tokens*; free refinement allowance per period | Credit refinement fees against delivery within a window | See §5 |
| Revert right after accepting to claim a refund (the reverse abuse) | Reversal limited to evidenced defects within X days | Cap on refunds per period | Mirrors Intercom's reversal rule |
| Account cycling or new orgs to reset reputation | Tie trust to a verified billing entity (KvK/VAT/KYC) | Deposit for new accounts | Standard B2B onboarding |

Principles that seem fair:
- **Graduated trust tiers.** A new organization pays a deposit or prepaid credit. After K accepted deliveries it gets deemed acceptance and post-paid billing. A sustained low acceptance rate or a detected-copy event demotes the organization.
- **Rate limits** on concurrent Shifts per organization, scaled by tier.
- **Clawbacks** (billing after the PR closed) only with evidence at the "exact" or "equivalent" level from §1, after notice with a dispute window of about 10 working days, mirroring the acceptance timer.
- **Public or customer-visible acceptance statistics** in the style of HackerOne's Signal. The customer sees their own acceptance rate and the platform-wide median.

### Gaps
- No empirical study was found on how honest customers perceive deposits or clawbacks in outcome-priced software services.
- No data was found on the base rate of "close and copy" abuse on any platform. The Fiverr evidence is anecdotal community posts.

## 4. What legal and contract terms support this pricing in NL/EU B2B?

### Takeaway
Dutch retention of title (eigendomsvoorbehoud, art. 3:92 BW) applies to goods, not to copyright. The software equivalent is to:
- keep the copyright with Glide or the agency's contractor side, or
- grant the licence to use delivered code under a condition precedent (opschortende voorwaarde) of acceptance or payment.

Under Dutch law, copyright in commissioned software stays with the maker unless it is transferred by deed. That gives the provider a strong default position.

### Cited Findings
- **Eigendomsvoorbehoud under art. 3:92 BW**: ownership of *delivered goods* passes only once the buyer has fully paid. **[search summary]** — [e-legal.nl](https://e-legal.nl/eigendomsvoorbehoud); [MAAK advocaten](https://www.maakadvocaten.nl/contractenrecht/eigendomsvoorbehoud/)
- **Copyright default**: copyright belongs to the maker. The client who paid for custom software does not acquire it automatically. Transfer, and the grant of an exclusive licence, require a written deed (akte). **[search summary]** — [Auteurswet art. 2 (boek9.nl)](https://www.boek9.nl/wetteksten/auteurswet/artikel-2); [ICTRecht: auteursrechten overdragen](https://www.ictrecht.nl/blog/auteursrechten-overdragen-hoe-zat-dat-ook-alweer); [Law & More: auteursrecht maatwerksoftware](https://lawandmore.nl/auteursrecht-maatwerksoftware/)
- **Conditional licences are used in practice**: a licence can be suspended automatically until full payment. A common structure combines transfer of specific deliverables with a licence on base code, sometimes with escrow. **[search summary]** — [MAAK: licentie op content](https://www.maakadvocaten.nl/intellectueel-eigendomsrecht/licentie-op-content/); [Dirkzwager: IT-contracten deel 14](https://www.dirkzwager.nl/kennis/artikelen/it-contracten-deel-14-intellectuele-eigendom)

### Inferences
Proposed contract terms (not legal advice; to be checked by counsel):
1. **Licence on acceptance.** Glide (or the agency, depending on who is the maker in the chain) grants the customer a licence to the delivered diff under the condition precedent of acceptance. Acceptance is defined as a merge, an explicit accept, deemed acceptance after 10 working days, **or incorporation of substantially the same code into any branch or repository the customer controls**. Incorporation without acceptance counts as acceptance and makes the delivery fee due.
2. **Definition of "substantially the same"**, tied to the published detection ladder. Before billing, the customer is notified and can dispute within about 10 working days.
3. **Audit and attestation right.** On closing a PR as rejected, the customer states that the code will not be used. Glide may verify through repository access. Keep this proportionate.
4. **Payment terms.** EU Late Payment Directive and Dutch commercial statutory interest (art. 6:119a BW). [Background, unverified this session.]
5. **Proportionality.** In B2B, the Dutch unfair-terms regime (art. 6:233 BW) protects mainly consumers and, through "reflexwerking", small businesses. Contractual penalties (boetebeding, art. 6:91–6:94 BW) can be moderated by a court. Prefer "the fee becomes due" over "a penalty applies". [Background, unverified this session.]
6. **Open-source nuance.** If the target repository is public under an open-source licence, the customer may argue that any contribution is licensed openly. The terms should state that Glide's output is licensed to the customer only on acceptance, whatever the repository's licence.
7. **AI-authorship nuance.** It is unsettled whether purely AI-generated code attracts copyright under EU and Dutch originality standards (a human's "own intellectual creation"). Relying only on copyright to enforce the fee is therefore risky. A contractual fee obligation triggered by use is more robust than an infringement claim. [Background, unverified this session; flag for legal review.]

### Gaps
- The exact NLdigital Voorwaarden 2025 clauses on IP and payment-conditioned rights could not be fetched (domain blocked). [Background, unverified this session: NLdigital and older ICT~Office conditions keep the IP with the supplier and make the right of use conditional on payment.]
- No 2025–2026 Dutch or EU case law was found on the copyright status of AI-generated code. This needs a separate legal research pass.
- No research was done on how the EU AI Act transparency obligations, or the Data Act, interact with this billing model.

## 5. How are free refinement and quotes abused, and how is it mitigated?

### Takeaway
Agencies long ago stopped giving away free detailed discovery because clients took the plan elsewhere. The established fix is a paid discovery fee of about 5–10% of project value, credited against the build if the client proceeds within a deadline. Glide's refinement output (plans, specs, estimates) is the direct analogue.

### Cited Findings
- **Paid discovery pricing**: typically 5–10% of total project value, for example $1,500–2,500 for brochure sites. **[search summary]** — [Sakas & Company](https://sakasandcompany.com/start-using-paid-discovery/); [The Admin Bar](https://theadminbar.com/charging-for-discovery-s-o-p/)
- **Crediting the fee toward the build**:
  - Some agencies credit 100% toward Phase 2 if the client proceeds within about a month.
  - Others credit 50% against the first build invoice if the client proceeds within 60 days.
  - Recommended deadlines are 2–6 weeks.
  - **[search summary]** — [Sakas & Company](https://sakasandcompany.com/start-using-paid-discovery/); [72 Technologies](https://www.72technologies.com/blog/billable-discovery-sprint-for-agencies)
- **Free proposals are cross-subsidized**: "you end up paying for all the proposals they wrote for clients they didn't win". **[search summary]** — [Avex Designs](https://www.avexdesigns.com/blog/what-is-a-paid-discovery/)

### Inferences
- For Glide:
  - Charge refinement as tokens (already chosen).
  - Give a monthly free-refinement allowance per organization, scaled by trust tier.
  - Credit refinement spend against the delivery fee when delivery on the same Work Item is accepted within about 30 days. This rewards conversion and removes the "paying twice" objection.
- Track the refinement-to-delivery conversion rate per organization. A persistently low rate is the abuse signal ("uses Glide as a free planner"). The response is to shrink the allowance, not to penalize.
- Refinement output should state that the plan is licensed for evaluation. Using it to implement elsewhere is permitted only once the refinement tokens are paid, which they always are under the tokens-always model. So the risk is limited to losing the delivery margin, not to unpaid cost.

### Gaps
- No platform-specific data was found on abuse of free AI-generated estimates or plans.
- No public examples were found of AI coding platforms charging separately for planning versus delivery with credit-back rules.
