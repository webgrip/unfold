## 3. Core abstractions (as Fullsend spells them)

Execution stack — "Five components form the vertical execution path ... Control flows strictly downward" (ADR 0016) (`docs/architecture.md` "Execution Stack"):
- **Agent Dispatch and Coordination Layer** — "translates events into agent tasks"; principle "the repo is the coordinator" (labels, CODEOWNERS, branch protection, events), no central orchestrator. Routing = harness CEL `trigger` over a `NormalizedEvent`/normalized entity, evaluated by `fullsend dispatch`; polling via `fullsend poll` (`docs/architecture.md` "Agent Dispatch and Coordination Layer"; ADRs 0061, 0063, 0098; `docs/normative/normalized-event/v1/README.md`).
- **Agent Infrastructure** — "provisions and runs agent workloads"; today GitHub Actions / GitLab CI runners; choice of 3rd-party/internal/own platform is an open question (`docs/architecture.md` "Agent Infrastructure").
- **Agent Sandbox** — "enforces isolation (network, filesystem)"; NVIDIA OpenShell, one ephemeral sandbox per run, per-agent policy (ADR 0020, ADR 0036, ADR 0065).
- **Agent Harness** — "assembles configuration and context (skills, prompts, tools)"; per-role YAML (`harness/<agent>.yaml`), with `base:` composition, `overlays:` (CEL-guarded), `providers`, `skills`, `plugins`, `pre_script`/`post_script`, `validation_loop`, `privilege_levels`, `timeout_minutes` (`docs/reference/harness-reference.md`; glossary prefers "agent spec").
- **Agent Runtime** — "the LLM in execution": `runtime.Runtime` interface; `claude | pi | codex | opencode | dummy | dummy-playback` (`docs/architecture.md` "Agent Runtime"; `docs/runtimes.md`).
- Cross-cutting: **Policy Store** (autonomy levels, guardrails in `.fullsend/`, mostly open questions), **Intent Source** (pointer e.g. `intent_repo: your-org/features`; representation is an open problem), **Agent Identity Provider** (per-role GitHub Apps + token mint), **Observability** (OTel, JSONL transcripts), **Agent Registry** (`agents:` list in config; ADR 0058) (`docs/architecture.md`).
- **Stage** — "A higher-level workflow component (e.g., triage, code, review)", chosen over "phase"; contains **steps** (`docs/glossary.md`).
- **Agent roles shipped (6)**: Triage, Prioritize (RICE), Code, Review, Fix, Retro (`docs/agents/README.md`). Default agents live in https://github.com/fullsend-ai/agents and are resolved at runtime. Mint roles in config: `triage, coder, review, fix, retro, prioritize` (`docs/reference/config-reference.md` `roles`). Criteria for a new built-in role: six tests (ADR 0124).
- **Agent classification**: Default / Configured default / Derived (`base:` lineage, identity fields replaced) / Custom; **BYOA** = capability to bring your own agents (`docs/glossary.md`; `docs/guides/user/default-vs-custom.md`).
- **"Ladder" — two different things:**
  - `LADDER.md` is the **Contributor Ladder** (governance, not autonomy): Vouched → Triage → Write → Maintainer. Each role unlocks slash commands: Triage unlocks `/fs-triage`, `/fs-review`; Write unlocks `/fs-code`, `/fs-fix`, `/fs-retro`, `/fs-prioritize` and `ok-to-test`; Maintainer = `@fullsend-ai/core`, CODEOWNERS approval. Approvals: Vouched 1 maintainer, Triage 1, Write 2, Maintainer consensus. "Agent-authored PRs you drove" count toward advancement.
  - **Escalation ladder** (customization, status Proposed): "Level 1 — Configure / Level 2 — Contribute / Level 3 — Derive / Level 4 — Replace" (`docs/guides/user/escalation-ladder.md`).
  - **Adoption stages** (not called a ladder): Crawl (triage, prioritize, review comment only) → Walk (AGENTS.md, skills, retro) → Run (code agent, auto fix loop) → Fly (auto-merge, BYOA) (`docs/guides/user/adoption.md`).
- **Intent representation**: an open problem doc, not a built feature. It contrasts "the formal record (JIRA states, rank...)" — "explicit but gameable" — with "the informal network"; asks "Is this change something we actually want?" (`docs/problems/intent-representation.md`). Implemented intent today is just: issue + labels (`ready-to-code`) + slash commands authorized by forge permission.
- **`.fullsend/` config** (per target repo): `.fullsend/config.yaml` (overlay) over `.fullsend/config.base.yaml` (preset) over compiled defaults; plus repo `AGENTS.md`, `.agents/skills/`, `.fullsend/harness/*.yaml`. "Guardrails can only be tightened, never weakened." (`docs/architecture.md` "Configuration layering"; `docs/reference/config-reference.md`). Fleet: `repos.yaml` manifest + `fullsend repos install` (ADR 0057/0074/0122).
- **Token mint** — OIDC → short-lived GitHub App installation token per role; GCF, Cloudflare Worker, or standalone `cmd/mint/` (ADR 0008, 0029, 0068).

## 4. Lifecycle of work

- **Intake**: GitHub issues (opened/edited) and PRs via the shim's `issues`, `issue_comment`, `pull_request_target` triggers (`internal/scaffold/fullsend-repo/templates/shim-per-repo.yaml`); slash commands; schedules (prioritize "CRON" on homepage); GitLab via native webhook fast-path + cron poller (ADR 0125/0067); **Jira** via `fullsend poll --input-driver jira-poll` on a scheduled GitHub Actions workflow, pre-alpha; Jira issues are triaged/coded but code output still goes to a GitHub repo; status notifications route back to the triggering tracker (ADR 0093) (`docs/guides/user/jira-integration.md`; config key `tracker: github|gitlab|jira`). GitHub Discussions as a "conversation" entity (ADR 0086).
- **States = labels** ("Labels are the state machine"): `blocked`, `duplicate`, `needs-info`, `feature`, `triaged`, `ready-to-code`, `ready-for-review`, `ready-for-merge`, `requires-manual-review`; PR control labels `fullsend-fix`, `fullsend-no-fix`, `needs-human`; e2e label `ok-to-test` (`docs/guides/user/bugfix-workflow.md`; `LADDER.md`).
- **Who moves them**: agents via post-scripts (triage applies `ready-to-code` only for bug/docs/performance; features get `feature`/`triaged` and wait for a human); humans via labels or slash commands. `ready-to-code` only dispatches the code agent "when applied by a user with `write` access or by an agent bot" (`LADDER.md` Triage).
- **Slash commands** (`/fs-` prefix, ADR 0042): `/fs-triage`, `/fs-code`, `/fs-review`, `/fs-fix [instruction]`, `/fs-fix-stop`, `/fs-retro`, `/fs-prioritize`. Auth: triage-level for `/fs-triage`, `/fs-review`; write-level for the rest; optional `authorization: [{provider: owners_file}]` grants Prow OWNERS approvers/reviewers (`docs/guides/user/bugfix-workflow.md`; `docs/reference/config-reference.md` `authorization`). Entity separation: `/fs-code` only on issues, `/fs-fix`/`/fs-review` only on PRs (ADR 0076).
- **Review agents**: bugfix guide says "N independent review agents in parallel ... One is randomly selected as coordinator" with outcomes unanimous approve → `ready-for-merge`, unanimous rework → fix agent, split → `requires-manual-review`; label cleared on every new push (`docs/guides/user/bugfix-workflow.md`; `docs/architecture.md` building block 12). The review agent reference instead describes one `pr-review` orchestrator skill dispatching parallel sub-agents per dimension (correctness, security, intent & coherence, ...) (`docs/agents/review.md`) — the two descriptions differ. PR risk score 1–5 sub-agent (ADR 0089). Severity knob `REVIEW_FINDING_SEVERITY_THRESHOLD`.
- **Fix loop caps**: bot-triggered up to 5 iterations per PR, human-triggered up to 10 total (configurable); `needs-human` applied near cap; over cap fails before sandbox (`docs/agents/fix.md` "Iteration limits"). Runs serialized per harness/repo/entity, later events coalesced (ADR 0106).
- **Human gates / merge**:
  - Glossary "Automerge": "The team has explicitly decided not to implement automerge in the MVP; agents will comment that they approve, but a human must merge." (`docs/glossary.md`)
  - But the adoption guide documents opt-in: "The code agent supports auto-merge via the `CODE_AUTO_MERGE` environment variable. Set it to `"true"` to enable GitHub auto-merge on code agent PRs. Use `CODE_AUTO_MERGE_METHOD` ... (`squash`, `rebase`, or `merge` — defaults to squash)", plus path-scoped auto-merge by making the review bot a CODEOWNER (`docs/guides/user/adoption.md` "Progressive Auto-Merge"). Merge itself is GitHub-native auto-merge gated by branch protection/CODEOWNERS/CI.
  - Roadmap Now: "a **fullsend auto-merge agent**: dedicated, opt-in, disabled by default, for a narrow class of low-risk work. Repository rules and CI stay the enforcement boundary ... will not be recommended for opt-in until revert and defect visibility ([fullsend#6892]) is operational" (`docs/roadmap.md`; agents#1132). PR #7151 "dedicated auto-merge authority boundary" is open, not accepted (`docs/spikes/2026-10-24-gemara-auto-merge.md`).
  - Autonomy model (problem doc): "**binary per-repo** with **CODEOWNERS as the escape hatch**"; shadow-mode probation; "Eligibility is not authority." (`docs/problems/autonomy-spectrum.md`).
  - "After merge ... merged (by human, merge queue, or automation per org governance)" → retro agent runs on PR close (`docs/guides/user/bugfix-workflow.md`).
- **Permission/autonomy config keys (exact)**: `kill_switch` ("Emergency stop — disables all agent dispatch when true"), `roles`, `agents[].enabled/runtime/model/effort/subagents/trigger`, `authorization[].provider: owners_file`, `create_issues.allow_targets.{orgs,repos}`, `allowed_remote_resources`, `status_notifications.{comment,reaction}.{start,completion}` (`docs/reference/config-reference.md`); harness `privilege_levels: {pre_script, runtime, post_script, default}` → mint levels `read`/`write` (ADR 0073); harness `trigger` (CEL); agent env vars `{AGENT}_{SETTING}` e.g. `CODE_AUTO_MERGE`, `CODE_AUTO_MERGE_METHOD`, `REVIEW_FINDING_SEVERITY_THRESHOLD` (ADR 0049/0080). Adoption scoping: `fullsend github setup ... --agents triage,prioritize,review`.

## 5. Execution

- **Where agents run**: CI runners. GitHub: repo shim `.github/workflows/fullsend.yaml` → `workflow_call` to upstream `fullsend-ai/fullsend/.github/workflows/reusable-dispatch.yml` → inline agent job → composite action `fullsend-ai/fullsend@<version>` runs `fullsend run <agent>` (`docs/architecture.md` "MVP embodiment"; `action.yml`). GitLab: `.gitlab/ci/fullsend-*.yml` jobs calling `fullsend run "${STAGE}"` (`docs/contributing/sandbox-topology.md`). Kubernetes/OpenShift execution is "Later: ... forge-decoupled agent runtime" (`docs/roadmap.md`). Local runs supported (`docs/guides/user/running-agents-locally.md`). Shell executors on GitLab excluded (ADR 0036).
- **Sandbox tech**: **NVIDIA OpenShell** (https://github.com/NVIDIA/OpenShell) — homepage: "Agents run inside NVIDIA OpenShell sandboxed environments with policy-enforced egress routing, filesystem isolation, and process constraints." Container-based, "Docker-first" shared image; images `ghcr.io/nvidia/openshell-community/sandboxes/base` → `fullsend-sandbox` (triage/prioritize/retro) → `fullsend-code` (code/fix/review, adds Go) (`docs/contributing/sandbox-topology.md`; ADR 0036 "Isolation mechanism: Container runtime (Docker, Podman, GitLab's Docker executor). OpenShell creates nested sandboxes inside the container"). Policies cover filesystem, landlock, process (ADR 0065). **No gVisor, Kata or Firecracker in use**: Kata is mentioned only as the complementary isolation layer Kubernetes SIG Agent Sandbox defers to; "What is the right isolation level — process, container, microVM, or separate cluster?" remains an open question (`docs/architecture.md` "Agent Sandbox"; `docs/problems/agent-infrastructure.md`). OpenShell rootless mode is an upstream feature request (ADR 0036). Container builds inside the sandbox: prohibited by default / external Kaniko or BuildKit (ADR 0036). Subagents currently share the parent sandbox (roadmap Next, fullsend#3978). "Alternative sandbox providers — considered; not worth the refactor now" (roadmap Later).
- **One sandbox per role/run**: "each agent gets its own sandbox with policies designed for its responsibility" (ADR 0020); "The sandbox is ephemeral. Created per-run, destroyed after extraction." (`docs/architecture.md` "Abstract model").
- **Credentials**: "Credentials never cross the sandbox boundary." Four delivery tiers (ADR 0017/0025): prefetch + post-process; OpenShell providers + L7 egress policy with placeholder credentials; host-side REST server (ADR 0046); host files + L7. Concretely: read-only GitHub App token enters the sandbox, read-write token stays on the runner for the post-script (`docs/architecture.md` layer table). Mint: OIDC token → mint (GCF / Cloudflare Worker / standalone) → per-role GitHub App installation token; PEMs in Secret Manager/Worker secrets/filesystem (ADR 0008, 0029). Hosted public mint `https://mint.fullsend.sh` with `PER_REPO_WIF_REPOS=*` public mode (ADR 0059/0068; roadmap fullsend#5116 "Deploy PROD public CF mint at mint.fullsend.sh"). Model keys: Vertex via GCP WIF (no stored key), OpenAI via OpenAI WIF into a run-scoped OpenShell provider (ADR 0092), or an inference gateway trusting forge OIDC (ADR 0137) or `api-key` mode with long-lived `FULLSEND_INFERENCE_GATEWAY_API_KEY` (ADR 0138); fallback `FULLSEND_OPENAI_API_KEY` secret. User secrets for host scripts: one `FULLSEND_GITHUB_RUNNER_SECRETS` JSON secret, never in the sandbox (ADR 0136). GitLab: per-role Developer-level bot PATs/project service accounts (`fullsend-poller`, `fullsend-analyst`, `fullsend-coder`) stored as protected CI/CD variables; **no token mint on GitLab** (`docs/guides/getting-started/configuring-gitlab.md` "Differences from GitHub").
- **Network egress**: per-endpoint and per-binary L7 allowlists via **provider profiles** declared in the harness (`providers: [vertex-ai, github, package-registries, ...]`; ADR 0065). Example: "Vertex AI → claude, node only; GitHub API → gh, git only; Pkg registries → npm, pip, go" (`docs/architecture.md` MVP diagram). Scaffold providers: `github`, `github-ro`, `github-artifacts`, `vertex-ai`, `openai`, `package-registries`, `gitleaks`, `atlassian-cloud` (`internal/scaffold/fullsend-repo/providers/`). Remote resources limited by `allowed_remote_resources` URL prefixes. Security hooks inside the sandbox: Tirith, SSRF, secret scan; pre-agent context-injection scan (`fullsend scan context`); post-agent gitleaks/redaction; post-script protected-path check, pre-commit, `git push --force-with-lease` (`docs/architecture.md`).

## 6. Money and limits

- **No spend budget or cost cap is enforced by Fullsend.** Cost is recorded after the fact: "Fullsend does not calculate inference cost from token counts or maintain a model-price table. Each runtime reports a USD cost value and fullsend records it as-is." claude reads `result.total_cost_usd`; pi sums `usage.cost.total`; **codex "No cost field; records `0`"**; opencode sums `step_finish.part.cost` (`docs/guides/infrastructure/distributed-tracing.md` "Cost data contract"). Surfaces: `metrics.json` `total_cost_usd`, `token_usage`, `per_model_usage`; OTel `fullsend.cost_usd` (rounded to cents); completion status comment footer shows runtime, model, effort, cost (`docs/cli/run.md`; `docs/guides/getting-started/choosing-a-runtime.md`).
- **Limits that exist**: `timeout_minutes` per iteration (default 30) — "Wall-clock budget for one agent iteration"; `validation_loop.max_iterations` (default 1); fix-loop caps (5 bot / 10 total); code-agent CI retry cap ("fixed retry cap"). Runtime-reported behavioural exits `error_max_turns`, `error_max_budget_usd` are passed to the post-script as `FULLSEND_AGENT_EXIT_REASON` (`docs/reference/harness-reference.md`; `docs/cli/run.md` "Budget and deadline"; `docs/guides/user/building-custom-agents.md`). No code path sets a budget flag on the runtime (grep of `internal/` for `--max-budget-usd`/`--max-turns`: none).
- Spend limits are an **open question**: "Should model and MCP ... traffic ... go through a **shared gateway** for authentication, spend limits, allowlists, and telemetry? ... spend limits, allowlists, telemetry and MCP traffic remain open." (`docs/architecture.md` "Agent Infrastructure"). OpenAI WIF guide: "the service account's spend limit is what bounds it" (`docs/guides/infrastructure/openai-workload-identity.md`) — i.e. provider-side caps.
- Cost work on roadmap: fullsend#6433 "hierarchical work-graph correlation IDs for cost rollup", fullsend#5361 cost omits cache tokens (`docs/roadmap.md` "Review quality and cost"). Example real cost in docs: `model=claude-opus-4-6 runtime=claude iterations=1 turns=33 cost_usd=2.16544465` (`docs/guides/user/chaining-follow-up-workflows.md`).

## 7. Forges and trackers

- **GitHub**: full path (per-role Apps, mint, shim, `fullsend github setup`).
- **GitLab**: supported, per-repo only, via `repos.yaml` + `fullsend repos install`; differences table: bot identity = role project service accounts/PATs; "Token mint — Not used — GitLab uses the stored PAT"; event dispatch = cron polling plus native webhook fast-path; inference = operator-created shared `gitlab-oidc` WIF provider; self-hosted GitLab supported via `gitlab.url` (`docs/guides/getting-started/configuring-gitlab.md` "Differences from GitHub", "Self-Hosted GitLab Instances"). Roadmap Now: "A usable GitLab path, including traces from real runs" — i.e. not yet considered fully usable (`docs/roadmap.md`). No formal GitHub/GitLab feature-parity table beyond that differences table.
- **Forgejo: not implemented.** Mentioned in README tagline, ADR template ("State which forges (GitHub, GitLab, Forgejo) this decision applies"), ADR 0005 ("Fullsend must eventually support GitHub, GitLab, and Forgejo"), normative schemas (`docs/normative/entity-context-snapshot/v1/` has a `forgejo` enum and field mappings), and `docs/normative/prescript-output/v1/README.md` ("GitLab and Forgejo scaffolds invoke `fullsend run` directly"). But: `internal/forge/` has only `github`, `gitlab`, `jira` implementations; `internal/forge/forge.go` says "Implementations exist for GitHub (and eventually GitLab, Forgejo)"; config `forge:` accepts "github, gitlab"; behaviour tests say `BEHAVIOUR_SCM=github # also: gitlab; future: forgejo` and reject `"forgejo"` (`pkg/behaviourtest/select_test.go`); ADR 0007: "GitLab and Forgejo will need equivalent per-role identity mechanisms when their forge implementations are built"; no Forgejo install guide, no Forgejo scaffold directory (only `fullsend-repo` and `fullsend-repo-gitlab`). The homepage says "GitHub & GitLab".
- **Trackers**: `tracker: github | gitlab | jira`; Jira is pre-alpha (poller, entity-property locks, Jira service account with Developers + Administrators project roles) and on roadmap Now ("Jira can drive the default agent loop", e.g. Konflux); no Linear, Vikunja, YouTrack or other tracker found.

## 8. Runtimes and model providers

- Runtimes: `claude` (Claude Code, default, `claude -p --agent`, run with `--dangerously-skip-permissions`), `pi` (https://github.com/earendil-works/pi), `codex` (https://github.com/openai/codex, `codex exec --json`), `opencode` (read-only agents only until security-hook adapter #7824), plus test-only `dummy`, `dummy-playback`. Model aliases `opus`/`sonnet`/`haiku`/`fable` remappable via `models.aliases`. Roadmap Next: "Red Hat AI inference routing — waiting on an inference proxy from another team".

## 9. Tenancy, hosting, business model, backing

- Install model: **per-repository only** (per-org mode removed, ADR 0044). "Each self-managed org is a fully independent instance ... They use their own model providers and API keys. The only shared element is the upstream fullsend project" (`docs/architecture.md` "Multi-org deployment model").
- Deployment models: **Managed** (default) — "Hosted by fullsend team" mint + shared `fullsend-ai-*` GitHub Apps; **Self-hosted** — own mint + custom app set (`--app-set`). Docs call the managed variant "the **SaaS installation profile**" (`docs/guides/infrastructure/advanced-setup.md`). The user still supplies inference (own GCP project / OpenAI / gateway); the "managed" part is only the token mint and shared Apps.
- Centrally managed agent-execution service: **not offered**. "If Fullsend offers a centrally managed service, each tenant's repository configuration will use the existing `repos.yaml` v1 manifest. ... service's runtime and deployment model, remain open" (ADR 0123; `docs/architecture.md`).
- **No pricing, paid tier, or business model anywhere** in docs or site (searched "pricing", "SaaS", "hosted"). Community mint budget "~$0" (ADR 0068).
- **Backing: Red Hat.** Community mint owner: "**Red Hat Fullsend Bootstrap** until community operations assumes on-call"; mint must not share infra with "internal Red Hat mints" (ADR 0068). Applied docs for Konflux CI (`docs/problems/applied/konflux-ci/`); first commit "fully agentic konflux-ci development".
